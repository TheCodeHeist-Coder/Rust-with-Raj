How to read this

  1. Every example is complete and runnable. Paste it into a main, add the use lines at the top of its group, and run it.
  2. Every Output block is real text from actually running the program — not written from memory.
  3. Read them in order. Each one adds exactly one idea to the last.
  4. The red notes are traps: code that compiles, gives correct answers, and is silently broken or slow. Those are the ones worth rereading.
01 – 12

Starting threads

The smallest possible thread, then a few at a time.

01basicSpawn one thread
Code
use std::thread;

let h = thread::spawn(|| println!("hello from a thread"));
h.join().unwrap();
Output — real, from running it
hello from a thread
Two halves

spawn starts the thread and returns a JoinHandle. join() waits for it to finish. Almost every example below is these two calls with something interesting in between.

02basicMain keeps working meanwhile
Code
let h = thread::spawn(|| {
    for i in 1..=3 { println!("  child: {i}"); sleep(5); }
});
for i in 1..=3 { println!("main : {i}"); sleep(5); }
h.join().unwrap();
Output — real, from running it
main : 1
  child: 1
main : 2
  child: 2
main : 3
  child: 3

The interleaving is the scheduler's choice — run it again and the order may differ. Never write code that depends on it.

03basicA thread returns a value
Code
let h = thread::spawn(|| 6 * 7);
let answer: i32 = h.join().unwrap();
println!("answer = {answer}");
Output — real, from running it
answer = 42
No shared variable needed

The closure's last expression is the thread's return value, and join() hands it back. You do not need a Mutex just to collect a result.

04basicWhy join() returns Result
Code
let h = thread::spawn(|| "I was joined");
println!("{}", h.join().unwrap());
Output — real, from running it
I was joined

join() returns Result because the thread might have panicked. Example 11 shows the Err case.

05basicSeveral threads at once
Code
let mut handles = Vec::new();
for id in 0..3 {
    handles.push(thread::spawn(move || {
        println!("  worker {id} done");
        id * 10
    }));
}
let results: Vec<i32> = handles.into_iter()
    .map(|h| h.join().unwrap())
    .collect();
Output — real, from running it
  worker 0 done
  worker 1 done
  worker 2 done
results = [0, 10, 20]
Push all, then join all

Spawn every thread before joining any. Spawning and joining one at a time makes the code fully sequential — see example 41, where that mistake costs 3x.

06basicMove a String into a thread
Code
let name = String::from("Ferris");
let h = thread::spawn(move || format!("hello, {name}!"));
println!("{}", h.join().unwrap());
Output — real, from running it
hello, Ferris!
Why move

Without it: "closure may outlive the current function" (E0373). Nothing guarantees the thread finishes before main returns, so borrowing a local is refused. move transfers ownership, so the data lives as long as the thread.

07basicMove a Vec, compute, return
Code
let nums = vec![1, 2, 3, 4, 5];
let h = thread::spawn(move || nums.iter().sum::<i32>());
println!("sum = {}", h.join().unwrap());
Output — real, from running it
sum = 15

nums is gone from main after the move. If you still need it there, clone it first (example 8) or use a scoped thread (example 37).

08basicOne clone per thread
Code
let base = String::from("task");
for i in 0..3 {
    let mine = base.clone();       // clone BEFORE the move
    hs.push(thread::spawn(move || format!("{mine}-{i}")));
}
Output — real, from running it
  task-0
  task-1
  task-2
Clone outside the closure

The clone must happen in the loop body, not inside the closure — inside, base would already have been moved by the first iteration. This exact shape reappears with Arc::clone in example 14.

09basicName a thread
Code
let h = thread::Builder::new()
    .name("counter".to_string())
    .spawn(|| {
        let me = thread::current();
        format!("running as {:?}", me.name().unwrap())
    }).unwrap();
Output — real, from running it
running as "counter"

Names show up in panic messages, which makes debugging much easier than thread '<unnamed>' panicked.

10basicHow many cores?
Code
println!("{}", thread::available_parallelism().unwrap());
Output — real, from running it
available_parallelism = 12
Use this to size a pool

It respects container/cgroup limits, so it is correct inside Docker where a raw CPU count is not.

11mediumA panic stays in its thread
Code
let h = thread::spawn(|| { panic!("worker exploded"); });
match h.join() {
    Ok(_)  => println!("thread finished normally"),
    Err(_) => println!("thread panicked, but main is alive"),
}
println!("main still running");
Output — real, from running it
thread '<unnamed>' panicked at: worker exploded
thread panicked, but main is alive
main still running
Never joining hides failures

The process survives, but if you do not join, the panic is invisible and your program carries on with work half-done. Join even when you do not need the return value.

12basicProof that it is concurrent
Code
// sequential
sleep(30); sleep(30);              // 60ms

// concurrent
let a = thread::spawn(|| sleep(30));
let b = thread::spawn(|| sleep(30));
a.join().unwrap(); b.join().unwrap();  // 30ms
Output — real, from running it
sequential sleeps: 60
concurrent sleeps: 30
The whole point, in two numbers

Both sleeps happen at the same time, so the total is 30ms rather than 60ms. Sleeping is I/O-like — see example 43 for real CPU work.

13 – 26

Sharing data

One value, many threads. This is where most confusion lives.

13mediumThe wrong way (it compiles!)
Code
let mut counter = 0;
for _ in 0..5 {
    hs.push(thread::spawn(move || { counter += 1; }));
}
for h in hs { h.join().unwrap(); }
println!("counter = {counter}");
Output — real, from running it
counter = 0   <-- WRONG, each thread got a copy
The one mistake Rust lets through

i32 is Copy, so move gives each thread its own private copy. Five copies each reach 1 and are discarded. There is no unsafety here — nothing is shared, so there is nothing to protect. Rust prevents data races, not wrong programs. The compiler does hint: "did you mean to capture by reference instead?"

14basicArc: shared reading
Code
let data = Arc::new(vec![10, 20, 30]);
for i in 0..3 {
    let d = Arc::clone(&data);      // clone the HANDLE
    hs.push(thread::spawn(move || d[i]));
}
Output — real, from running it
read concurrently = [10, 20, 30]
No lock needed to read

Arc gives many owners of one value. Every thread only reads, and many shared references are always safe — the same borrowing rule as single-threaded Rust. Locks are only for mutation.

15basicWhat Arc::clone actually does
Code
let a = Arc::new(1);
println!("{}", Arc::strong_count(&a));   // 1
let b = Arc::clone(&a);
println!("{}", Arc::strong_count(&a));   // 2
drop(b);
println!("{}", Arc::strong_count(&a));   // 1
Output — real, from running it
count with 1 handle  = 1
count with 2 handles = 2
after drop           = 1
Cheap, not a deep copy

Arc::clone copies a pointer and bumps an atomic counter. The data is never duplicated. It is written Arc::clone(&x) rather than x.clone() by convention, so readers can see no deep copy is happening.

16basicArc<Mutex<T>>: the right counter
Code
let c = Arc::new(Mutex::new(0));
for _ in 0..5 {
    let c = Arc::clone(&c);
    hs.push(thread::spawn(move || { *c.lock().unwrap() += 1; }));
}
Output — real, from running it
counter = 5   <-- correct
Read the type as a sentence

Arc = shared ownership. Mutex = exclusive access. Arc<Mutex<i32>> = many owners of one lock protecting an integer. Arc must be outermost so every thread can hold a handle.

17basicScaled up: 8 x 1000
Code
for _ in 0..8 {
    let c = Arc::clone(&c);
    hs.push(thread::spawn(move || {
        for _ in 0..1000 { *c.lock().unwrap() += 1; }
    }));
}
Output — real, from running it
8 x 1000 = 8000
Exactly 8000, every run

Run it a hundred times and it is always 8000. Compare example 22, where an unsynchronised version loses more than half its increments.

18basicSharing a Vec
Code
let v = Arc::new(Mutex::new(Vec::new()));
for i in 0..5 {
    let v = Arc::clone(&v);
    hs.push(thread::spawn(move || v.lock().unwrap().push(i)));
}
Output — real, from running it
pushed (sorted) = [0, 1, 2, 3, 4]
Order is never guaranteed

The mutex stops the pushes corrupting each other. It says nothing about which thread goes first — that is the scheduler's business. Sort before asserting on concurrently-produced results.

19mediumSharing a HashMap
Code
let m = Arc::new(Mutex::new(HashMap::new()));
for chunk in words.chunks(2) {
    let m = Arc::clone(&m);
    hs.push(thread::spawn(move || {
        for w in chunk {
            *m.lock().unwrap().entry(w).or_insert(0) += 1;
        }
    }));
}
Output — real, from running it
word counts = [("a", 3), ("b", 2), ("c", 1)]
This locks once per word

Heavy contention. A better design gives each thread its own local HashMap and merges them at the end under one lock. The general rule: lock once per batch, not once per item.

20mediumControlling when the lock releases
Code
{
    let mut g = m.lock().unwrap();
    *g += 100;
    println!("holding lock: {}", *g);
}   // <- lock released HERE, when g is dropped
println!("outside: {}", *m.lock().unwrap());
Output — real, from running it
inside block, holding lock: 100
outside block: 100
There is no unlock()

The MutexGuard unlocks when it is dropped — the Drop trait doing real work. So the lock is held exactly as long as the guard lives. Use a { } block, or a single statement, to keep that short.

21basicAtomics: no lock at all
Code
let a = Arc::new(AtomicUsize::new(0));
// in each of 8 threads, 1000 times:
a.fetch_add(1, Ordering::Relaxed);
// read it:
a.load(Ordering::SeqCst)
Output — real, from running it
atomic counter = 8000
Note the &self

fetch_add mutates through a shared reference — no &mut, no lock, no blocking. The hardware guarantees the operation is indivisible. For a single number this is much faster than a mutex.

22advancedThe lost update, live
Code
// RACY: two separate atomic operations
let v = b.load(Ordering::Relaxed);    // read
b.store(v + 1, Ordering::Relaxed);    // ...then write

// CORRECT: one atomic read-modify-write
g.fetch_add(1, Ordering::Relaxed);
Output — real, from running it
load+store: 82557 of 200000  <-- LOST UPDATES
fetch_add : 200000 of 200000  <-- correct
Two atomic ops are not one atomic op

Between the load and the store, another thread can slip in — the classic lost update. Here more than half the work vanished. Both versions are perfectly safe Rust with no data race, so the compiler cannot catch this. It is a logic error. Run it again and you get a different number, which is exactly what makes race bugs so expensive to find.

23mediumAtomicBool as a stop flag
Code
let stop = Arc::new(AtomicBool::new(false));
let s = Arc::clone(&stop);
let worker = thread::spawn(move || {
    while !s.load(Ordering::Relaxed) { /* work */ }
});
stop.store(true, Ordering::Relaxed);   // tell it to finish
Output — real, from running it
worker stopped when the flag was set

The standard shutdown pattern for a long-running thread. A channel disconnect (example 40) also works and is often cleaner.

24mediumRwLock: many readers, one writer
Code
let rw = Arc::new(RwLock::new(vec![1, 2, 3]));

rw.read().unwrap().len();     // concurrent with other readers
rw.write().unwrap().push(4);  // exclusive
Output — real, from running it
4 concurrent readers saw = [3, 3, 3, 3]
after one writer         = [1, 2, 3, 4]
Not automatically faster

RwLock does more bookkeeping than Mutex. It wins only when reads heavily dominate and critical sections are non-trivial. A steady stream of readers can also starve a waiting writer.

25mediumMutex poisoning
Code
// a thread panics while holding the lock
thread::spawn(move || {
    let _g = m2.lock().unwrap();
    panic!("died holding lock");
}).join();

println!("{}", m.lock().is_err());          // true
// recover anyway if you decide it is sound:
match m.lock() { Ok(g) => .., Err(p) => p.into_inner() }
Output — real, from running it
is_err after panic = true
recovered anyway   = [1, 2, 3]
Why lock() returns Result

If a thread panics mid-update, the data may be half-modified, so the mutex is poisoned and later locks return Err. Most code writes .lock().unwrap(), propagating the panic — usually right, since something already went wrong.

26basicChoosing between them
Code
// one number or flag        -> Atomic
// a whole data structure    -> Mutex
// structure, mostly read    -> RwLock
// read-only shared data     -> Arc alone, no lock
Output — real, from running it
Arc      = shared ownership (many handles)
Mutex    = exclusive access  (one at a time)
The decision in one line

If a single atomic can express it, it beats any lock. If the data is never mutated, you need no lock at all — just Arc. Wrapping immutable config in a Mutex is a common reflex that costs speed and buys nothing.

27 – 36

Channels

Instead of sharing data under a lock, send it. Often the simpler design.

27basicSend one message
Code
let (tx, rx) = mpsc::channel();
thread::spawn(move || tx.send("hello from thread").unwrap());
println!("received: {}", rx.recv().unwrap());
Output — real, from running it
received: hello from thread
tx and rx

tx is the transmitter, rx the receiver. mpsc = multi-producer, single-consumer: you can clone tx freely, but there is only ever one rx.

28basicSend several, collect them all
Code
let (tx, rx) = mpsc::channel();
thread::spawn(move || { for i in 1..=4 { tx.send(i).unwrap(); } });
let got: Vec<i32> = rx.iter().collect();
Output — real, from running it
got = [1, 2, 3, 4]

rx.iter() blocks and yields messages until every sender is dropped. Here tx was moved into the thread, so it dies when the closure ends.

29mediumMany producers
Code
let (tx, rx) = mpsc::channel();
for i in 0..4 {
    let tx = tx.clone();               // one sender per producer
    thread::spawn(move || tx.send(i * i).unwrap());
}
drop(tx);                              // <-- essential
let got: Vec<i32> = rx.iter().collect();
Output — real, from running it
squares = [0, 1, 4, 9]
The line everyone forgets

rx.iter() ends only when every sender is gone. The original tx is still alive in main, so without drop(tx) the receiver waits forever. No error, no panic — the program just hangs.

30mediumProof of what drop(tx) does
Code
let (tx, rx) = mpsc::channel::<i32>();
let tx2 = tx.clone();
thread::spawn(move || { tx2.send(1).unwrap(); });
drop(tx);                    // remove main's sender
let n: Vec<i32> = rx.iter().collect();
Output — real, from running it
terminated cleanly, got [1]
Shutdown by ownership

You never write a "stop" message. The channel closes when the last sender is dropped, and the receiver loop ends on its own. Ownership is doing your shutdown logic.

31mediumSending moves ownership
Code
let (tx, rx) = mpsc::channel();
thread::spawn(move || {
    let data = vec![String::from("a"), String::from("b")];
    tx.send(data).unwrap();
    // data is GONE here — it moved into the channel
});
println!("{:?}", rx.recv().unwrap());
Output — real, from running it
received vec = ["a", "b"]
Why channels are safe

send takes the value by value. Afterwards the sender provably cannot touch it — using it is E0382. There is no shared mutable state, so there is nothing to race on. In C++ you would send a pointer and hope.

32mediumProducer and consumer threads
Code
let (tx, rx) = mpsc::channel();
let prod = thread::spawn(move || { for i in 1..=5 { tx.send(i).unwrap(); } });
let cons = thread::spawn(move || rx.iter().sum::<i32>());
prod.join().unwrap();
println!("{}", cons.join().unwrap());
Output — real, from running it
consumer summed = 15

The classic producer–consumer problem, in six lines. No mutex, no condvar — the channel handles the buffering and the blocking.

33basictry_recv: do not block
Code
rx.try_recv().is_err()    // true, nothing there yet
tx.send(7).unwrap();
rx.try_recv()             // Ok(7)
Output — real, from running it
before send, try_recv is_err = true
after send,  try_recv = Ok(7)

Use try_recv when a thread has other work to do and should not sit blocked — a game loop polling for events, for instance.

34basicrecv_timeout: wait, but not forever
Code
let r = rx.recv_timeout(Duration::from_millis(20));
println!("timed out = {}", r.is_err());
Output — real, from running it
timed out as expected = true
A deadlock escape hatch

Any blocking call that can wait forever is a hang waiting to happen. Timeouts turn a hang into an error you can handle.

35mediumBounded channel = backpressure
Code
let (tx, rx) = mpsc::sync_channel::<i32>(2);   // capacity 2
// send() now BLOCKS when the buffer is full
Output — real, from running it
  sent 1
  sent 2
  sent 3
  sent 4
got = [1, 2, 3, 4]
Prefer bounded for long-running work

channel() is unbounded — a fast producer can queue millions of items and exhaust memory. sync_channel(n) forces the producer to slow to the consumer's pace.

36advancedA two-stage pipeline
Code
let (tx1, rx1) = mpsc::channel::<i32>();
let (tx2, rx2) = mpsc::channel::<i32>();

thread::spawn(move || { for i in 1..=4 { tx1.send(i).unwrap(); } });
thread::spawn(move || { for v in rx1 { tx2.send(v * 10).unwrap(); } });

let out: Vec<i32> = rx2.iter().collect();
Output — real, from running it
pipeline out = [10, 20, 30, 40]
Shutdown cascades automatically

Stage 1 finishes → tx1 drops → for v in rx1 ends → tx2 drops → main's loop ends. Each stage closes the next, with no flags or sentinel values.

37 – 40

Borrowing across threads

Scoped threads let you skip Arc entirely when threads are short-lived.

37mediumBorrow locals — no Arc, no move
Code
let local = vec![1, 2, 3, 4];

let total = thread::scope(|s| {
    let a = s.spawn(|| local[0] + local[1]);    // borrows!
    let b = s.spawn(|| local[2] + local[3]);    // borrows!
    a.join().unwrap() + b.join().unwrap()
});
// local is STILL usable here
Output — real, from running it
scoped total = 10  (local still usable: [1, 2, 3, 4])
Why this is allowed

scope guarantees every thread is joined before it returns, so the borrows provably cannot outlive local. That removes the 'static requirement that forces move everywhere else. Stabilised in Rust 1.63.

38mediumSplit a slice and sum in parallel
Code
let data: Vec<i64> = (1..=100).collect();
let mid = data.len() / 2;

let sum = thread::scope(|s| {
    let (l, r) = data.split_at(mid);
    let a = s.spawn(move || l.iter().sum::<i64>());
    let b = s.spawn(move || r.iter().sum::<i64>());
    a.join().unwrap() + b.join().unwrap()
});
Output — real, from running it
parallel sum 1..=100 = 5050
Disjoint borrows

split_at proves the halves do not overlap, so two threads can hold them at once. The move here moves the slice references (which are Copy), not the data.

39advancedChunked parallel map
Code
let partials: Vec<u64> = thread::scope(|s| {
    data.chunks(2)
        .map(|c| s.spawn(move || c.iter().sum::<u64>()))
        .collect::<Vec<_>>()          // spawn ALL first!
        .into_iter()
        .map(|h| h.join().unwrap())
        .collect()
});
Output — real, from running it
chunk sums = [3, 7, 11, 15], total = 36
That collect() in the middle

Without it, iterator laziness spawns and joins each thread one at a time — correct results, zero parallelism. The same trap as example 5, and example 41 measures what it costs. In production, rayon's par_iter() does all of this for you.

40advancedA worker pool
Code
let (tx, rx) = mpsc::channel::<u32>();
let rx = Arc::new(Mutex::new(rx));       // share the single consumer

for _ in 0..3 {
    let rx = Arc::clone(&rx);
    workers.push(thread::spawn(move || loop {
        let job = { rx.lock().unwrap().recv() };   // braces matter!
        match job {
            Ok(n)  => { out.lock().unwrap().push(n * n); }
            Err(_) => break,                       // channel closed
        }
    }));
}
for i in 1..=6 { tx.send(i).unwrap(); }
drop(tx);                                 // triggers shutdown
Output — real, from running it
pool squared = [1, 4, 9, 16, 25, 36]
The braces are load-bearing

{ rx.lock().unwrap().recv() } drops the guard at the closing brace, before the job runs. Without them the lock is held for the whole loop body and your three workers run strictly one at a time. Example 42 measures exactly this mistake.

41 – 52

Traps and real patterns

Code that looks right, runs correctly, and is secretly serial — plus the coordination tools.

41advancedTRAP: spawn-then-join is sequential
Code
// WRONG — spawns and joins one at a time
(0..3).map(|_| thread::spawn(|| sleep(20)).join().unwrap())

// RIGHT — spawn all, then join all
let hs: Vec<_> = (0..3).map(|_| thread::spawn(|| sleep(20))).collect();
for h in hs { h.join().unwrap(); }
Output — real, from running it
spawn+join per item : 60ms  <-- SEQUENTIAL
collect() then join : 20ms  <-- parallel
3x slower, identical output

Both versions produce the same results, so tests pass and nothing warns you. Only the clock tells you. Always spawn every thread before joining any.

42advancedTRAP: working while holding a lock
Code
// WRONG — lock held during the work
let mut g = m.lock().unwrap();
expensive_work();
*g += 1;

// RIGHT — work first, lock briefly
expensive_work();
*m.lock().unwrap() += 1;
Output — real, from running it
work INSIDE lock : 81ms  <-- serialised
work OUTSIDE lock: 20ms  <-- parallel
Amdahl's law in miniature

Everything inside a lock is serialised. Holding one across expensive work makes your serial fraction 100%, and four threads run like one. Never do I/O, sleep, or heavy computation while holding a lock.

43mediumReal speedup on real CPU work
Code
let t = Instant::now();
for i in 0..4 { black_box(work(black_box(i))); }
let seq = t.elapsed();

let t = Instant::now();
let hs: Vec<_> = (0..4).map(|i| thread::spawn(move || work(i))).collect();
for h in hs { h.join().unwrap(); }
let par = t.elapsed();
Output — real, from running it
sequential 16.79ms / parallel 4.47ms = 3.76x speedup
Use black_box when benchmarking

An earlier version of this measurement reported 94 nanoseconds for 160 million iterations, because rustc -O saw the result was unused and deleted the loop. If a benchmark looks impossibly fast, it did not run. std::hint::black_box hides values from the optimiser.

44advancedAvoiding deadlock: lock ordering
Code
// BOTH threads take A before B, always.
let _x = a.lock().unwrap();
let _y = b.lock().unwrap();
Output — real, from running it
t1 ok / t2 ok  (both took A before B)
The fix worth memorising

Deadlock needs a circular wait. If every thread acquires locks in the same global order, a cycle is impossible. Order by address, by ID, or by a documented convention — and write the convention down.

45advancedThe deadlock that would have happened
Code
// thread 1: lock A, then try B
// thread 2: lock B, then try A     <-- opposite order!
match b1.try_lock() {
    Ok(_)  => "got both",
    Err(_) => "could NOT get B",
}
Output — real, from running it
t1: could NOT get B
t2: got both
Rust does not prevent deadlock

Data races are compile errors; deadlock is not — it is not a memory-safety violation. With blocking lock() calls this program hangs forever with no panic and no error. try_lock at least lets you detect and back off.

46advancedCondvar: wait without spinning
Code
let (lock, cv) = &*pair;
let mut ready = lock.lock().unwrap();
while !*ready {                        // while, NOT if
    ready = cv.wait(ready).unwrap();
}
Output — real, from running it
woken by notify, ready = true
Always while, never if

wait can return spuriously with no notification at all, and another thread may consume the condition before you re-acquire the lock. Re-checking in a loop is the only correct form — in every language. Note wait consumes the guard and returns a new one, encoding "the lock is released while waiting" in the type system.

47advancedA bounded queue from scratch
Code
let (m, cv) = &*q;
let mut g = m.lock().unwrap();
while g.is_empty() { g = cv.wait(g).unwrap(); }
while let Some(v) = g.pop_front() { got.push(v); }
Output — real, from running it
drained = [1, 2, 3, 4]

The producer–consumer problem built by hand from a mutex and a condvar. In practice you would use a channel — but this is what a channel is doing internally, and it is standard interview material.

50mediumFan-out, fan-in
Code
let (tx, rx) = mpsc::channel();
for id in 0..4 {
    let tx = tx.clone();
    thread::spawn(move || {
        let result = compute(id);
        tx.send((id, result)).unwrap();     // tag results with their source
    });
}
drop(tx);
let mut results: Vec<(i32, i32)> = rx.iter().collect();
results.sort();
Output — real, from running it
fan-in results = [(0, 5050), (1, 10100), (2, 15150), (3, 20200)]
Send the id alongside the result

Results arrive in whatever order threads finish. Tagging each with its source lets you sort afterwards and get deterministic output from non-deterministic execution.

let hs: Vec<_> = (0..4).map(|i| thread::spawn(move || {

Two layers of failure

join() returns Result for panics; your closure returns Result for expected errors. Keep them separate — a panic means a bug, a returned Err means a handled failure.

52basicWhich tool do I reach for?
Code
// split a local computation  -> thread::scope
// read-only shared data      -> Arc<T>
// shared mutable data        -> Arc<Mutex<T>>
// read-heavy shared data     -> Arc<RwLock<T>>
// one counter or flag        -> Arc<AtomicUsize>
// hand work between threads  -> mpsc::channel
// wait for a condition       -> Condvar
// all threads meet up        -> Barrier
// many jobs, few threads     -> worker pool / rayon
// 10k concurrent I/O waits   -> async, NOT threads

Two defaults worth internalising

Prefer message passing to shared state, and prefer scoped threads to Arc. Reach for a lock only when data genuinely must be shared and mutated. Most threading pain comes from choosing a heavier tool than the problem needs.
