SET 01

Spawning and joining

Getting work onto a thread and results back off it.

1.1easy Return a value from a thread

Task

Spawn a thread that sums 1..=100 and get the answer back in main.

Solution
Answer — verified 5050
thread::spawn(|| (1..=100u64).sum::<u64>())
    .join()
    .unwrap()
Why unwrap

join() returns Result because the thread might have panicked. The closure's final expression is the thread's return value — no shared variable needed.

1.2easy Spawn several, collect all

Task

Spawn four threads computing i * i for i in 0..4, and collect the results in order.

Solution
Answer — verified [0, 1, 4, 9]
let hs: Vec<_> = (0..4)
    .map(|i| thread::spawn(move || i * i))
    .collect();                          // collect FIRST

hs.into_iter().map(|h| h.join().unwrap()).collect()
The collect() is essential

Without it, laziness means each thread is spawned and immediately joined — fully sequential, no parallelism at all. You must spawn all the threads before joining any. This is the single most common way to accidentally write serial code.

1.3easy Move data into a thread

Task

Sum a local Vec<i32> inside a spawned thread. Predict the compiler error if you forget one keyword.

Solution
Answer — verified 6
let d = vec![1, 2, 3];
thread::spawn(move || d.iter().sum()).join().unwrap()
Without move: E0373

"closure may outlive the current function." Nothing guarantees the thread finishes before main returns, so borrowing a local is rejected. move transfers ownership and satisfies 'static.

1.4medium Detect a panicked thread

Task

Spawn a thread that panics. Show that main survives, and detect the failure.

Solution
Answer — verified true
thread::spawn(|| panic!("x")).join().is_err()
Silent failure

A panic in a spawned thread does not kill the process — it unwinds only that thread. If you never join, the failure is invisible and your program continues with work half-done. Join even when you do not need the value.

1.5easy How many cores?

Task

Print the number of threads the machine can usefully run in parallel.

Solution
Answer — 12 on the test machine
thread::available_parallelism().unwrap().get()

The right default for sizing a CPU-bound worker pool. It respects cgroup limits, so it is correct inside containers where num_cpus may not be.

1.6medium Predict: what does this print?

Task

This compiles with only a warning. Predict the output before running.

Compiles — but is it right?
let mut counter = 0;
let mut hs = vec![];
for _ in 0..5 {
    hs.push(thread::spawn(move || { counter += 1; }));
}
for h in hs { h.join().unwrap(); }
println!("{counter}");

Prints

Solution
Prints 0
// i32 is Copy, so `move` gives each thread its OWN copy.
// Five private counters each reach 1, then are discarded.
// The original never changes.
Rust does not catch this

There is no unsafety here — no sharing, no race, nothing to protect. It is a pure logic error, and Rust prevents data races, not wrong programs. The compiler does hint: "did you mean to capture by reference instead?" The real fix is Arc<Mutex<i32>> or an atomic.

SET 02

Arc — sharing ownership

Many threads, one value, no copying.

2.1easy Share a vector for reading

Task

Three threads each read the length of one shared Vec. No cloning of the data itself.

Solution
Answer — verified 15 (3 × 5)
let data = Arc::new(vec![1,2,3,4,5]);

let hs: Vec<_> = (0..3).map(|_| {
    let d = Arc::clone(&data);      // clone the HANDLE, not the data
    thread::spawn(move || d.len())
}).collect();
The clone-before-move idiom

Arc::clone must happen outside the closure — inside, the original would already have been moved. This two-line pattern appears in every threaded Rust program.

2.2easy Count the references

Task

Create an Arc, clone it once, and print the strong count. Predict the number.

Solution
Answer — verified 2
let a = Arc::new(5);
let _b = Arc::clone(&a);
Arc::strong_count(&a)      // → 2

The value is dropped when this reaches zero. Each Arc::clone is one atomic increment; each drop is one atomic decrement.

2.3medium Index into shared data per thread

Task

Given vec![10, 20, 30], spawn one thread per index that returns that element. Sum the results.

Solution
Answer — verified 60
let data = Arc::new(vec![10,20,30]);
let hs: Vec<_> = (0..3).map(|i| {
    let d = Arc::clone(&data);
    thread::spawn(move || d[i])
}).collect();
Why no lock is needed

Every thread only reads. Arc<T> hands out &T, and many shared references are always safe — the borrowing rule from single-threaded Rust, unchanged. Locks are only for mutation.

2.4medium Why not Rc?

Task

Replace Arc with Rc in 2.1 and read the error. Name the trait and explain the underlying danger.

Trait, and why

Solution
E0277: Rc<i32> cannot be sent between threads safely
// = help: the trait `Send` is not implemented for `Rc<i32>`
// note: required by a bound in `spawn`
//   F: Send + 'static
The real danger

Rc's refcount is a plain integer, incremented non-atomically. Two threads cloning simultaneously hit exactly the lost-update race from the fundamentals guide — the count ends too low, the value is freed while still in use, and you have a use-after-free. Arc pays for an atomic counter to make this impossible.

SET 03

Mutex — shared mutation

The Arc<Mutex<T>> pattern, and the ways it goes wrong.

3.1easy The shared counter, done right

Task

Eight threads each increment a shared counter 1000 times. Fix exercise 1.6 properly. Run it several times — the answer must be identical every run.

Solution
Answer — verified 8000, every run
let c = Arc::new(Mutex::new(0));

let hs: Vec<_> = (0..8).map(|_| {
    let c = Arc::clone(&c);
    thread::spawn(move || {
        for _ in 0..1000 {
            *c.lock().unwrap() += 1;   // guard drops at ';'
        }
    })
}).collect();
Read the type aloud

Arc<Mutex<i32>> — shared ownership of exclusive access to an integer. Arc outside so every thread holds a handle; Mutex inside because the data is what needs protecting.

3.2easy Collect into a shared vector

Task

Five threads each push their index into one shared Vec. Why must you sort the result before asserting on it?

Solution
Answer — verified [0, 1, 2, 3, 4] after sorting
let v = Arc::new(Mutex::new(Vec::new()));
// each thread: v.lock().unwrap().push(i);
let mut out = v.lock().unwrap().clone();
out.sort();
Order is never guaranteed

The mutex guarantees the pushes do not corrupt each other. It says nothing about which thread gets the lock first — that is the scheduler's choice and it varies per run. Never assert on the order of concurrently produced results.

3.3medium Parallel word count

Task

Split ["a","b","a","c","b","a"] into chunks, count words across threads into one shared HashMap.

Solution
Answer — verified [("a", 3), ("b", 2), ("c", 1)]
let m = Arc::new(Mutex::new(HashMap::new()));

// per thread, over its own chunk:
for w in chunk {
    *m.lock().unwrap().entry(w).or_insert(0usize) += 1;
}
A better design

This locks once per word — heavy contention. Faster: give each thread its own local HashMap, then merge the maps at the end under one lock. Map-reduce, and the general lesson is to lock once per batch, not once per item.

3.4medium Poison a mutex

Task

Panic inside a thread while holding a lock, then show the mutex is poisoned from main.

Solution
Answer — verified poisoned=true
let _ = thread::spawn(move || {
    let _g = m2.lock().unwrap();
    panic!("poison");
}).join();

let poisoned = m.lock().is_err();   // bind, do not tail-return
poisoned
A real error I hit writing this

Writing m.lock().is_err() as the function's tail expression gives E0597: m does not live long enough — the temporary guard outlives m at the end of scope. Bind the boolean to a variable first. Temporary lifetimes in tail position are a genuine trap.

3.5hard Find the accidental serialisation

Task

This worker pool compiles and produces correct results, but runs no faster than one thread. Why?

Correct, but serial
thread::spawn(move || loop {
    let guard = rx.lock().unwrap();
    match guard.recv() {
        Ok(job) => expensive_work(job),   // still holding the lock!
        Err(_) => break,
    }
})
Solution
The fix: drop the guard before working
thread::spawn(move || loop {
    let job = { rx.lock().unwrap().recv() };   // ← braces!
    match job {
        Ok(job) => expensive_work(job),        // lock released
        Err(_) => break,
    }
})
Critical sections again

guard lives until the end of the loop body, so each worker holds the lock while doing its work — the others queue behind it. The braces confine the guard to just the recv(). This is Amdahl's law in miniature: your serial fraction was accidentally 100%, and nothing warns you.

SET 04

Atomics

Lock-free counters, and the trap that catches everyone.

4.1easy An atomic counter

Task

Redo the 8×1000 counter with AtomicUsize instead of a mutex.

Solution
Answer — verified 8000
let a = Arc::new(AtomicUsize::new(0));
// per thread:
a.fetch_add(1, Ordering::Relaxed);
// read:
a.load(Ordering::SeqCst)
Note the &self

fetch_add mutates through a shared reference. Atomics provide interior mutability, safely, because the hardware guarantees indivisibility. No &mut, no lock, no blocking.

4.2hard Reproduce a lost update

Task

Using only safe Rust, write two versions of a 4×50,000 counter: one with a separate load then store, one with fetch_add. Run several times.

Solution
Verified — expected 200000
// RACY: two separate atomic operations
let v = a.load(Ordering::Relaxed);
a.store(v + 1, Ordering::Relaxed);
// → racy=162176  (lost 37824)

// CORRECT: one atomic read-modify-write
b.fetch_add(1, Ordering::Relaxed);
// → atomic=200000
Two atomic operations ≠ one atomic operation

There is a window between the load and the store where another thread can intervene — the classic lost update. Rust cannot catch this: both versions are safe code with no data race. It is a logic error.

Run it repeatedly and you get a different number every time — one earlier run of this same program gave 136210 out of 400,000. That non-reproducibility is exactly what makes race bugs so expensive to find.

4.3medium A shutdown flag

Task

Use an AtomicBool to signal from one thread to another. Which orderings pair up?

Solution
Answer — verified true
let flag = Arc::new(AtomicBool::new(false));

// signaller:
f.store(true, Ordering::Release);

// observer:
flag.load(Ordering::Acquire)
Release/Acquire pair

Release on the write, Acquire on the read. Together they create a happens-before edge: everything the signaller did before the store is visible to any thread that observes it via the load. This is how you publish data safely without a lock.

4.4medium Mutex or atomic?

Task

No code — decide. For each, write Atomic, Mutex, or RwLock:

a) a request counter

b) a shared HashMap cache, read constantly, written rarely

c) a Vec that threads push to

d) a "should we stop?" flag

Solution
Answers
// a) Atomic  — one integer, fetch_add
// b) RwLock  — reads dominate heavily
// c) Mutex   — a whole data structure, writes are the point
// d) Atomic  — one bool, AtomicBool
The rule

One machine-word value → atomic. A data structure → mutex. A data structure read far more than written → rwlock. If a single atomic can express it, it will be faster than any lock.

SET 05

Channels

Message passing — sharing memory by communicating.

5.1easy Many producers, one consumer

Task

Four threads each send i*i. Collect everything in main. There is one line beginners always forget.

Solution
Answer — verified [0, 1, 4, 9]
let (tx, rx) = mpsc::channel();
for i in 0..4 {
    let tx = tx.clone();
    thread::spawn(move || tx.send(i*i).unwrap());
}
drop(tx);                         // ← THE forgotten line
let mut v: Vec<i32> = rx.iter().collect();
Without drop(tx) it hangs forever

rx.iter() ends only when every sender is dropped. The original tx is still alive in main, so the receiver waits for a message that will never come. No error, no panic — just a hung program.

5.2easy Producer and consumer threads

Task

One thread produces 1..=5, a second consumes and sums them. main waits for both.

Solution
Answer — verified 15
let (tx, rx) = mpsc::channel();
let p = thread::spawn(move || { for i in 1..=5 { tx.send(i).unwrap(); } });
let c = thread::spawn(move || rx.iter().sum::<i32>());
p.join().unwrap();
c.join().unwrap()

No drop(tx) needed here — tx was moved into the producer thread and dies when that closure ends.

5.3medium Backpressure with a bounded channel

Task

Use a channel with capacity 2 and send 4 items. What happens to the producer on the third send?

Solution
Answer — verified [1, 2, 3, 4]
let (tx, rx) = mpsc::sync_channel::<u32>(2);
// send() BLOCKS when the buffer is full,
// resuming when the consumer takes one.
Why bounded is usually right

An unbounded channel lets a fast producer queue millions of items and exhaust memory. A bounded one applies backpressure — the producer is forced to slow to the consumer's pace. For any long-running system, prefer sync_channel.

5.4hard A two-stage pipeline

Task

Chain two channels: stage 1 emits 1..=4, stage 2 multiplies by 10, main collects.

Solution
Answer — verified [10, 20, 30, 40]
let (tx1, rx1) = mpsc::channel::<u32>();
let (tx2, rx2) = mpsc::channel::<u32>();

thread::spawn(move || { for i in 1..=4 { tx1.send(i).unwrap(); } });
thread::spawn(move || { for v in rx1 { tx2.send(v*10).unwrap(); } });

let v: Vec<u32> = rx2.iter().collect();
Shutdown cascades for free

When stage 1 finishes, tx1 drops, so for v in rx1 ends, so tx2 drops, so main's loop ends. Each stage closes the next automatically — ownership doing your shutdown logic with no flags or sentinels.

5.5medium Why is send safe?

Task

No code. Explain why sending a Vec down a channel and then using it in the sender cannot compile — and which error you get.

Error, and the reason

Solution
E0382: use of moved value
tx.send(data).unwrap();
println!("{data:?}");   // error: value used after move
Ownership doing concurrency work

send takes the value by value. Once sent, the receiver owns it and the sender provably cannot touch it — so there is no shared mutable state and nothing to race on. In C++ you would send a pointer and hope nobody modifies the original. Here it is a compile error, using the same move rule from the ownership guide.

SET 06

Scoped threads, RwLock, Condvar

Borrowing across threads, read-heavy sharing, and waiting properly.

6.1easy Borrow a local from two threads

Task

Sum vec![1,2,3,4] using two threads that borrow it — no Arc, no move, no clone.

Solution
Answer — verified 10
let local = vec![1,2,3,4];

thread::scope(|s| {
    let a = s.spawn(|| local[0]+local[1]);
    let b = s.spawn(|| local[2]+local[3]);
    a.join().unwrap() + b.join().unwrap()
})
Why the borrow is allowed

scope guarantees every thread is joined before it returns, so the borrows cannot outlive local. That removes the 'static requirement entirely. For short-lived parallelism inside one function, this is simpler and cheaper than Arc.

6.2medium Split a slice and sum in parallel

Task

Sum 1..=8 by splitting the slice in half and summing each half on its own thread.

Solution
Answer — verified 36
let mid = data.len()/2;
thread::scope(|s| {
    let (l, r) = data.split_at(mid);
    let a = s.spawn(move || l.iter().sum::<i32>());
    let b = s.spawn(move || r.iter().sum::<i32>());
    a.join().unwrap() + b.join().unwrap()
})
Disjoint borrows, again

split_at proves the halves do not overlap — the same reasoning as split_at_mut in the ownership guide. Here move moves the slice references, which are Copy, not the data.

6.3easy Four concurrent readers

Task

Four threads read a shared Vec through an RwLock simultaneously.

Solution
Answer — verified [3, 3, 3, 3]
let rw = Arc::new(RwLock::new(vec![1,2,3]));
// per thread:
rw.read().unwrap().len()      // concurrent
// to write:
rw.write().unwrap().push(4);   // exclusive
Not automatically faster

RwLock does more bookkeeping than Mutex. It only wins when reads heavily dominate and critical sections are non-trivial. A steady stream of readers can also starve a waiting writer. Measure before switching.

6.4hard Wait for a signal

Task

Block until another thread sets a flag, using Condvar — no spinning, no sleeping.

Solution
Answer — verified true
let pair = Arc::new((Mutex::new(false), Condvar::new()));

// waiter
let (l, c) = &*pair;
let mut g = l.lock().unwrap();
while !*g { g = c.wait(g).unwrap(); }   // while, NOT if

// signaller
*l.lock().unwrap() = true;
c.notify_one();
Why while

Spurious wakeups are real — wait may return with no notification at all. And another thread may consume the condition before you re-acquire the lock. Re-checking in a loop is the only correct form, in every language.

Notice wait consumes the guard and returns a new one. That is Rust encoding "the lock is released while waiting" directly in the type system.

SET 07

Putting it together

The patterns you will actually reach for.

7.1hard A worker pool

Task

Three workers share one job queue, square each number 1..=6, and collect results. Workers must exit cleanly when the work runs out.

Solution
Answer — verified [1, 4, 9, 16, 25, 36]
let (tx, rx) = mpsc::channel::<u32>();
let rx = Arc::new(Mutex::new(rx));      // share the consumer
let out = Arc::new(Mutex::new(Vec::new()));

// each worker:
thread::spawn(move || loop {
    let job = { rx.lock().unwrap().recv() };   // braces matter
    match job {
        Ok(n) => out.lock().unwrap().push(n*n),
        Err(_) => break,                     // channel closed
    }
});

for i in 1..=6 { tx.send(i).unwrap(); }
drop(tx);                                   // triggers shutdown
Shutdown by ownership

Dropping tx closes the channel, recv() returns Err, every worker breaks. No sentinel values, no shutdown flag, no timeout — the type system handles it.

7.2medium Parallel map over chunks

Task

Sum 1..=8 by giving each chunk of 2 to its own scoped thread, then summing the partial results.

Solution
Answer — verified 36
let sums: Vec<u64> = thread::scope(|s| {
    data.chunks(2)
        .map(|c| s.spawn(move || c.iter().sum::<u64>()))
        .collect::<Vec<_>>()          // spawn ALL first
        .into_iter()
        .map(|h| h.join().unwrap())
        .collect()
});
sums.iter().sum::<u64>()
The collect in the middle

Same trap as 1.2. Without it, iterator laziness spawns and joins each thread one at a time — perfectly correct, entirely sequential. In production, rayon's par_iter() does all of this for you.

7.3hard Write a deadlock, then fix it

Task

Two mutexes, two threads, opposite lock orders. Write it, confirm it hangs, then fix it two different ways.

Solution
Hangs forever
// thread 1
let _a = a.lock().unwrap();
let _b = b.lock().unwrap();
// thread 2
let _b = b.lock().unwrap();
let _a = a.lock().unwrap();   // circular wait
Fix 1 — global lock ordering (preferred)
// BOTH threads take A before B, always.
let _a = a.lock().unwrap();
let _b = b.lock().unwrap();
Fix 2 — try_lock, verified output
match b.try_lock() {
    Ok(_) => println!("got both"),
    Err(_) => println!("could NOT get B — backing off"),
}
// t1: could NOT get B (would deadlock with lock())
// t2: got both
Rust does not save you here

Deadlock is not a memory-safety violation, so the borrow checker has nothing to say about it. All four Coffman conditions remain available. Global lock ordering breaks circular wait and is the fix you should reach for; try_lock breaks no-preemption but needs a back-off strategy.

7.4medium Choose the primitive

Task

No code — decide. Name the tool for each:

a) parallelise a sum over a local Vec

b) 10,000 concurrent HTTP requests

c) a background logger receiving messages

d) config read by every thread, never written

e) a progress counter across workers

Solution
Answers
// a) thread::scope       — local data, short-lived threads
// b) async, not threads  — I/O-bound, far too many for OS threads
// c) a channel           — one consumer, many producers
// d) Arc<T>              — read-only, no lock needed at all

Read-only shared data needs Arc alone — no Mutex. Wrapping immutable config in a lock is a common reflex that costs performance and buys nothing.

FINAL

Capstone: a concurrent job scheduler

A download manager: a shared job queue, a worker pool, atomic statistics, and a results channel. Build it one part at a time.

Given
#[derive(Debug, Clone)]
struct Job { id: u32, url: String, size_kb: u32 }

#[derive(Debug)]
enum Outcome {
    Done   { id: u32, worker: usize, kb: u32 },
    Failed { id: u32, why: String },
}

struct Stats {
    completed: AtomicUsize,
    failed:    AtomicUsize,
    bytes_kb:  AtomicUsize,
}

// 12 jobs; every job whose id is divisible by 5 fails.
C.1medium Shared statistics

Task

Make Stats shareable across workers. Why atomics rather than Mutex<Stats>?

Solution
Answer
let stats = Arc::new(Stats {
    completed: AtomicUsize::new(0),
    failed:    AtomicUsize::new(0),
    bytes_kb:  AtomicUsize::new(0),
});
// no Mutex anywhere — each field updates independently
stats.completed.fetch_add(1, Ordering::Relaxed);
Why atomics win here

Each counter is independent — no invariant links them, so no thread ever needs a consistent snapshot of all three at once. Mutex<Stats> would serialise every update for no benefit. Relaxed is right because we only care about the final totals.

C.2hard The shared job queue

Task

Make one Receiver usable by four workers. Note the type you need and why.

Solution
Answer
let (job_tx, job_rx) = mpsc::channel::<Job>();
let job_rx = Arc::new(Mutex::new(job_rx));
Why the Mutex is required

mpsc is multi-producer, single-consumer — the Receiver cannot be cloned. To let several workers pull from it, they must share one receiver under a lock. (Crates like crossbeam-channel provide true MPMC channels and skip this.)

C.3hard The worker loop

Task

Write the worker: take a job, do the work, report the outcome, update stats. The lock must be held for as little as possible.

Solution
Answer
thread::spawn(move || loop {
    // Lock ONLY to take a job — guard drops at the ';'
    let job = { job_rx.lock().unwrap().recv() };
    let job = match job { Ok(j) => j, Err(_) => break };

    thread::sleep(Duration::from_millis(2));   // the "download"

    if job.id % 5 == 0 {
        stats.failed.fetch_add(1, Ordering::Relaxed);
        res_tx.send(Outcome::Failed { id: job.id, why: "timeout".into() }).unwrap();
    } else {
        stats.completed.fetch_add(1, Ordering::Relaxed);
        stats.bytes_kb.fetch_add(job.size_kb as usize, Ordering::Relaxed);
        res_tx.send(Outcome::Done { id: job.id, worker: wid, kb: job.size_kb }).unwrap();
    }
})
The whole point of the exercise

The sleep is outside the lock. Move it inside and your four workers become one — correct results, zero parallelism, no warning. That is exercise 3.5 in a realistic setting.

C.4hard Shutting down cleanly

Task

Two drop calls are needed for this program to terminate. Identify both and say what each one releases.

Which two, and why

Solution
Answer
drop(res_tx);   // main's results sender — else the collector loop
                // never ends, because main still holds a sender

for j in jobs { job_tx.send(j).unwrap(); }
drop(job_tx);   // closes the queue — workers' recv() returns Err,
                // so every worker breaks out of its loop
Two independent shutdown chains

drop(job_tx) stops the workers. Each worker then drops its own res_tx clone as it exits; once all of them plus main's copy are gone, the results loop ends. Miss either drop and the program hangs with no error at all.

C.5medium Collect the results

Task

Drain the results channel, separating successes from failures and tallying jobs per worker.

Solution
Answer — verified output
for outcome in res_rx {
    match outcome {
        Outcome::Done { id, worker, .. } => {
            done.push(id);
            *per_worker.entry(worker).or_insert(0) += 1;
        }
        Outcome::Failed { id, .. } => failed.push(id),
    }
}
Verified — identical across runs
1. completed   = 10
2. failed      = 2
3. total kb    = 6300
4. done ids    = [1, 2, 3, 4, 6, 7, 8, 9, 11, 12]
5. failed ids  = [5, 10]
6. all 12 accounted for = true
No lock needed here

main is the sole consumer, so done, failed, and per_worker are ordinary local variables. Collecting results on one thread avoids sharing entirely — the cheapest synchronisation is none.

C.6hard What is deterministic, and what is not?

Task

Run the finished program several times. Which outputs are identical every run, and which vary? Explain.

Stable

Varies

Solution
Verified across repeated runs
// STABLE — every run:
completed = 10, failed = 2, total kb = 6300
done ids  = [1,2,3,4,6,7,8,9,11,12]     // after sorting
all 12 accounted for = true

// VARIES between runs:
which worker handled which job
the order results arrive in the channel
The property you want

A correct concurrent program is deterministic in its aggregates and non-deterministic in its scheduling. The totals are guaranteed because atomics make each update indivisible; the assignment of work is the scheduler's business and must never be asserted on.

If a total ever varies between runs, you have a race — go back and find it.
