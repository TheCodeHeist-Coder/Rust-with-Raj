Threads:
the concepts first

Before any language's syntax, there is a body of ideas every interviewer expects you to have: what a thread actually is, why shared state breaks, what a race condition really means, and the four conditions that produce deadlock. This guide is language-agnostic. The Rust follows after.

PART 01

Process vs thread — the question you will be asked

This is the most common opening question on the topic, so it is worth being able to answer it precisely rather than vaguely.

A process is a running program together with its own private address space. A thread is a unit of execution inside a process. One process can hold many threads, and they all share the same memory.

   PROCESS A                          PROCESS B
 ┌────────────────────────────┐    ┌──────────────────┐
 │ CODE │ GLOBALS │ HEAP      │    │ CODE │ … │ HEAP  │
 │ ───────── shared ───────── │    │                  │
 │  ┌────────┐  ┌────────┐    │    │  ┌────────┐      │
 │  │Thread 1│  │Thread 2│    │    │  │Thread 1│      │
 │  │ stack  │  │ stack  │    │    │  │ stack  │      │
 │  │ regs   │  │ regs   │    │    │  │ regs   │      │
 │  │ PC     │  │ PC     │    │    │  │ PC     │      │
 │  └────────┘  └────────┘    │    │  └────────┘      │
 └────────────────────────────┘    └──────────────────┘
        isolated by the OS — separate address spaces

Threads share the heap and globals. Each has its own stack, registers, and program counter.

ProcessThread
Address spacePrivateShared with siblings
Creation costHigh (new page tables)Low (~stack + bookkeeping)
Context switchExpensive (TLB flush)Cheaper (same page tables)
CommunicationIPC: pipes, sockets, shared memoryJust read the same variable
Crash blast radiusOne process diesUsually the whole process dies
OwnsMemory, file handles, socketsStack, registers, PC, thread-local storage
Threads share memory by default. That is the whole reason they are fast, and the whole reason they are dangerous.

What each thread owns privately

Interviewers like this follow-up. Each thread has its own:

  • Stack — so local variables are private and function calls do not interfere
  • Registers and program counter — so each can be at a different instruction
  • Thread-local storage — opt-in per-thread globals

Everything else — the heap, globals, open files, sockets — is shared. When two threads touch the same heap object without coordination, you get the bugs the rest of this guide is about.

PART 02

Concurrency vs parallelism

These get used interchangeably in conversation and are not the same thing. Getting this right signals that you actually understand the field.

Concurrency is dealing with many things at once. Parallelism is doing many things at once.
CONCURRENT, not parallel (1 core, interleaved):

  core 0:  [A][B][A][B][A][B][A]      time ──►

PARALLEL (2 cores, simultaneous):

  core 0:  [AAAAAAAAAAAAAAAAAA]
  core 1:  [BBBBBBBBBBBBBBBBBB]      time ──►

BOTH (4 tasks, 2 cores):

  core 0:  [A][C][A][C][A][C]
  core 1:  [B][D][B][D][B][D]        time ──►

Concurrency is a structuring choice; parallelism is a hardware outcome.

Concurrency is about structure — your program is organised as independent tasks that may be in progress at the same time. Parallelism is about execution — those tasks genuinely run simultaneously on different cores.

A single-core machine can be concurrent but never parallel. A concurrent program is what allows parallelism when cores are available.

The interview answer

"Concurrency is about dealing with lots of things at once; parallelism is about doing lots of things at once." That is Rob Pike's formulation, and it is the one people expect. Follow it with the single-core example to show you understand why they are separable.

PART 03

Why threads at all — the two motivations

There are exactly two reasons to reach for threads, and they call for different designs.

1. CPU-bound work — you want more cores

Image processing, simulation, compilation. The work is genuinely computational, and splitting it across cores makes it finish sooner. Here you want roughly one thread per core; more threads than cores just adds context-switching overhead.

2. I/O-bound work — you want to stop waiting

Web servers, database clients, file processing. Threads spend most of their time blocked waiting on the network or disk. One thread waiting does not consume CPU, so you can profitably have far more threads than cores.

CPU-boundI/O-bound
BottleneckProcessor timeWaiting on external things
Ideal thread count≈ number of coresCan far exceed cores
Speedup from threadsReal, up to core countReal, often dramatic
Modern alternativeSIMD, GPUasync/await, event loops
Why this distinction matters in an interview

If asked "how many threads should a server use?", the answer depends entirely on which kind of work it does. Saying "one per core" for an I/O-heavy service is wrong, and saying "hundreds" for a CPU-bound batch job is also wrong. Ask which kind it is — that itself is a good sign.

PART 04

Amdahl's law — the ceiling on speedup

You cannot make a program infinitely fast by adding cores, and there is a formula for exactly how far you can get. If a fraction P of your program is parallelisable and you have N processors:

                    1
  Speedup  =  ─────────────────
               (1 - P)  +  P/N


  P = 0.95 (95% parallel), N → ∞  ⟹  max speedup = 20×
  P = 0.90                        ⟹  max speedup = 10×
  P = 0.50                        ⟹  max speedup =  2×

  The serial 5% is what caps you at 20×, no matter how many cores.

The serial fraction, not the core count, sets the ceiling.

The consequence is counter-intuitive and worth stating out loud: the part you cannot parallelise determines your limit. Halving the parallel part barely helps once N is large; shrinking the serial part is what matters.

What this looks like in practice

Here is a real measurement — four CPU-bound tasks, run sequentially and then on four threads:

Measured on a 12-core machine
cores            = 12
sequential (4x)  = 21.02ms
parallel   (4x)  = 10.77ms
speedup          = 1.95x
Why 1.95× and not 4×

Four threads on twelve cores, yet under 2×. Thread creation costs real time, the threads contend for memory bandwidth and shared cache, and the measurement itself has serial parts. Real speedup is always below the theoretical ceiling. Anyone claiming linear scaling has not measured. Being honest about this in an interview is a strong signal.

PART 05

The thread lifecycle

Every threading system has roughly the same state machine, and interviewers draw it often.

                    ┌─────────┐
       spawn ──────►│   NEW   │
                    └────┬────┘
                         │ scheduled
                         ▼
    ┌──────────┐    ┌─────────┐    dispatched   ┌──────────┐
    │  READY   │◄───┤ RUNNABLE├──────────────► │ RUNNING  │
    │(in queue)│    └─────────┘                 └────┬─────┘
    └────▲─────┘                                     │
         │ I/O done,                     blocks on:  │
         │ lock released,                 lock, I/O, │
         │ notified                       sleep      │
         │                                           ▼
         │                                    ┌──────────┐
         └────────────────────────────────────┤ BLOCKED  │
                                              └──────────┘
                                                   │
                    ┌────────────┐  returns/panics │
                    │ TERMINATED │◄────────────────┘
                    └────────────┘

A thread is only ever consuming CPU in RUNNING. Blocked threads are free.

StateMeaningUsing CPU?
NewCreated, not yet scheduledNo
Runnable / ReadyAble to run, waiting for a coreNo
RunningExecuting on a core right nowYes
Blocked / WaitingWaiting on I/O, a lock, or a signalNo
TerminatedFinished or crashedNo

This is why I/O-bound programs can run hundreds of threads: a blocked thread costs memory for its stack but no CPU at all.

Context switching

When the scheduler moves a core from one thread to another it must save the first thread's registers and program counter, then load the second's. That costs on the order of a microsecond, plus a less visible cost: the new thread's data is not in cache, so it runs slowly at first.

Thrashing

More threads is not more throughput. Past a point, the machine spends its time switching rather than working. This is why thread pools exist — a fixed set of threads pulling from a queue, instead of one thread per task.

PART 06

User threads, kernel threads, and the M:N question

A question that separates people who have read about threads from people who have only used them.

ModelHowTrade-off
1:1 (kernel)Each language thread is one OS threadTrue parallelism; creation is expensive. Rust, C++, Java.
N:1 (green)Many language threads on one OS threadVery cheap; one blocking call stalls everyone; no parallelism.
M:N (hybrid)M language threads over N OS threadsCheap and parallel; complex runtime. Go's goroutines.

Rust made a deliberate choice here: 1:1. Early Rust had green threads and removed them before 1.0, because an M:N runtime imposes overhead on every program — including ones embedding Rust in C, or running without an OS. Rust's async gives you the cheap-task model as a library instead, so you only pay when you use it.

A good thing to say

"Rust uses 1:1 threads so thread::spawn is a real OS thread, and gets M:N-style cheap concurrency through async instead. Go bakes M:N into its runtime — that is why goroutines are cheap but you cannot easily embed Go in a C program."

PART 07

Race conditions — the core problem

A race condition is when the result depends on the unpredictable timing of two or more threads.

The classic case is the lost update. counter += 1 looks like one action. It is three:

  counter += 1   compiles to roughly:

     1.  LOAD   counter → register     (read)
     2.  ADD    register, 1            (modify)
     3.  STORE  register → counter     (write)

  Two threads interleaving, counter starts at 0:

   Thread A            Thread B           counter
   ─────────           ─────────          ───────
   LOAD  → 0                                 0
                       LOAD  → 0             0
   ADD   → 1                                 0
                       ADD   → 1             0
   STORE → 1                                 1
                       STORE → 1             1   ← should be 2!

  One increment vanished. This is a LOST UPDATE.

Read-modify-write is not atomic. Interleaving destroys one of the updates.

This is not theoretical — here it is measured

Four threads, each incrementing a shared counter 100,000 times with a separate load and store. The correct answer is 400,000:

Real measured output
load+store (racy pair): 136210  (expected 400000)
fetch_add (atomic RMW): 400000  (expected 400000)

Roughly two-thirds of the increments disappeared. Not a rare glitch under load — the normal outcome. And note the number is not reproducible: run it again and you get a different one, which is exactly what makes these bugs so hard to find.

Why race bugs are so nasty

They are non-deterministic. They may appear once in ten thousand runs, vanish under a debugger (which changes timing), and only show up in production under load. This is why the whole apparatus of locks and atomics exists — you cannot test your way out of a race, you have to make it structurally impossible.

Race condition vs data race

A distinction interviewers like, and most candidates blur:

Data raceRace condition
DefinitionTwo threads access the same memory concurrently, ≥1 writes, no synchronisationCorrectness depends on timing
ScopeA specific memory-level bugA general logic-level bug
ExampleUnsynchronised counter += 1Check-then-act: "is the file there? then open it"
Rust prevents?Yes — in safe code, at compile timeNo — it is a logic error

All data races are race conditions; not all race conditions are data races. Rust's guarantee is precisely the first row — which is a strong guarantee, but it does not make your concurrent logic correct.

PART 08

Critical sections and mutual exclusion

A critical section is a region of code that must not be executed by more than one thread at a time. The fix for the lost update is to make the read-modify-write one indivisible unit.

  Thread A ──►┌───────────────────────┐──►
              │ ACQUIRE LOCK          │
              │   read  counter       │  critical section:
              │   modify              │  only one thread
              │   write counter       │  in here at a time
              │ RELEASE LOCK          │
              └───────────────────────┘
                        ▲
  Thread B ─────────────┘ blocked here until A releases

Mutual exclusion serialises the critical section, and only the critical section.

Any correct mutual-exclusion mechanism must provide three properties — a classic exam question:

PropertyMeans
Mutual exclusionAt most one thread in the critical section
ProgressIf nobody is inside, someone waiting gets in (no needless stalling)
Bounded waitingA waiting thread eventually gets in (no starvation)
Keep critical sections small

Everything inside the lock is serialised — it is your Amdahl's-law serial fraction. Never do I/O, sleep, or expensive computation while holding a lock. Acquire, touch the shared data, release.

PART 09

The synchronisation primitives

Six tools. Know what each is for and you can answer almost any design question on this topic.

1. Mutex (mutual exclusion lock)

One holder at a time. lock() blocks until free; unlock() releases. The default choice for protecting shared data.

2. Semaphore

A counter with wait (decrement, block at zero) and signal (increment). Permits N concurrent holders rather than one — use it to cap resource usage, such as "at most 10 simultaneous connections."

  MUTEX:      one key, one holder
              ┌───┐
     ────────►│ 1 │────────►   binary: locked / unlocked
              └───┘

  SEMAPHORE:  N permits
              ┌───┐
     ────────►│ 3 │────────►   three threads may pass;
              └───┘            the fourth blocks

  A mutex is (almost) a semaphore initialised to 1 — but a mutex
  also has an OWNER, so only the locker may unlock it.

A binary semaphore and a mutex differ in ownership, which matters for correctness.

3. Condition variable

Lets a thread wait for a condition rather than spinning. Always paired with a mutex: wait() atomically releases the lock and sleeps; notify() wakes a waiter.

Always wait in a loop

while !condition { cv.wait(); } — never if. Because of spurious wakeups (a thread can wake without a notification) and because another thread may have consumed the condition before you re-acquire the lock. This is a favourite interview detail.

4. Read-write lock

Many concurrent readers, or one exclusive writer. Worth it when reads greatly outnumber writes; otherwise the extra bookkeeping costs more than a plain mutex.

5. Atomic operations

Single indivisible instructions provided by the CPU — fetch_add, compare_and_swap. No OS involvement, no blocking. Only good for single values, but far faster than a lock.

6. Barrier

A rendezvous point: every thread waits until all N arrive, then all proceed. Used in phase-based algorithms — simulation steps, parallel matrix passes.

PrimitiveUse whenCost
MutexProtecting a data structureBlocking, syscall on contention
SemaphoreLimiting to N concurrent usersBlocking
CondvarWaiting for a state changeBlocking, needs a mutex
RwLockRead-heavy shared dataBlocking, more overhead than mutex
AtomicOne counter or flagNon-blocking, very fast
BarrierPhase synchronisationBlocking
PART 10

Deadlock — the four conditions

Guaranteed interview material. Deadlock is when threads wait on each other in a cycle, so none can proceed. It requires all four of Coffman's conditions simultaneously:

1. Mutual exclusion  ·  2. Hold and wait  ·  3. No preemption  ·  4. Circular wait
ConditionMeaningBreak it by
Mutual exclusionResources cannot be sharedUsing lock-free structures
Hold and waitHolding one, waiting for anotherAcquiring all locks at once, or none
No preemptionCannot forcibly take a lock awayTimeouts — try_lock
Circular waitA waits on B, B waits on AGlobal lock ordering ← the usual fix
 
       Thread 1                     Thread 2
       ────────                     ────────
    lock(A)  ✓                   lock(B)  ✓
       │                             │
    lock(B)  ✗ blocked           lock(A)  ✗ blocked
       │                             │
       └──────────┐     ┌────────────┘
                  ▼     ▼
              ┌─────────────┐
              │  A held by 1│◄──── 2 wants A
              │  B held by 2│◄──── 1 wants B
              └─────────────┘
                CIRCULAR WAIT — neither can ever proceed

The classic two-lock deadlock. Both threads hold what the other needs.

Demonstrated with a real run

Two threads taking two locks in opposite orders. Using try_lock instead of lock so the program reports the situation rather than hanging forever:

Real measured output
t1: could NOT get B (would deadlock with lock())
t2: got both

Thread 1 held A and could not get B. With a blocking lock() both threads would have hung permanently — no error, no crash, just a program that stops responding.

The fix worth memorising

Establish a global lock ordering. If every thread always takes A before B, a cycle is impossible. In practice: order locks by address, by ID, or by a documented convention — and write the convention down.

Related failures that are not deadlock

FailureWhat happens
LivelockThreads keep changing state in response to each other but make no progress — two people stepping aside in a corridor, forever.
StarvationA thread is runnable but never scheduled — often a low-priority thread starved by high-priority ones.
Priority inversionA low-priority thread holds a lock a high-priority thread needs, so the high-priority one waits on the low one. Famously nearly ended the Mars Pathfinder mission.
ConvoyingThreads bunch up behind one slow lock holder, destroying throughput.
PART 11

The classic problems

These are the named problems that appear on exams and in interviews. Each isolates one difficulty.

Producer–consumer (bounded buffer)

Producers add items to a fixed-size queue; consumers remove them. Producers must block when full, consumers when empty.

   Producers                BUFFER (size 4)              Consumers
   ─────────         ┌────┬────┬────┬────┐              ─────────
     P1 ──┐          │ i1 │ i2 │    │    │          ┌──► C1
     P2 ──┼─── put ─►└────┴────┴────┴────┘── take ──┤
     P3 ──┘            ▲              ▲              └──► C2
                       │              │
              block if FULL    block if EMPTY

   Needs: a mutex (protect the queue) + two condvars
          (not-full, not-empty), or a semaphore for each.

The foundational pattern for pipelines, work queues, and message passing.

This is the single most important pattern in practice — thread pools, logging systems, and job queues are all producer–consumer. In Rust it is largely solved for you by channels, which is why part 12 of the Rust guide leans on them.

Readers–writers

Many readers may share, but a writer needs exclusivity. The interesting part is the policy: reader-preference starves writers, writer-preference starves readers, so real implementations aim for fairness.

Dining philosophers

Five philosophers, five forks, each needs the two adjacent forks to eat. If all pick up their left fork simultaneously, everyone holds one and waits forever — a pure demonstration of circular wait.

            P0
        f0      f1
      P4          P1        Each philosopher needs
        f4      f2          BOTH adjacent forks.
            P3  f3  P2
                          All grab left first → deadlock.

   FIXES:
   • Order the forks: everyone takes the lower-numbered one first.
     (One philosopher becomes left-handed — breaks the cycle.)
   • Allow at most 4 to sit at once (semaphore) — breaks hold-and-wait.
   • Pick up both atomically, or neither.

The canonical illustration of breaking circular wait.

Sleeping barber

A barber sleeps when there are no customers; customers wait if chairs are free and leave if not. Models a server with a bounded request queue — the pattern behind connection backlogs.

PART 12

Atomics, and why volatile is not the answer

An atomic operation completes indivisibly — no other thread can observe it half-done. Modern CPUs provide these as single instructions.

OperationDoes
load / storeRead or write indivisibly
fetch_addRead, add, write — as one unit
compare_and_swap (CAS)"If the value is still X, set it to Y" — the foundation of lock-free code
swapExchange and return the old value

Part 7's measurement showed exactly why the distinction matters: a separate load and store lost two-thirds of the increments, while fetch_add — the same logical operation, but atomic — gave the exact answer.

volatile does not make things thread-safe

A very common misconception, and a good interview trap. In C/C++, volatile tells the compiler not to cache a value in a register. It says nothing about atomicity or about CPU memory ordering, so volatile int x; x++; is still a data race. Use real atomics. (Java's volatile is a different and stronger thing — it does impose ordering.)

Memory ordering, briefly

Compilers and CPUs reorder instructions for speed. Single-threaded code cannot tell; multithreaded code very much can. Memory orderings let you say how much reordering is acceptable:

OrderingGuaranteeUse for
RelaxedAtomic, but no ordering with other operationsCounters where only the total matters
Acquire / ReleasePairs up to create a happens-before edgeLock implementations, publishing data
SeqCstOne global order all threads agree onThe safe default when unsure
Practical advice

Use SeqCst unless you have measured and understand exactly why you need weaker ordering. Relaxed on a pure counter is the one common exception — you only care that the final total is right, not when each increment became visible.

PART 13

Thread pools and work queues

Creating a thread per task does not scale: creation costs milliseconds and thousands of threads thrash. A thread pool creates N workers once and feeds them tasks from a shared queue.

   submit ──►┌──────────────────────────────┐
             │  TASK QUEUE  [t1][t2][t3][t4]│
             └──────┬──────┬──────┬─────────┘
                    │      │      │
              ┌─────▼─┐ ┌──▼───┐ ┌▼─────┐
              │Worker1│ │Worker2│ │Worker3│   fixed set of threads,
              └───────┘ └───────┘ └───────┘   created once, reused

   Each worker loops: take a task, run it, repeat.
   This IS producer-consumer, with tasks as the items.

Bounded threads, unbounded tasks. The standard shape for servers.

How many workers?

WorkloadRule of thumb
CPU-boundN = number of cores
I/O-boundN = cores × (1 + wait time / compute time)
MixedMeasure. Separate pools per workload type.

For I/O-heavy work the multiplier can be large — if a task waits 90% of the time, you want roughly ten threads per core.

Work stealing

An advanced refinement worth knowing by name: each worker has its own queue, and idle workers steal from busy ones' tails. This avoids contention on a single shared queue. It is how Rayon, Go's scheduler, and Java's ForkJoinPool all work.

PART 14

Shared memory vs message passing

Two philosophies for getting threads to cooperate. Interviewers ask you to compare them.

Shared memoryMessage passing
ModelThreads read/write the same data under locksThreads own their data, send copies
PrimitiveMutex, RwLock, atomicsChannels, queues
StrengthNo copying; efficient for large dataNo locks to get wrong; easy to reason about
WeaknessDeadlock, races, subtle bugsCopying costs; can hide backpressure
Slogan—"Do not communicate by sharing memory; share memory by communicating."

Neither is universally better. Message passing is easier to get right and should be your default; shared memory wins when the data is large or the access pattern is genuinely random.

Rust supports both, safely

Most languages let you use both and hope. Rust makes both safe: channels move ownership so the sender provably cannot touch the data afterwards, and Mutex<T> puts the data inside the lock so you cannot access it without locking. That second idea is genuinely unusual and worth mentioning in an interview.

PART 15

Threads vs async — the modern question

Increasingly asked, because every modern language has both.

  THREADS (preemptive):
    The OS interrupts a thread whenever it likes.
    Each thread needs a full stack (~8 MB virtual, ~8 KB real).
    10,000 threads = heavy.

  ASYNC (cooperative):
    A task yields ONLY at an await point.
    A task is a small state machine — hundreds of bytes.
    10,000 tasks = fine.

    ┌──────────────────────────────────────────┐
    │  async runtime (a few OS threads)        │
    │   ┌────┐┌────┐┌────┐┌────┐┌────┐         │
    │   │task││task││task││task││task│  …10k   │
    │   └────┘└────┘└────┘└────┘└────┘         │
    └──────────────────────────────────────────┘

Async multiplexes many tasks onto few threads. It does not add cores.

Use threads whenUse async when
Work is CPU-boundWork is I/O-bound
You need real parallelismYou need many concurrent waits
Tasks are few and long-livedTasks are many and short
Code is simpler without a runtimeYou are writing a network service
The trap

Async does not make CPU-bound work faster — there are no extra cores involved. Worse, a long computation inside an async task blocks the whole executor thread and stalls every other task on it. CPU-bound work belongs on threads (or a dedicated blocking pool), even inside an async program.

Questions you should expect

  1. Process vs thread? → Part 01's table. Lead with the address space.
  2. Concurrency vs parallelism? → Pike's line, then the single-core example.
  3. What is a race condition? Give an example. → counter += 1 as three steps, with the interleaving diagram.
  4. How do you prevent one? → Mutex, atomics, or eliminate the sharing entirely.
  5. What are the four conditions for deadlock? → Mutual exclusion, hold-and-wait, no preemption, circular wait.
  6. How do you avoid deadlock? → Global lock ordering is the main answer; then timeouts, and taking all locks at once.
  7. Mutex vs semaphore? → Ownership, and binary vs counting.
  8. Why while and not if around cv.wait()? → Spurious wakeups and lost conditions.
  9. How many threads for a server? → Ask CPU-bound or I/O-bound first.
  10. Threads or async? → I/O-bound → async; CPU-bound → threads.
  11. Is volatile enough? → No. It prevents caching in a register, not races.
  12. Why is 8 threads not 8× faster? → Amdahl's law, plus contention and thread overhead. Cite a real number: 4 threads gave 1.95×.
