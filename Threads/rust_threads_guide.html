Rust · Learning notes

Threads:
fearless, and why

Every concept in the fundamentals guide — races, deadlock, shared state — is a runtime hazard in C and Java. In Rust most of them are compile errors, and the mechanism is not new: it is ownership and borrowing, applied across threads. This is where that investment pays.

18 parts Before: cs_threading_fundamentals.html Practice: rust_threads_practice.html Verified on rustc 1.96
PART 01

Spawning and joining

thread::spawn takes a closure and runs it on a new OS thread. It returns a JoinHandle, and .join() waits for the thread to finish and gives you its return value.

Verified output
use std::thread;

let h = thread::spawn(|| {
    let mut s = 0u64;
    for i in 1..=1000 { s += i; }
    s                            // the thread's return value
});

println!("{:?}", h.join().unwrap());   // → 500500

Two things are worth noticing immediately. join() returns a Result, not the value directly — because the thread might have panicked (part 16). And a thread's return value comes back through the handle, which is how Rust avoids needing a shared "result" variable.

1:1 threads

As covered in the fundamentals guide, thread::spawn creates a genuine OS thread — not a green thread or a task. It costs real memory (a full stack) and real time to create. For thousands of concurrent waits you want async, not thousands of spawns.

Detached threads

If you never call join, the thread is detached. When main returns, the process exits and any still-running threads are killed abruptly:

Output is unpredictable — the thread may never finish
thread::spawn(|| {
    for i in 1..10 {
        println!("spawned: {i}");
        thread::sleep(Duration::from_millis(1));
    }
});
// main ends here — the spawned thread is cut off mid-loop
If you care that a thread finished, you must join it.
PART 02

move — the first error you will hit

Try to use a local variable inside a spawned closure and the compiler stops you:

Does not compile
let data = vec![1, 2, 3];
thread::spawn(|| { println!("{:?}", data); });
error[E0373]: closure may outlive the current function, but it borrows `data`, which is owned by the current function
 --> te1.rs:4:19
  |
4 |     thread::spawn(|| { println!("{:?}", data); });
  |                   ^^                    ---- `data` is borrowed here
  |                   |
  |                   may outlive borrowed value `data`
  |
note: function requires argument type to outlive `'static`
help: to force the closure to take ownership of `data` (and any other referenced variables), use the `move` keyword
  |
4 |     thread::spawn(move || { println!("{:?}", data); });
  |                   ++++

Read the reasoning, because it is the whole design in one sentence: the closure may outlive the current function. Nothing forces the spawned thread to finish before main returns, so a borrow of a local would become a dangling reference — exactly the E0106 problem from the ownership guide, now across threads.

The fix — verified output 6
let data = vec![1, 2, 3];
let h = thread::spawn(move || data.iter().sum::<i32>());
println!("{}", h.join().unwrap());

move forces the closure to take ownership of everything it captures. Now the vector belongs to the thread, lives as long as the thread does, and main can no longer touch it — try, and you get the familiar E0382.

The 'static bound

spawn requires F: Send + 'static. 'static here does not mean "lives forever" — it means "contains no borrows of anything that could die first." Owned data satisfies it. This is why move is the answer.

PART 03

The trap: move copies, it does not share

Here is a program that compiles, emits only a warning, and is completely wrong. Predict the output before reading on:

Compiles. Prints 0.
let mut counter = 0;
let mut hs = vec![];
for _ in 0..5 {
    hs.push(thread::spawn(move || { counter += 1; }));
}
for h in hs { h.join().unwrap(); }
println!("{counter}");       // → 0, not 5
warning: value captured by `counter` is never read
 --> te3.rs:6:41
  |
6 |         hs.push(thread::spawn(move || { counter += 1; }));
  |                                         ^^^^^^^
  |
  = help: did you mean to capture by reference instead?

i32 is Copy. So move gives each of the five threads its own private copy of counter, each increments its own to 1, and all five are discarded. The original never changes.

Why this matters

This is the one place Rust will let a threading mistake through, and it is worth understanding exactly why: there is no unsafety here — no race, no shared memory, nothing to protect. It is a pure logic error. Rust prevents data races, not wrong programs. The compiler still hints: "did you mean to capture by reference instead?"

To actually share, you need shared ownership plus synchronisation — which is parts 4 and 5.

PART 04

Send and Sync — the two marker traits

These are how Rust encodes thread safety in the type system. Two traits, no methods, both usually derived automatically.

TraitMeansTest
SendSafe to move to another threadCan I transfer ownership across a thread boundary?
SyncSafe to share by reference between threadsIs &T Send?

Almost every type is both, automatically — if all your fields are Send, your struct is Send. The interesting cases are the exceptions:

TypeSendSyncWhy
i32, String, Vec<T>✓✓Plain data
Rc<T>✗✗Non-atomic refcount — two threads could corrupt it
Arc<T>✓✓Atomic refcount
RefCell<T>✓✗Non-atomic borrow flag; movable but not shareable
Mutex<T>✓✓That is its entire job
Raw pointers✗✗No guarantees at all

Seeing the error

Try to send an Rc to another thread:

Does not compile
let d = Rc::new(5);
let d2 = Rc::clone(&d);
thread::spawn(move || { println!("{}", d2); });
error[E0277]: `Rc<i32>` cannot be sent between threads safely
   --> te2.rs:6:19
    |
  6 |     thread::spawn(move || { println!("{}", d2); }).join().unwrap();
    |     ------------- -------^^^^^^^^^^^^^^^^^^^^^^^^
    |     |             |
    |     |             `Rc<i32>` cannot be sent between threads safely
    |
    = help: within `{closure@te2.rs:6:19: 6:26}`, the trait `Send` is not implemented for `Rc<i32>`
note: required by a bound in `spawn`
    |
125 | pub fn spawn<F, T>(f: F) -> JoinHandle<T>
    |        ----- required by a bound in this function
...
128 |     F: Send + 'static,
    |        ^^^^ required by this bound in `spawn`

The error points straight at spawn's signature: F: Send + 'static. Rc's reference count is a plain integer, incremented non-atomically — two threads cloning at once could lose an increment and free memory that is still in use. So Rc is deliberately not Send, and the compiler enforces it.

The Sync half

RefCell shows the other trait. It is Send — you may move one to another thread — but it is not Sync, so it cannot be shared. Wrapping it in an Arc tries to share it, and fails:

Does not compile
let d = Arc::new(RefCell::new(5));
let d2 = Arc::clone(&d);
thread::spawn(move || { *d2.borrow_mut() += 1; });
error[E0277]: `RefCell<i32>` cannot be shared between threads safely
   --> te5.rs:7:19
    |
  7 |     thread::spawn(move || { *d2.borrow_mut() += 1; }).join().unwrap();
    |     ------------- ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ `RefCell<i32>` cannot be shared between threads safely
    |
    = help: the trait `Sync` is not implemented for `RefCell<i32>`
    = note: if you want to do aliasing and mutation between multiple threads, use `std::sync::RwLock` instead
    = note: required for `Arc<RefCell<i32>>` to implement `Send`

Two details worth reading closely. The compiler names the replacement outright — "use std::sync::RwLock instead". And the last line shows the traits composing: Arc<T> is only Send when T is Sync, which is exactly why Arc cannot be used to smuggle a non-Sync type across a thread boundary.

This is the whole trick

"Fearless concurrency" is not a runtime checker. It is two marker traits and the ownership rules you already know. Thread safety became a type property, so misuse is a type error — caught at compile time, with zero runtime cost.

PART 05

Arc — shared ownership across threads

Arc<T> is an Atomically Reference Counted pointer. Multiple owners of one value; the value is dropped when the last Arc goes away.

   Thread 1        Thread 2        Thread 3
      │               │               │
   ┌──▼───┐        ┌──▼───┐        ┌──▼───┐
   │ Arc  │        │ Arc  │        │ Arc  │      each is a clone
   └──┬───┘        └──┬───┘        └──┬───┘
      └───────────────┼───────────────┘
                      ▼
            ┌───────────────────┐
            │  count: 3         │  ← atomic, safe to update
            │  data:  T         │     from any thread
            └───────────────────┘
        dropped when count reaches 0

Arc::clone copies the pointer and bumps the count — it does not copy the data.

Arc::clone(&x) is cheap: one atomic increment. It is deliberately written as Arc::clone(&x) rather than x.clone() by convention, so readers can see at a glance that no deep copy is happening.

Rc vs Arc

Same API, different refcount. Rc uses a plain integer — faster, single-threaded only. Arc uses an atomic — slightly slower, thread-safe. Use Rc until the compiler tells you otherwise; it will.

But Arc alone only gives you shared reading. Arc<T> hands out &T, never &mut T — because that would be multiple mutable aliases, exactly what the borrow rules forbid. To mutate, you need part 6.

PART 06

Mutex — and the idea that makes it safe

Rust's Mutex has a design most languages do not: the data lives inside the lock.

  OTHER LANGUAGES:              RUST:

    Mutex  m;                     Mutex<Vec<i32>>
    Vec    data;                        │
      ↑        ↑                        └── the data is INSIDE
      │        │
   two separate things.          You cannot reach the data
   Nothing forces you to         without locking, because
   lock before touching          lock() is the only way to
   the data. Forgetting          get a reference to it.
   is a silent race.
                                 Forgetting is impossible.

In Rust, the lock owns the data. This is the structural difference.

lock() returns a Result<MutexGuard<T>>. The guard derefs to &mut T, and unlocks automatically when it is dropped — the Drop trait from the ownership guide, doing real work. There is no unlock() to forget.

The canonical counter — verified output 8000
use std::sync::{Arc, Mutex};
use std::thread;

let c = Arc::new(Mutex::new(0));
let mut hs = vec![];

for _ in 0..8 {
    let c = Arc::clone(&c);          // each thread gets its own handle
    hs.push(thread::spawn(move || {
        for _ in 0..1000 {
            *c.lock().unwrap() += 1;    // lock, mutate, auto-unlock
        }
    }));
}
for h in hs { h.join().unwrap(); }
println!("{}", *c.lock().unwrap());   // → 8000, exactly, every time

Compare that with the fundamentals guide's measurement, where an unsynchronised version lost two-thirds of its increments. Here it is 8000 every run, and the compiler would not have let you write the broken version.

Reading the type

Arc<Mutex<T>> = shared ownership (Arc) of exclusive access (Mutex) to data (T).

The nesting order matters and follows from what each piece does. Arc must be outermost so every thread can hold a handle; Mutex is inside because the thing being protected is the data. Mutex<Arc<T>> would be a lock protecting a pointer — almost never what you want.

Keep the guard's life short

The lock is held until the guard drops. let g = m.lock().unwrap(); at the top of a long function holds it for the whole function. Prefer *m.lock().unwrap() += 1;, where the temporary guard drops at the end of the statement, or wrap the critical section in a { } block.

PART 07

Deadlock is still possible

An important honesty point. Rust prevents data races — it does not prevent deadlock. All four Coffman conditions are still available to you.

Two locks, opposite orders — verified with try_lock
// Thread 1: lock A, then B
let _g = a1.lock().unwrap();
let _h = b1.lock().unwrap();     // waits for thread 2

// Thread 2: lock B, then A
let _g = b2.lock().unwrap();
let _h = a2.lock().unwrap();     // waits for thread 1  → DEADLOCK
Real output using try_lock so it reports instead of hanging
t1: could NOT get B (would deadlock with lock())
t2: got both

With blocking lock() calls that program hangs forever — no panic, no error, just silence. The fixes are the ones from the fundamentals guide: global lock ordering first, try_lock with a timeout second.

The self-deadlock

Rust's Mutex is not reentrant. Locking it twice from the same thread deadlocks that thread against itself. In particular, calling a method that locks while already holding the lock is a real and easy mistake.

Poisoning

This is why lock() returns a Result. If a thread panics while holding a lock, the mutex is poisoned — the data may be in a half-updated state, so every later lock() returns Err:

Verified output
// A thread panics while holding the lock:
poisoned = true

// You can still recover the value if you decide it is sound:
let val = match m.lock() {
    Ok(g) => *g,
    Err(p) => *p.into_inner(),   // deliberate override
};
// recovered value = 0

Most code writes .lock().unwrap(), which propagates the panic — usually the right call, since a poisoned lock means something already went wrong.

PART 08

RwLock — many readers or one writer

When reads vastly outnumber writes, a Mutex serialises readers unnecessarily. RwLock lets them run concurrently:

Four threads reading at once — verified [3, 3, 3, 3]
use std::sync::RwLock;

let rw = Arc::new(RwLock::new(vec![1, 2, 3]));

let rw = Arc::clone(&rw);
thread::spawn(move || rw.read().unwrap().len());   // shared read

// and for writing:
rw.write().unwrap().push(4);                       // exclusive
MutexRwLock
Concurrent readersNoYes
OverheadLowerHigher
Best whenWrites are commonReads dominate heavily
Guard typeslock()read() / write()
Not automatically faster

RwLock does more bookkeeping than Mutex. If writes are frequent, or critical sections are tiny, a plain Mutex often wins. Measure before switching — and be aware that a steady stream of readers can starve a waiting writer.

PART 09

Atomics — locks for a single value

For one counter or flag, a mutex is overkill. Atomic types do the whole read-modify-write in a single CPU instruction:

Verified output 8000
use std::sync::atomic::{AtomicUsize, Ordering};

let a = Arc::new(AtomicUsize::new(0));

// in each of 8 threads, 1000 times:
a.fetch_add(1, Ordering::Relaxed);

println!("{}", a.load(Ordering::SeqCst));   // → 8000

Note there is no Mutex and no &mut — fetch_add takes &self. Atomics provide interior mutability: they can be modified through a shared reference, safely, because the hardware guarantees indivisibility.

Why the operation must be atomic, not just the accesses

This is the measurement from the fundamentals guide, and it is worth repeating here in Rust terms. Both versions below are perfectly safe Rust with no data race — yet only one is correct:

Real measured output, 4 threads × 100,000 increments
// let v = a.load(Relaxed); a.store(v + 1, Relaxed);
load+store (racy pair): 136210  (expected 400000)

// a.fetch_add(1, Relaxed);
fetch_add (atomic RMW): 400000  (expected 400000)
The lesson

Two atomic operations are not one atomic operation. A load followed by a store leaves a window where another thread can intervene — the classic lost update, losing two-thirds of the work here. Use a single read-modify-write (fetch_add, compare_exchange) and the window disappears. This is a logic error Rust cannot catch for you.

Which ordering?

OrderingUse for
RelaxedPure counters — you only care about the final total
Acquire/ReleasePublishing data: release on write, acquire on read
SeqCstThe default when you are not certain

Start with SeqCst. Drop to Relaxed only for independent counters, and only when you can articulate why the ordering does not matter.

PART 10

Channels — message passing

The other philosophy from the fundamentals guide: instead of sharing data under a lock, send it. mpsc stands for multi-producer, single-consumer.

Verified output [0, 10, 20] after sorting
use std::sync::mpsc;

let (tx, rx) = mpsc::channel();

for i in 0..3 {
    let tx = tx.clone();          // one sender per producer
    thread::spawn(move || { tx.send(i * 10).unwrap(); });
}
drop(tx);                        // drop the original — see below

let got: Vec<i32> = rx.iter().collect();
The drop(tx) that everyone forgets

rx.iter() ends only when every sender has been dropped. If you keep the original tx alive in main, the receiver waits forever and your program hangs. Either drop(tx) explicitly, or make sure the last clone goes out of scope.

Ownership makes this safe

send takes the value by value. Once sent, you provably cannot touch it.

This is the ownership system doing concurrency work. In a language with shared references, sending a pointer and then modifying the original is a classic race. In Rust, send(data) moves data, and any later use is E0382. The channel is safe not because of runtime checks but because of the move.

Bounded channels and backpressure

Verified output [1, 2, 3, 4]
let (tx, rx) = mpsc::sync_channel::<u32>(2);   // capacity 2
// send() now BLOCKS when the buffer is full

channel() is unbounded — a fast producer can exhaust memory. sync_channel(n) blocks the producer when full, which is backpressure: the queue length becomes self-limiting. For anything long-running, prefer bounded.

MethodBehaviour
recv()Blocks until a message or all senders drop
try_recv()Returns immediately, Err if empty
recv_timeout(d)Blocks up to a duration
rx.iter()Blocking iterator; ends when all senders drop
PART 11

Scoped threads — borrowing across threads

Everything so far required move and owned data, because a thread might outlive the function. thread::scope removes that requirement by guaranteeing the threads finish before the scope ends.

Verified output 60 — note: no Arc, no move, no clone
let local = vec![10, 20, 30];

let total: i32 = thread::scope(|s| {
    let a = s.spawn(|| local[0] + local[1]);   // borrows!
    let b = s.spawn(|| local[2]);              // borrows!
    a.join().unwrap() + b.join().unwrap()
});
// local is still usable here

Both closures borrow local immutably, which is fine — many readers, no writer. scope joins any unjoined threads before returning, so the borrows provably cannot outlive the data. Stabilised in Rust 1.63; before that this needed an external crate.

Reach for this first

If your threads are short-lived and confined to one function — the common case for parallelising a computation — scoped threads are simpler and cheaper than Arc. Use Arc<Mutex<T>> when threads genuinely outlive the spawning scope.

UseWhen
thread::scopeThreads finish inside this function; you want to borrow locals
Arc<T>Threads outlive the scope; read-only sharing
Arc<Mutex<T>>Threads outlive the scope; shared mutation
ChannelsHanding work off; no shared state at all
PART 12

Condvar — waiting for a condition

Spinning on a flag burns CPU. A condition variable lets a thread sleep until something changes. It is always paired with a Mutex:

Verified output signalled = true
use std::sync::Condvar;

let pair = Arc::new((Mutex::new(false), Condvar::new()));

// Waiter:
let (lock, cv) = &*pair;
let mut ready = lock.lock().unwrap();
while !*ready {                       // while, NOT if
    ready = cv.wait(ready).unwrap();
}

// Signaller, on another thread:
*lock.lock().unwrap() = true;
cv.notify_one();
while, never if

The exact point flagged in the fundamentals guide, now in Rust. wait can return spuriously without any notification, and another thread may consume the condition before you re-acquire the lock. Re-checking in a loop is the only correct form.

Note how wait works with ownership: it consumes the guard and returns a new one. That is Rust encoding "the lock is released while waiting, and re-acquired on wake" directly in the type signature — you cannot accidentally use the guard while it is released.

Bounded buffer built on Condvar — verified [1, 2, 3, 4]
let (m, cv) = &*q;
let mut g = m.lock().unwrap();
while g.is_empty() { g = cv.wait(g).unwrap(); }
while let Some(v) = g.pop_front() { got.push(v); }

That is the producer–consumer problem from the fundamentals guide, implemented. In practice you would use a channel — but knowing how to build one from a mutex and a condvar is standard interview material.

PART 13

Building a worker pool

The pattern behind every server. N workers share one receiver and pull jobs from it:

Verified output [1, 4, 9, 16, 25, 36]
let (tx, rx) = mpsc::channel::<u32>();
let rx = Arc::new(Mutex::new(rx));       // share the single consumer
let results = Arc::new(Mutex::new(Vec::new()));

for id in 0..3 {
    let rx = Arc::clone(&rx);
    let results = Arc::clone(&results);
    workers.push(thread::spawn(move || {
        loop {
            let job = { rx.lock().unwrap().recv() };   // ← guard drops here
            match job {
                Ok(n) => { results.lock().unwrap().push((id, n*n)); }
                Err(_) => break,                    // channel closed
            }
        }
    }));
}
for i in 1..=6 { tx.send(i).unwrap(); }
drop(tx);                                     // closes the channel → workers exit
The inner block is load-bearing

let job = { rx.lock().unwrap().recv() }; — those braces matter enormously. They drop the mutex guard before processing the job. Without them the lock is held for the whole loop body and your three workers run strictly one at a time, silently. This is the most common way a Rust worker pool ends up with no parallelism at all.

Note the shutdown mechanism: dropping tx closes the channel, recv() returns Err, and every worker breaks out of its loop. No sentinel values, no flags — just ownership.

In production, use Rayon

For data parallelism, rayon turns .iter() into .par_iter() and handles pooling and work-stealing for you. Build a pool by hand once to understand it, then use the library.

PART 14

Does it actually go faster?

Worth measuring rather than assuming. Four CPU-bound tasks, sequential versus four threads:

Real measurement, 12-core machine, rustc -O
cores            = 12
sequential (4x)  = 21.02ms
parallel   (4x)  = 10.77ms
speedup          = 1.95x

Just under 2× from four threads on twelve cores. Amdahl's law, plus thread-creation cost, plus memory-bandwidth contention. Real parallel speedup is always below the theoretical ceiling.

Beware the optimiser when benchmarking

My first attempt at this measurement reported 94 nanoseconds for 160 million iterations — because rustc -O noticed the result was unused and deleted the entire loop. If a benchmark looks impossibly fast, it did not run. Use std::hint::black_box around inputs and results to stop the optimiser removing the work.

How to benchmark honestly
use std::hint::black_box;

let t = Instant::now();
black_box(work(black_box(seed)));      // opaque to the optimiser
let elapsed = t.elapsed();

thread::available_parallelism() reports usable cores — the right default for sizing a pool.

PART 16

Panics, and what survives them

A panic in a spawned thread does not kill the process. It unwinds that thread only, and join() reports it:

Verified output
let h = thread::spawn(|| panic!("boom"));
println!("{}", h.join().is_err());   // → true

// stderr also shows:
// thread '<unnamed>' panicked at t1.rs:67:30: boom

This is why join() returns Result. If you never join, a panicking thread dies silently and your program carries on with work half-done — a good reason to join even when you do not need the value.

EventConsequence
Spawned thread panicsThat thread dies; join() returns Err
Panic while holding a MutexThe mutex is poisoned
Main thread panics or returnsProcess exits; other threads are killed
Panicking thread is never joinedFailure is silent

PART 18

Cheat sheet

Spawn and join

let h = thread::spawn(move || { /* work */ 42 });
let v = h.join().unwrap();          // Result — Err if it panicked

thread::scope(|s| {                     // can borrow locals
    s.spawn(|| { /* borrows fine */ });
});                                     // all joined here

Shared state

let c = Arc::new(Mutex::new(0));
let c2 = Arc::clone(&c);            // per thread, before the move
*c2.lock().unwrap() += 1;           // guard drops at end of statement

let rw = Arc::new(RwLock::new(v));
rw.read().unwrap();                  // many at once
rw.write().unwrap();                 // exclusive

let a = Arc::new(AtomicUsize::new(0));
a.fetch_add(1, Ordering::Relaxed);   // one instruction

Channels

let (tx, rx) = mpsc::channel();          // unbounded
let (tx, rx) = mpsc::sync_channel(10);   // bounded — backpressure
let tx2 = tx.clone();                    // multi-producer
drop(tx);                                 // ← or rx.iter() hangs forever
for msg in rx { /* until all senders drop */ }

The four rules that prevent most bugs

1Keep critical sections tiny — never do I/O holding a lock
2Always take multiple locks in the same global order
3Use while, never if, around cv.wait()
4drop(tx) before draining a channel
What Rust does and does not give you

Prevented at compile time: data races, sending non-Send types, use-after-free across threads, forgetting to lock.
Still your problem: deadlock, livelock, starvation, lost updates from non-atomic operation pairs, and every logic error. Rust makes concurrency memory-safe, not automatically correct.
