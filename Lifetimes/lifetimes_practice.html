For every signature here, ask the same question before writing anything: what does the returned reference point into? Nearly every lifetime error is that question, unanswered.

24 exercises + capstone Guide: lifetimes_guide.html Prerequisite: ownership_guide.html Verified on rustc 1.96

How to use this workbook

  1. Write your attempt before opening the solution.
  2. Compile and run: rustc --edition 2021 practice.rs && ./practice
  3. For every signature, ask the one question: what does the returned reference point into? Almost every lifetime error answers to that.
  4. When you get E0597, read the three annotations in order — declared here, dropped here while still borrowed, borrow later used here. The fix is always to move one of them.
SET 01

Reading signatures

Before writing any annotations, learn to read them. Say each one out loud.

1.1easy The classic longest

Task

Write a function returning the longer of two &str. Then say in words what your signature promises.

Solution
Answer — verified long string
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() > b.len() { a } else { b }
}
Says

"The result lives as long as the shorter of a and b." Not "both must be equal" — 'a is the overlap of the two input lifetimes, and the result cannot escape it.

1.2easy Why does this one need nothing?

Task

fn trim_it(s: &str) -> &str { s.trim() } compiles with no annotation. Which elision rule applies?

Rule, and why

Solution
Rule 2 — verified "padded"
// You write:
fn trim_it(s: &str) -> &str { s.trim() }
// Compiler sees:
fn trim_it<'a>(s: &'a str) -> &'a str

Exactly one input reference, so there is no ambiguity about where the output borrows from. That is the whole difference from 1.1.

1.3medium Tie the output to one input only

Task

Write a function taking two references but returning one tied only to the first. The second should be free to die immediately.

Solution
Answer — verified kept
fn first_of<'a>(x: &'a str, _y: &str) -> &'a str { x }
A stronger promise

_y gets its own anonymous lifetime from rule 1, unrelated to the result. This is more useful than forcing both into 'a, which would needlessly shorten the result to the overlap.

1.4easy When is no lifetime involved?

Task

Write a function taking &str and returning usize. Why is there no lifetime question here at all?

Solution
Answer — verified 5
fn count(s: &str) -> usize { s.len() }
No reference out, no question

usize is owned Copy data — it does not point at anything. Lifetimes only matter for returned references. This is why most functions never need them.

1.5easy A borrow inside an Option

Task

Return the first element of a slice as Option<&i32>.

Solution
Answer — verified Some(7)
fn first<'a>(v: &'a [i32]) -> Option<&'a i32> { v.first() }

// elision handles it too — one input reference:
fn first(v: &[i32]) -> Option<&i32> { v.first() }

A lifetime inside a generic type works exactly the same way. Option<&'a i32> cannot outlive 'a.

SET 02

Elision — predicting the rules

For each, decide whether it compiles bare, and what the compiler expands it to.

2.1easy First word

Task

Return the first word of a sentence, with no annotation. This is the function from the ownership guide — now you can say why it works.

Solution
Answer — verified the
fn first_word(s: &str) -> &str {
    match s.find(' ') { Some(i) => &s[..i], None => s }
}

Rule 2. The returned slice points into s, and there is only one input it could point into.

2.2easy Longest item in a slice

Task

Return the longest String in a slice as a borrow.

Solution
Answer — verified Some("bbb")
fn longest_item(v: &[String]) -> Option<&String> {
    v.iter().max_by_key(|s| s.len())
}

No annotation needed — one input reference. Returning Option<&String> rather than Option<String> avoids a clone.

2.3medium Two outputs from one input

Task

Split a string in half and return both pieces. How many lifetimes are involved?

Solution
Answer — verified ("abc", "def")
fn halves(s: &str) -> (&str, &str) { s.split_at(s.len()/2) }

// expands to:
fn halves<'a>(s: &'a str) -> (&'a str, &'a str)
One lifetime, two uses

Rule 2 assigns the single input lifetime to all outputs. Both slices point into s, so both share 'a.

2.4hard Rule 3, and when to override it

Task

Given struct B<'a> { v: &'a str }, write two getters — one elided, one returning &'a str explicitly. What is the difference to a caller?

Solution
Answer — both verified, both print held
impl<'a> B<'a> {
    fn get(&self) -> &str { self.v }          // rule 3: tied to &self
    fn get_long(&self) -> &'a str { self.v }   // tied to 'a
}
The difference that matters

get's result keeps self borrowed while you hold it — so you cannot call a &mut self method meanwhile. get_long's result is tied to the original string, so self is free again immediately. Same runtime behaviour, very different ergonomics. This is the key to exercise 5.1.

SET 03

Structs that hold references

Where you genuinely must write annotations.

3.1easy An excerpt struct

Task

Write a struct holding a &str borrowed from a novel, plus a constructor and two methods — one returning the part, one returning an i32.

Solution
Answer — verified Excerpt { part: "Call me Ishmael" }
#[derive(Debug)]
struct Excerpt<'a> { part: &'a str }

impl<'a> Excerpt<'a> {
    fn new(part: &'a str) -> Self { Excerpt { part } }
    fn part(&self) -> &str { self.part }
    fn level(&self) -> i32 { 3 }        // no reference out
}
impl<'a> Excerpt<'a>

'a appears twice: declared in impl<'a>, then used in Excerpt<'a>. Identical shape to impl<T> Wrapper<T>. level needs nothing because it returns no reference.

3.2medium Make the struct outlive its source

Task

Deliberately break 3.1 — construct an Excerpt inside a block and use it outside. Predict the error and read all four annotations.

Solution
E0597
let e;
{
    let novel = String::from("Call me Ishmael.");
    e = Excerpt { part: &novel };
}
println!("{}", e.part);
Verified compiler output
error[E0597]: `novel` does not live long enough
5 |         let novel = String::from("Call me Ishmael.");
  |             ----- binding `novel` declared here
6 |         e = Excerpt { part: &novel };
  |                             ^^^^^^ borrowed value does not live long enough
7 |     }
  |     - `novel` dropped here while still borrowed
8 |     println!("{}", e.part);
  |                    ------ borrow later used here
What <'a> bought you

The struct declaration is what makes this checkable: Excerpt<'a> says "an Excerpt may not outlive what it borrows." The fix is to declare novel in the outer scope.

3.3medium A struct with two borrows

Task

Write Pair holding two &str fields, with a method returning the longer one — tied to the source, not to &self.

Solution
Answer — verified alpha
struct Pair<'a> { first: &'a str, second: &'a str }

impl<'a> Pair<'a> {
    fn longer(&self) -> &'a str {
        if self.first.len() >= self.second.len() { self.first } else { self.second }
    }
}

One 'a covers both fields — they must share a common lifetime, which is their overlap. The explicit &'a str return overrides rule 3.

3.4hard Lifetime plus generic type

Task

Write a struct holding &'a T for any T: Display, with a method formatting it.

Solution
Answer — verified 42
struct Wrapper<'a, T> { inner: &'a T }

impl<'a, T: Display> Wrapper<'a, T> {
    fn show(&self) -> String { format!("{}", self.inner) }
}
Order matters

Lifetimes come first in the parameter list: <'a, T>, never <T, 'a>. To the compiler they are the same kind of thing — compile-time parameters — and both are erased before codegen.

SET 04

Returning references, and 'static

The escape hatches, and when each is correct.

4.1medium Fix a dangling return

Task

This does not compile. Give two different valid fixes.

E0515
fn make<'a>() -> &'a String {
    let s = String::from("hello");
    &s
}
Solution
Fix 1 — return owned
fn make() -> String { String::from("hello") }
Fix 2 — a literal, which is 'static
fn make() -> &'static str { "hello" }
Why the annotation did not help

E0515 says "returns a reference to data owned by the current function." Declaring 'a promises a lifetime the caller chooses — but the data dies at the closing brace regardless. Annotations describe reality; they cannot alter it.

4.2easy Borrow in, owned out

Task

Uppercase a &str. Why must the return be owned rather than a slice?

Solution
Answer — verified SHOUT
fn shout(s: &str) -> String { s.to_uppercase() }
Nothing to borrow from

The uppercased text does not exist anywhere in the input — it is new data, so it needs new storage. A slice can only be a window onto bytes that already exist. This is the same reasoning as reversing a string in the ownership workbook.

4.3medium &'static str vs T: 'static

Task

Write a function with bound T: 'static and pass it an owned String. Explain why that compiles, given that a String is not a literal.

Solution
Answer — verified owned data satisfies 'static
fn needs_static<T: 'static>(_t: T) -> &'static str {
    "owned data satisfies 'static"
}

needs_static(String::from("x"));   // compiles
Two different meanings

&'static T is "a reference valid forever." T: 'static is "a type containing no short-lived borrows" — which all owned data satisfies. That is precisely why thread::spawn's F: Send + 'static accepts owned Strings and Vecs.

4.4medium A slice of a slice

Task

Return the middle of a slice (first and last removed), never panicking on short inputs.

Solution
Answer — verified [2, 3, 4]
fn middle<'a>(v: &'a [i32]) -> &'a [i32] {
    if v.len() <= 2 { v } else { &v[1..v.len()-1] }
}

The 'a is optional here — rule 2 would infer it. Writing it out makes the "output borrows from input" relationship explicit, which is often worth it in a public API.

4.5hard Add the outlives bound

Task

This fails. Read the compiler's suggestion and apply it.

lifetime may not live long enough
fn pick<'a, 'b>(x: &'a str, y: &'b str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
Solution
Answer — verified aa
fn pick<'a, 'b: 'a>(x: &'a str, y: &'b str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
Reading 'b: 'a

"'b outlives 'a." A &'b str is then usable wherever a &'a str is wanted — longer coerces to shorter, never the reverse. The compiler's own error said "consider adding the following bound: 'b: 'a".

Simply using one 'a for both also works, and is what you would usually write. The bound is for when the two must stay distinct elsewhere in the signature.

SET 05

Real patterns

Where lifetimes stop being an exercise and start earning their keep.

5.1hard A borrowing tokenizer

Task

Write a Parser holding &'a str with next_token(&mut self) -> Option<&'a str>. Then explain what breaks if you elide that return lifetime.

Solution
Answer — verified ["let", "x", "=", "5"]
struct Parser<'a> { input: &'a str, pos: usize }

impl<'a> Parser<'a> {
    fn new(input: &'a str) -> Self { Parser { input, pos: 0 } }

    fn next_token(&mut self) -> Option<&'a str> {
        let rest = self.input[self.pos..].trim_start();
        if rest.is_empty() { return None; }
        let start = self.input.len() - rest.len();
        let end = rest.find(' ').map(|i| start + i)
                      .unwrap_or(self.input.len());
        self.pos = end;
        Some(&self.input[start..end])
    }
}
The most valuable lifetime lesson there is

Elide that return and rule 3 ties each token to &mut self. Holding a token then keeps the parser mutably borrowed — so while let Some(t) = parser.next_token() will not compile, because you are calling a &mut self method while a previous borrow is live.

Writing &'a str ties tokens to the input string instead, which outlives the parser entirely. The parser is free again the instant the call returns.

5.2medium Split without allocating

Task

Split a string on a separator and return trimmed pieces — with zero allocations for the pieces themselves.

Solution
Answer — verified ["a", "b", "c"]
fn split_trim<'a>(text: &'a str, sep: char) -> Vec<&'a str> {
    text.split(sep).map(|s| s.trim()).collect()
}
Only the Vec allocates

Every &str inside points into text. Vec<&'a str> versus Vec<String> is the difference between one allocation and one-per-piece. Note sep is char — Copy, so no lifetime.

5.3medium Two independent lifetimes in practice

Task

Filter a slice of Strings by a prefix, returning borrows. The prefix must not need to outlive the result.

Solution
Answer — verified ["db_host", "db_port"]
fn with_prefix<'a, 'k>(items: &'a [String], prefix: &'k str) -> Vec<&'a str> {
    items.iter()
        .filter(|s| s.starts_with(prefix))
        .map(|s| s.as_str())
        .collect()
}
Why two names

The results borrow from items ('a); prefix is only read during the call ('k). Separating them lets callers pass a temporary prefix — with_prefix(&items, &format!("db_")) — and still keep the results. One shared 'a would have forbidden that.

5.4medium Borrowing out of a HashMap

Task

Look up a key and return Option<&str> tied to the map, not to the key.

Solution
Answer — verified Some("v")
fn lookup<'a>(m: &'a HashMap<String, String>, k: &str) -> Option<&'a str> {
    m.get(k).map(|s| s.as_str())
}

Here the annotation is required: two input references, so rule 2 does not apply. Without it you get E0106 and the compiler asks whether the result borrows from m or from k.

5.5hard A caching view

Task

Write a struct borrowing a &[i32] that computes a sum once and caches it. Why is there no borrow conflict between the shared field and &mut self?

Solution
Answer — verified 10 then cached 10
struct Cache<'a> { data: &'a [i32], computed: Option<i32> }

impl<'a> Cache<'a> {
    fn new(data: &'a [i32]) -> Self { Cache { data, computed: None } }

    fn sum(&mut self) -> i32 {
        if let Some(v) = self.computed { return v; }
        let v = self.data.iter().sum();
        self.computed = Some(v);
        v
    }
}
Two different things

Mutating the struct (its computed field) is separate from the data it points at. &mut self gives exclusive access to the Cache, while data remains a shared borrow of someone else's slice. Returning i32 rather than a reference also keeps the caller free of any borrow.

5.6medium Borrow or own?

Task

No code — decide. For each, write &'a str or String:

a) a token produced by a parser scanning a buffer

b) a username stored in a Vec<User> for the program's life

c) a config value read from a file that stays in memory

d) an error message built by format!

Solution
Answers
// a) &'a str  — a view over the buffer, zero-copy
// b) String   — long-lived and stored; a lifetime would infect Vec<User>
// c) &'a str  — the file contents outlive the config (the capstone's design)
// d) String   — newly created, nothing to borrow from
The rule

Borrow for a view over data you are passing through; own for a thing your program keeps. If lifetime parameters start spreading through your types, that is the signal to own at some boundary — not to add more annotations.

FINAL

Capstone: a zero-copy config parser

Parse an INI-style config where every key and value borrows from the original text. No String allocations until the very last step.

Given
#[derive(Debug, PartialEq)]
struct Entry<'a> { key: &'a str, value: &'a str, section: &'a str }

struct Config<'a> { entries: Vec<Entry<'a>>, source: &'a str }

// Input:
// # server config
// [server]
// host = localhost
// port = 8080
//
// [db]
// db_host = 127.0.0.1
// db_port = 5432
C.1hard Parse without allocating

Task

Write Config::parse(source: &'a str) -> Self. Skip comments and blanks, track the current section, and store only borrows.

Solution
Answer — verified 4 entries, source len 95
fn parse(source: &'a str) -> Self {
    let mut entries = Vec::new();
    let mut section = "global";          // a &'static str — also fine as &'a
    for line in source.lines() {
        let line = line.trim();
        if line.is_empty() || line.starts_with('#') { continue; }
        if line.starts_with('[') && line.ends_with(']') {
            section = &line[1..line.len()-1];
            continue;
        }
        if let Some(eq) = line.find('=') {
            entries.push(Entry {
                key:   line[..eq].trim(),
                value: line[eq+1..].trim(),
                section,
            });
        }
    }
    Config { entries, source }
}
Every slice points into source

line comes from source.lines(), so it borrows from source. Slicing line further keeps that lifetime. The entire parse allocates only the Vec — not one byte of text is copied.

C.2hard Two getters, two lifetimes

Task

Write get (elided) and get_long (returning Option<&'a str>). What can a caller do with one but not the other?

Solution
Answer — verified Some("localhost") and Some("8080")
// elided — result tied to &self
fn get(&self, key: &str) -> Option<&str> {
    self.entries.iter().find(|e| e.key == key).map(|e| e.value)
}

// explicit — result tied to the SOURCE, outliving &self
fn get_long(&self, key: &str) -> Option<&'a str> {
    self.entries.iter().find(|e| e.key == key).map(|e| e.value)
}
Proof — get_long survives the Config being dropped
let value_outliving_config;
{
    let cfg = Config { /* borrows text */ };
    value_outliving_config = cfg.get_long("host");
}   // cfg dropped here
println!("{:?}", value_outliving_config);
// → Some("localhost")   ✓ compiles and runs
The same code with get() — real compiler output
error[E0597]: `cfg` does not live long enough
15 |         let cfg = Config { ... };
   |             --- binding `cfg` declared here
16 |         value_outliving_config = cfg.get("host");
   |                                  ^^^ borrowed value does not live long enough
17 |     }
   |     - `cfg` dropped here while still borrowed
18 |     println!("{:?}", value_outliving_config);
   |                      ---------------------- borrow later used here
Identical bodies, different contracts

The two methods have exactly the same body and compile to exactly the same machine code. Only the signature differs — and that difference decides whether the caller above compiles.

get's result keeps the Config borrowed; get_long's points into source, which outlives the config. Rule 3 chose the weaker option by default; writing 'a takes the stronger one.

C.3medium Return a collection of borrows

Task

Return every key in a named section as Vec<&'a str>.

Solution
Answer — verified ["db_host", "db_port"]
fn section(&self, name: &str) -> Vec<&'a str> {
    self.entries.iter()
        .filter(|e| e.section == name)
        .map(|e| e.key)
        .collect()
}

One allocation for the Vec; the strings inside are still views into the original text.

C.4hard A needle that need not outlive the haystack

Task

Return all values whose key starts with a prefix. The prefix may be a temporary.

Solution
Answer — verified ["127.0.0.1", "5432"]
fn find_prefix<'k>(&self, prefix: &'k str) -> Vec<&'a str> {
    self.entries.iter()
        .filter(|e| e.key.starts_with(prefix))
        .map(|e| e.value)
        .collect()
}
Three lifetimes in one signature

'a (the source), 'k (the prefix), and the elided lifetime of &self — all distinct. The results are tied only to 'a, so the prefix can be a temporary and self can be dropped, and the returned values stay valid.

C.5medium Prove it is really zero-copy

Task

Demonstrate that a parsed value points inside the original buffer rather than being a copy. Use pointer arithmetic.

Solution
Answer — verified true
let v = cfg.get("host").unwrap();
let inside = v.as_ptr() as usize >= text.as_ptr() as usize
          && (v.as_ptr() as usize) < text.as_ptr() as usize + text.len();
// value borrows into the original buffer = true
What the lifetime was protecting

The value's pointer falls within the original String's heap allocation — it is genuinely the same memory. That is exactly why Config<'a> must not outlive text: drop the text and every parsed value becomes a dangling pointer. The annotation is what makes that impossible.

C.6hard Escape the lifetime

Task

Write into_owned(self) -> HashMap<String, String>. Why does the return type have no lifetime parameter — and when would you actually call this?

Solution
Answer — verified ["db_host", "db_port", "host", "port"]
fn into_owned(self) -> HashMap<String, String> {
    self.entries.into_iter()
        .map(|e| (e.key.to_string(), e.value.to_string()))
        .collect()
}
The boundary between borrowed and owned

This is the only place that allocates strings — and it is deliberate. The result owns its data, so it has no lifetime parameter and can outlive text, be stored in a struct, or be sent to another thread (it now satisfies T: 'static).

The pattern: borrow while parsing and filtering, which is the hot path; own once at the boundary, when the data must outlive its source. Taking self by value means the keys and values move out with no double allocation.
