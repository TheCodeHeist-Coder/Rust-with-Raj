Rust · Learning notes

Lifetimes:
naming what you already knew

Lifetimes have a reputation for being the hard part of Rust. They are not a new rule — every borrow you have ever written already had one. The compiler was inferring them silently. Lifetime syntax appears only when it genuinely cannot guess, and this guide is about the handful of cases where that happens.

17 parts Prerequisite: ownership_guide.html Practice: lifetimes_practice.html Verified on rustc 1.96
PART 01

What a lifetime actually is

A lifetime is the span of code over which a reference is valid.

That is the whole definition. Not a duration in seconds, not a runtime property — a region of your source code. Every reference has one, and the compiler has been computing them for you since your first program.

  fn main() {
      let r;                       ┐
      {                            │
          let x = 5;        ┐      │  'a — how long r
          r = &x;           │ 'b   │       must be valid
      }                     ┘      │
      println!("{r}");             ┘
  }

  'b (x's life) is SHORTER than 'a (r's life)
  → the borrow checker rejects this.

The borrow checker compares two regions and asks: does the referent outlive the reference?

Here is that program, and the error it produces:

Does not compile
let result;
{
    let inner = String::from("short lived");
    result = &inner;
}
println!("{result}");
error[E0597]: `inner` does not live long enough
 --> le2.rs:5:18
  |
4 |         let inner = String::from("short lived");
  |             ----- binding `inner` declared here
5 |         result = &inner;
  |                  ^^^^^^ borrowed value does not live long enough
6 |     }
  |     - `inner` dropped here while still borrowed
7 |     println!("{result}");
  |                ------ borrow later used here

Read those four annotations in order — they are the complete argument. Declared here, borrowed here, dropped here while still borrowed, used here. The compiler is showing you a reference that outlives its referent.

You have already met this

This is the same E0597 from the ownership guide, and the same rule: every reference must always be valid. Lifetimes are not a second system bolted on top — they are the notation for the rule you already know.

PART 02

Why the syntax exists at all

Inside a single function the compiler can see everything and needs no help. The problem appears at function boundaries, where it can only see the signature.

Does not compile
fn longest(a: &str, b: &str) -> &str {
    if a.len() > b.len() { a } else { b }
}
error[E0106]: missing lifetime specifier
 --> le1.rs:1:33
  |
1 | fn longest(a: &str, b: &str) -> &str {
  |               ----     ----     ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but the signature does
          not say whether it is borrowed from `a` or `b`
help: consider introducing a named lifetime parameter
  |
1 | fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
  |           ++++     ++          ++          ++
"the signature does not say whether it is borrowed from a or b"

That single sentence is the entire reason lifetime syntax exists. The compiler is not confused about the body — it can see the if. It is telling you that callers only get to read the signature, and the signature is ambiguous.

Why the caller needs to know

Consider what a caller must decide: how long may I keep the returned reference? If the answer is "as long as a lives" that permits one thing; "as long as b lives" permits another. Without the annotation there is no answer, and the compiler will not guess.

Annotated — verified output long string is long
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() > b.len() { a } else { b }
}
Annotations describe; they do not change

Writing 'a does not make anything live longer. You are describing a relationship that already exists so the compiler can check it. Lifetime syntax is documentation the compiler enforces — nothing about the running program changes.

PART 03

Reading the syntax

The notation is small. Four pieces and you can read any signature.

  fn longest<'a>(a: &'a str, b: &'a str) -> &'a str
             │        │            │           │
             │        └────────────┴───────────┴──  used here
             │
             └── declared here, like a generic parameter

  &str        a reference          (lifetime inferred)
  &'a str     a reference with lifetime 'a
  &'a mut str a mutable reference with lifetime 'a
  <'a>        declares the lifetime parameter

Lifetimes are declared in angle brackets, exactly like generic type parameters.

The name is arbitrary — 'a, 'b, 'input all work. Convention is short lowercase, starting at 'a. The apostrophe is what marks it as a lifetime rather than a type.

How to say it out loud

SignatureReads as
fn f<'a>(x: &'a str) -> &'a str"the output lives as long as x"
fn f<'a>(x: &'a str, y: &str) -> &'a str"the output lives as long as x; y is unrelated"
fn f<'a>(x: &'a str, y: &'a str) -> &'a str"the output lives as long as the shorter of x and y"
struct S<'a> { f: &'a str }"an S cannot outlive what f borrows"
The third row is the one people misread

Giving two parameters the same 'a does not mean they must have equal lifetimes. It means the compiler substitutes the shorter of the two — 'a is the overlap. That is why part 04's example fails: the overlap ends when the inner scope does.

PART 04

What the annotation actually enforces

Here is where the theory becomes concrete. With longest correctly annotated, this still fails — and understanding why is the heart of the topic:

Does not compile, even though longest is correct
let outer = String::from("outer");
let result;
{
    let inner = String::from("inner is much longer");
    result = longest(&outer, &inner);
}
println!("{result}");
error[E0597]: `inner` does not live long enough
  --> le3.rs:9:34
   |
 8 |         let inner = String::from("inner is much longer");
   |             ----- binding `inner` declared here
 9 |         result = longest(&outer, &inner);
   |                                  ^^^^^^ borrowed value does not live long enough
10 |     }
   |     - `inner` dropped here while still borrowed
11 |     println!("{result}");
   |                ------ borrow later used here

Notice what the compiler did not do: it never looked at the function body. It did not reason "well, inner is longer, so the result is inner, so this is unsafe." It only used the signature.

  let outer = ...;          ┐
  let result;               │  'outer
  {                         │
      let inner = ...;  ┐   │
      result = longest( │   │   'a = the SHORTER of the two
          &outer,       │'in│      = 'inner
          &inner);      │   │
  }                     ┘   │   ← 'a ends HERE
  println!("{result}");     │   ← but result is used HERE ✗
                            ┘

'a is the overlap of the two input lifetimes. The result cannot outlive it.

The signature said the output lives as long as 'a, and 'a is the shorter of the two inputs. So the result is only valid until inner dies — regardless of which branch actually ran.

Why this design is right

Checking signatures rather than bodies is what makes Rust's analysis modular. Change a function's body and no caller needs rechecking; change its signature and the compiler tells you exactly who is affected. It also means the check works across crates, where the body may not even be available.

And this version compiles, because the result is used while both inputs are still alive:

Verified output outer is longer
let outer = String::from("outer is longer");
{
    let inner = String::from("inner");
    println!("{}", longest(&outer, &inner));   // used inside the scope
}
PART 05

Elision — why you rarely write any of this

If every borrow has a lifetime, why does almost no Rust code have annotations? Because of three elision rules the compiler applies automatically. If they determine every lifetime, you write nothing.

Rule 1: each elided input reference gets its own lifetime parameter.
Rule 2: if there is exactly one input lifetime, it is assigned to all outputs.
Rule 3: if one input is &self or &mut self, its lifetime is assigned to all outputs.

Rule 2 in action

Verified output the
// What you write:
fn first_word(s: &str) -> &str {
    match s.find(' ') { Some(i) => &s[..i], None => s }
}

// What the compiler sees (rule 1 then rule 2):
fn first_word<'a>(s: &'a str) -> &'a str

One input reference, so there is no ambiguity about where the output borrows from. That is why first_word in the ownership guide needed no annotation while longest did — longest has two inputs, so rule 2 does not apply and nothing else resolves it.

Rule 3 in action

Verified — both work
impl<'a> Excerpt<'a> {
    // elided → tied to &self by rule 3
    fn part(&self) -> &str { self.part }

    // explicit → tied to 'a, which OUTLIVES &self
    fn announce(&self, msg: &str) -> &'a str {
        println!("announce: {msg}");
        self.part
    }
}

Rule 3 is why methods almost never need annotations. It is also why announce must be explicit if you want the stronger guarantee — see part 09.

When elision fails, you get E0106

The rules are not heuristics or guesses — they are deterministic. If they resolve every output lifetime, your code compiles with no annotations. If they do not, you get "missing lifetime specifier" and must say what you mean. There is no third outcome.

PART 06

Structs that hold references

So far every struct you have written owned its data. A struct can hold a borrow instead — but then it needs a lifetime parameter:

Does not compile
struct Excerpt { part: &str }
error[E0106]: missing lifetime specifier
 --> le6.rs:1:24
  |
1 | struct Excerpt { part: &str }
  |                        ^ expected named lifetime parameter
  |
help: consider introducing a named lifetime parameter
  |
1 | struct Excerpt<'a> { part: &'a str }
  |               ++++          ++
Verified output Excerpt { part: "Call me Ishmael" }
#[derive(Debug)]
struct Excerpt<'a> { part: &'a str }

let novel = String::from("Call me Ishmael. Some years ago...");
let first = novel.split('.').next().expect("no .");
let e = Excerpt { part: first };
struct Excerpt<'a> means: an Excerpt may not outlive the string it borrows from.

And the compiler enforces exactly that:

Does not compile — the struct outlives its source
let e;
{
    let novel = String::from("Call me Ishmael.");
    e = Excerpt { part: &novel };
}
println!("{}", e.part);
error[E0597]: `novel` does not live long enough
 --> le4.rs:6:29
  |
5 |         let novel = String::from("Call me Ishmael.");
  |             ----- binding `novel` declared here
6 |         e = Excerpt { part: &novel };
  |                             ^^^^^^ borrowed value does not live long enough
7 |     }
  |     - `novel` dropped here while still borrowed
8 |     println!("{}", e.part);
  |                    ------ borrow later used here

The impl block needs it too

Note 'a appears twice
impl<'a> Excerpt<'a> {
//   ↑ declare      ↑ use
    fn new(part: &'a str) -> Self { Excerpt { part } }
    fn level(&self) -> i32 { 3 }        // no reference out — no lifetime
}

Same shape as generics: impl<T> Wrapper<T> declares then uses. Methods returning no references need no annotation at all.

Should your struct hold a reference?

Often not. A struct with a lifetime parameter infects everything that holds it — every containing struct needs one too. Borrow when you are building a short-lived view over data (a parser, an iterator, an excerpt); own when the struct is long-lived or stored in a collection. Part 13 develops this.

PART 07

Returning references — and E0515

The most common lifetime failure. Annotating a return type does not conjure a valid reference:

Does not compile — annotation cannot save it
fn dangle<'a>() -> &'a String {
    let s = String::from("hello");
    &s
}
error[E0515]: cannot return reference to local variable `s`
 --> le5.rs:3:5
  |
3 |     &s
  |     ^^ returns a reference to data owned by the current function

A different error from the ownership guide's version of this — there, omitting 'a gave E0106. Here the lifetime is declared, so the compiler moves on to the real problem: the data is owned by this function and dies at the closing brace. There is nothing for 'a to refer to.

A returned reference must borrow from an input, or from something that outlives the call. Never from a local.
You want to returnDo this
Part of an argumentfn f(s: &str) -> &str — elision handles it
Something newly createdReturn it owned: -> String
A string literal-> &'static str — see part 08
Data from selffn f(&self) -> &str — rule 3
The three valid shapes — all verified
// borrow from the input
fn trim_it(s: &str) -> &str { s.trim() }            // "padded"

// return owned
fn shout(s: &str) -> String { s.to_uppercase() }        // "SHOUT"

// a literal lives forever
fn label() -> &'static str { "literals are &'static str" }
PART 08

'static — the longest lifetime

'static means "valid for the entire program." Two things have it naturally:

Verified output
// 1. string literals — baked into the binary
let s: &'static str = "I live for the whole program";

// 2. anything you leak or declare static
static GREETING: &'static str = "hello";

Every string literal you have ever written was a &'static str. That is why passing "hello" to a function expecting &str always works, no matter how long the result is kept.

The distinction that trips people up

&'static TT: 'static
MeansA reference valid foreverA type containing no short-lived borrows
Satisfied byLiterals, leaked dataAll owned data — String, Vec, i32
Common inConstantsthread::spawn bounds
Verified — an owned String satisfies T: 'static
fn needs_static<T: 'static>(_t: T) -> &'static str { "ok" }

needs_static(String::from("owned is 'static"));   // compiles!
This resolves a threading puzzle

thread::spawn requires F: Send + 'static, yet you pass it owned Strings and Vecs constantly. Now you know why: T: 'static means "contains no borrows that could dangle," and owned data qualifies trivially. It never meant "lives forever."

Not a fix for lifetime errors

Adding 'static to silence a borrow error almost always makes things worse — you have promised something stronger and pushed the error to the call site. If a reference does not live long enough, either restructure so it does, or return owned data.

PART 09

Multiple lifetimes, and outlives bounds

When inputs genuinely have unrelated lifetimes, give them different names:

Verified output alpha
fn first_of<'a, 'b>(x: &'a str, _y: &'b str) -> &'a str { x }

The result is tied to x only. y may die immediately afterwards and the result stays valid — a stronger and more useful promise than forcing both into one 'a.

When two lifetimes need a relationship

Try to return either one and it fails:

Does not compile
fn pick<'a, 'b>(x: &'a str, y: &'b str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
error: lifetime may not live long enough
 --> le7.rs:3:39
  |
2 | fn pick<'a, 'b>(x: &'a str, y: &'b str) -> &'a str {
  |         --  -- lifetime `'b` defined here
  |         |
  |         lifetime `'a` defined here
3 |     if x.len() > y.len() { x } else { y }
  |                                       ^ function was supposed to return data with
  |                                         lifetime `'a` but it is returning data
  |                                         with lifetime `'b`
  |
  = help: consider adding the following bound: `'b: 'a`

The compiler hands you the fix. 'b: 'a reads "'b outlives 'a" — so a &'b str is safe to use anywhere a &'a str is expected:

Verified output aa
fn pick<'a, 'b: 'a>(x: &'a str, y: &'b str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
Reading 'b: 'a

The colon means the same as in trait bounds: "satisfies." 'b: 'a is "'b lives at least as long as 'a." Longer lifetimes coerce to shorter ones, never the reverse — the same direction as subtyping.

Combined with generics and traits

Verified output alpha
fn longest_with<'a, T: Display>(a: &'a str, b: &'a str, ann: T) -> &'a str {
    println!("note: {ann}");
    if a.len() > b.len() { a } else { b }
}

Lifetimes and type parameters share one angle-bracket list, lifetimes first. They are the same kind of thing to the compiler: parameters resolved at compile time.

PART 10

Lifetimes are erased — the zero-cost proof

Everything so far happens at compile time. The binary contains no lifetime information at all:

Verified output
println!("{}", std::mem::size_of::<&str>());            // 16
println!("{}", std::mem::size_of::<&'static str>());   // 16

Identical. A &'static str and an ordinary &str are the same 16 bytes — pointer plus length. The lifetime existed only during type checking and was then discarded.

  COMPILE TIME                          RUNTIME
  ─────────────                         ───────
  &'a str   ┐
  &'b str   ├─ checked, then erased ──► just a pointer
  &'static  ┘                            + a length

  no tags, no refcounts, no checks, no cost

Lifetimes are a static analysis. They cost nothing at runtime.

The same trick as everywhere else

Generics are monomorphised away; Send/Sync are markers with no methods; lifetimes are erased. Rust's pattern is consistent — encode the property in the type system, verify it, then compile it out. You pay in compile time and in learning, never at runtime.

PART 11

A real pattern: the borrowing parser

Here is where lifetimes earn their keep. A parser that holds a reference to its input and hands out slices of it — no allocation anywhere:

Verified output ["let", "x", "=", "5"]
struct Parser<'a> { input: &'a str, pos: usize }

impl<'a> Parser<'a> {
    fn new(input: &'a str) -> Self { Parser { input, pos: 0 } }

    // Returns &'a str, NOT &str — the token outlives the &mut self borrow.
    fn next_token(&mut self) -> Option<&'a str> {
        let rest = self.input[self.pos..].trim_start();
        if rest.is_empty() { return None; }
        let start = self.input.len() - rest.len();
        let end = rest.find(' ').map(|i| start + i).unwrap_or(self.input.len());
        self.pos = end;
        Some(&self.input[start..end])
    }
}

let text = String::from("let x = 5");
let mut parser = Parser::new(&text);
while let Some(t) = parser.next_token() { toks.push(t); }
The one crucial detail

next_token returns Option<&'a str>, not the elided Option<&str>. Rule 3 would have tied the token to &mut self — meaning each token would keep the parser mutably borrowed, and you could not call next_token again while holding one. Writing 'a explicitly ties tokens to the input instead, so they outlive the borrow of the parser. This is the single most valuable thing to understand about lifetimes in practice.

Without it, the while let loop above would not compile — you would be holding a token (borrowing the parser) while calling a method needing &mut self.

PART 12

Lifetimes and the borrow checker together

A struct holding a borrow interacts with the usual borrowing rules. This works because the borrows are compatible:

Verified output 10 then cached 10
struct Cache<'a> { data: &'a [i32], computed: Option<i32> }

impl<'a> Cache<'a> {
    fn new(data: &'a [i32]) -> Self { Cache { data, computed: None } }

    fn sum(&mut self) -> i32 {
        if let Some(v) = self.computed { return v; }
        let v = self.data.iter().sum();
        self.computed = Some(v);
        v
    }
}

The struct holds &'a [i32] (shared) while sum takes &mut self. No conflict: mutating the struct is separate from the data it points at. Returning i32 rather than a reference also keeps things simple.

The rule of thumb for return types

ReturnWhenEffect on the caller
&str (elided)The value is logically part of selfKeeps self borrowed while held
&'a str (explicit)The value comes from borrowed inputself is free again immediately
String / i32The value is computedNo borrow at all

When a method returning a borrow makes callers fight the borrow checker, this table is where to look. Usually the answer is that an elided lifetime should have been 'a.

PART 13

Should this struct borrow or own?

The design question lifetimes force you to answer. Both versions are legitimate:

struct S<'a> { f: &'a str }struct S { f: String }
AllocationNone — zero-copyOne per field
LifespanCannot outlive its sourceIndependent
Storing in a collectionAwkward — infects the collectionEasy
Returning from a functionOnly if borrowing an inputAlways fine
Good forParsers, views, iterators, short-lived scansDomain types, config, anything stored
Borrow for a view over data you are passing through. Own for a thing your program keeps.
Lifetime parameters are contagious

Put &'a str in a struct and every struct containing it needs 'a too, and so on outward. That is fine for a parser used inside one function; it is painful for a type stored in a long-lived collection. If annotations are spreading through your codebase, the fix is usually to own the data at some boundary — not to add more lifetimes.

A common and healthy pattern is to borrow while processing and own at the end — exactly what the capstone in the practice workbook does with into_owned.

PART 14

Every error, decoded

CodeSaysMeansFix
E0106 missing lifetime specifier Elision could not decide where the output borrows from Add <'a> and mark which input; or return owned
E0597 x does not live long enough A reference outlives its referent Move the value to an outer scope, or use it earlier
E0515 cannot return reference to local variable Returning a borrow of something this function owns Return an owned value instead
(no code) lifetime may not live long enough Returning 'b data where 'a was promised Add the bound 'b: 'a
E0621 explicit lifetime required An elided lifetime is too weak for what you do Name it and tie it to the right input

E0621 is the one you have not seen yet. It appears when an elided lifetime is too weak for what the body does — here, storing a reference into a collection that outlives it:

error[E0621]: explicit lifetime required in the type of `item`
 --> le8.rs:3:5
  |
3 |     dest.push(item);
  |     ^^^^^^^^^^^^^^^ lifetime `'a` required
  |
help: add explicit lifetime `'a` to the type of `item`
  |
2 | fn store<'a>(dest: &mut Vec<&'a S>, item: &'a S) {
  |                                            ++

Elision gave item its own anonymous lifetime (rule 1), but pushing it into a Vec<&'a S> requires it to live at least as long as 'a. The fix, as always, is in the help: line.

How to debug any lifetime error

Ask: what does this reference point into, and is that thing still alive when the reference is used?
  1. Find "borrowed value does not live long enough" — that is the reference.
  2. Find "dropped here while still borrowed" — that is when the data dies.
  3. Find "borrow later used here" — that is why it needed to survive.
  4. Fix by moving step 2 later (declare the value in an outer scope) or step 3 earlier.
  5. If neither is possible, the reference should not be a reference — return owned data.

Notice this is the same procedure as the ownership guide's borrow-error recipe. It is the same checker; lifetimes just give the regions names.

PART 15

Things you do not need yet

Four features you will meet in other people's code. Recognising them is enough for now.

'_ — the anonymous lifetime

fn f(e: Excerpt<'_>) { }      // "there is a lifetime, I don't need to name it"
impl Excerpt<'_> { }            // same, in an impl block

Purely for readability — it makes "this type has a lifetime" visible without inventing a name.

Higher-ranked trait bounds

fn call_with<F>(f: F) where F: for<'a> Fn(&'a str) -> &'a str { }

for<'a> means "for every possible lifetime," not one specific one. Needed when a closure must work with references of any lifetime. You will see it in error messages long before you need to write it.

Variance

The rules for when &'long T may be used as &'short T. It is why longer lifetimes coerce to shorter ones, and it works silently. Worth knowing the word exists.

Self-referential structs

A struct holding a reference to its own field cannot be expressed in safe Rust — moving it would invalidate the reference. This is what Pin and crates like ouroboros address, and it is the one genuine expressiveness limit lifetimes impose.

Do not go looking for these

Ordinary application code uses <'a> on a few structs and almost nothing else. If you find yourself needing HRTBs or fighting variance, step back and ask whether owning the data would be simpler. It usually is.

PART 16

Where lifetimes have already appeared

Worth collecting, because you have been using them for six topics without the syntax.

Why scoped threads work

Now you can state it exactly. thread::spawn demands 'static because the thread may outlive the caller. thread::scope guarantees all threads join before it returns, so borrows of local data are provably valid for the whole thread's life — the 'static requirement can be dropped. That was the one piece of the threads guide that needed this topic to be complete.

PART 17

Cheat sheet

Syntax

&str              // reference, lifetime inferred
&'a str           // reference with lifetime 'a
&'a mut str       // mutable reference with lifetime 'a
&'static str      // valid for the whole program

fn f<'a>(..)        // declare a lifetime parameter
struct S<'a> {..}   // struct holding a borrow
impl<'a> S<'a> {..} // declare, then use
<'b: 'a>           // 'b outlives 'a
T: 'static          // T contains no short-lived borrows
S<'_>              // anonymous — "has a lifetime, unnamed"

The three elision rules

// 1. every elided input reference gets its own lifetime
// 2. exactly ONE input lifetime  → assigned to all outputs
// 3. one input is &self/&mut self → ITS lifetime goes to all outputs

fn f(s: &str) -> &str              // rule 2 — fine
fn f(a: &str, b: &str) -> &str    // E0106 — must annotate
fn f(&self, x: &str) -> &str     // rule 3 — tied to self

Do I need an annotation?

Function returns no referenceNo
Exactly one input referenceNo — rule 2
Method with &self returning a borrow of selfNo — rule 3
Two-plus input refs, one returnedYes — say which
Struct holding a referenceYes — struct S<'a>
Method result must outlive &selfYes — write 'a explicitly

Fixes, in order of preference

1Declare the borrowed value in a longer-lived scope
2Use the result earlier, before the source dies
3Return owned data (String) instead of a borrow
4Add the annotation the compiler suggested
5Add an outlives bound 'b: 'a
—Reaching for 'static is almost never the answer
If you remember one thing

Lifetime annotations never change how long anything lives. They describe a relationship between input and output references so the compiler can verify at every call site what it cannot see from a signature alone. When you are stuck, ask what the reference points into — and whether that is still alive when it is used.
