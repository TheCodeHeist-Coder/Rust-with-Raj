Traits in Rust:
shared behavior, zero cost

A structure is data. A trait is behavior. Everything in this guide follows from keeping those two ideas apart — and from one question the compiler keeps asking you: prove this type can do that.

19 parts Companion: traits_complete_guide.rs Exercises: traits_practice.rs Edition 2021
PART 01

The mental model — why traits exist

The problem

Say you have three animal types, each making a sound. You write one function per animal. Then you want "make this animal speak twice" — and you write three more. The logic is identical; only the type changes.

You already know generics, so the instinct is right:

This does not compile
fn speak_twice<T>(animal: &T) {
    println!("{} {}", animal.speak(), animal.speak());
}
error[E0599]: no method named `speak` found for reference `&T`
              in the current scope

The compiler is saying: "T could be any type — i32, String, Vec<u8>. I have no idea whether it has a .speak() method. Prove it to me."

A trait is that proof. It is a named contract saying: any type implementing me guarantees these methods exist.

The key mental split

Beginners mix these up constantly. Keep them separate and traits become easy:

struct  →  defines DATA       (what a type HAS)
trait   →  defines BEHAVIOR   (what a type CAN DO)
impl    →  CONNECTS them      (this type does this behavior)

Three keywords, three jobs. Every confusion about traits traces back to blurring these.

The split, as code
// DATA: a Dog has a name. Says nothing about what it can DO.
struct Dog { name: String }

// BEHAVIOR: "things that can speak". Says nothing about data.
trait Speak { fn speak(&self) -> String; }

// CONNECTION: a Dog can speak, and here is HOW.
impl Speak for Dog {
    fn speak(&self) -> String { format!("{} says Woof!", self.name) }
}

// Now this compiles. `T: Speak` is the proof the compiler wanted.
fn speak_twice<T: Speak>(animal: &T) {
    println!("{} {}", animal.speak(), animal.speak());
}

If you know other languages

LanguageClosest concept
Java / C#interface
Gointerface — but Go's is implicit, Rust's explicit
Pythonduck typing / ABCs / Protocols
C++abstract base class, or concepts (C++20)
Haskelltypeclass — the closest; Rust borrowed from here

Rust's traits go further than Java interfaces: default methods, associated types, operator overloading, generic parameters — all checked at compile time with zero runtime cost.

PART 02

Basic syntax

Declaring a trait states a contract. Implementing it fulfills that contract for one specific type.

Declare, then implement
trait Greet {
    fn hello(&self) -> String;   // no body — a REQUIRED method
}

struct Dog { name: String }
struct Cat { name: String }

impl Greet for Dog {
    fn hello(&self) -> String { format!("{} says Woof!", self.name) }
}

impl Greet for Cat {
    fn hello(&self) -> String { format!("{} says Meow!", self.name) }
}

Read impl Greet for Dog as "implement Greet for Dog". The trait itself implements nothing — it is a contract, not code.

Two kinds of impl block

Do not confuse these
impl Dog { ... }              // INHERENT — methods belonging to Dog alone
impl Greet for Dog { ... }    // TRAIT — Dog fulfilling a shared contract

Both give Dog methods, called identically with dot syntax. The difference: inherent methods are Dog-specific; trait methods are part of a vocabulary other types also speak.

Self versus self

  • Self (capital) — the type being implemented. In impl Greet for Dog, Self means Dog. Used in return types.
  • self (lowercase) — the instance. Used as a parameter, in three forms: &self borrows immutably, &mut self borrows mutably, self takes ownership.
The most common beginner error

A trait's methods are only callable if the trait is in scope. Import the type but forget the trait, and the method vanishes:

error[E0599]: no method named `hello` found for struct `Dog`
  = help: items from traits can only be used if the trait is in scope
  help: the following trait is implemented but not in scope;
        perhaps add a `use` for it:
        + use animals::Greet;

This is why you write use std::io::Write; before calling .flush(). flush() comes from the Write trait, not from Stdout itself — that is the entire reason for that import.

Marker traits

A trait with no methods is still useful. Marker traits carry no behavior, only a compile-time fact about the type. Real examples: Copy, Send, Sync.

PART 03

Default methods

A trait method can have a body. Implementors get it free and may override it.

Required accessor + default logic
trait Greet {
    fn name(&self) -> String;              // REQUIRED

    fn hello(&self) -> String {             // DEFAULT
        format!("Hello, {}!", self.name())
    }

    fn shout(&self) -> String {             // defaults can call defaults
        self.hello().to_uppercase()
    }
}

impl Greet for Person {
    fn name(&self) -> String { self.name.clone() }
    // hello() and shout() come free
}

Look closely at hello(). It calls self.name() — a method whose implementation it does not know. That is the trait calling back into the implementor. You write the interesting logic once; each type supplies only the piece that differs.

This is how Iterator works

Implement exactly one method — next() — and receive .map(), .filter(), .take(), .zip(), .enumerate(), .sum(): roughly seventy methods, all defaults on the Iterator trait. This mechanism, at maximum leverage.

A subtle rule

A default method cannot touch struct fields:

Does not compile
trait Greet {
    fn hello(&self) -> String {
        format!("Hello, {}!", self.name)   // error: no field `name` on &Self
    }
}

The trait has no idea what fields the implementing type has — Self could be a struct, an enum, an i32. Fields are data; traits describe behavior. Access data through a required accessor method. That is exactly why the "required accessor + default logic" pattern exists.

Design rule

Few required methods, many defaults built on them. That makes your trait easy to implement and rich to use.

PART 04

Traits as function parameters

Three syntaxes, nearly the same meaning:

Three ways to say the same thing
fn introduce(item: &impl Greet)              { ... }   // 1. impl Trait
fn introduce<T: Greet>(item: &T)            { ... }   // 2. trait bound
fn introduce<T>(item: &T) where T: Greet { ... }   // 3. where clause

When 1 and 2 actually differ

This distinction matters
fn compare(a: &impl Greet, b: &impl Greet)  // a, b may be DIFFERENT types
fn compare<T: Greet>(a: &T, b: &T)          // a, b must be the SAME type

The second is impossible to express with impl Trait. Once you name T, every use refers to that one type.

Rule of thumb

Use impl Trait for simple cases. Use the bound form when you need to name the type or reuse it. Move to where once you have more than one or two bounds.

Multiple bounds, and the slice limitation

Combining bounds with +
fn show<T: Greet + Debug>(item: &T) { ... }   // must implement BOTH

fn greet_all<T: Greet>(items: &[T]) { ... }     // every element SAME type
The limitation that motivates Part 8

&[T] means every element is the same type. You cannot mix dogs and cats in that slice. Storing a genuinely mixed collection requires trait objects.

PART 05

Deriving traits

Some traits are mechanical enough that the compiler writes them for you. You have used #[derive(Debug)] already — now you know what it really is: derive generates a trait impl at compile time.

TraitGives youRequires
Debug{:?} formattingall fields Debug
Clone.clone() — explicit deep copyall fields Clone
Copyimplicit bitwise copy, not moveall fields Copy + Clone
PartialEq== and !=all fields PartialEq
Eqmarks equality total (no NaN)PartialEq
PartialOrd< > <= >=PartialEq
Ordtotal ordering, enables .sort()Eq + PartialOrd
Hashusable as a HashMap keyall fields Hash
DefaultType::default()all fields Default
Field order is semantic

PartialOrd and Ord derive lexicographically by field order — first field, then second on a tie, then third. Reorder your struct declaration and < changes meaning.

Copy versus Clone — the ownership connection

Move versus copy
let a = Big { data: String::from("hi") };
let b = a;              // MOVE — `a` is now invalid

let p = Small { x: 1, y: 2 };  // Small is Copy
let q = p;              // COPY — `p` is STILL VALID

Try deriving Copy on a struct holding a String:

error[E0204]: the trait `Copy` cannot be implemented for this type
 |  s: String,
 |  --------- this field does not implement `Copy`

String owns a heap allocation. A bitwise copy would produce two Strings pointing at the same buffer, and both would free it on drop — a double free. Rust forbids it at compile time. That is the whole reason Copy is a separate opt-in trait.

When derive is not enough

Derive is all-or-nothing — it uses every field. For custom logic (say, two users are equal when their IDs match, ignoring name and login time), write the impl by hand.

PART 06

Implementing standard library traits

This is where traits stop being academic. Implementing std traits plugs your types into the language itself.

Display — user-facing output

Debug ({:?}) is for programmers and is derivable. Display ({}) is for users and is never derivable — only you know how your type should read to a human.

The signature is always exactly this
use std::fmt;

impl fmt::Display for Point {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "({}, {})", self.x, self.y)   // NO semicolon
    }
}

No semicolon after write! — it is the tail expression returning fmt::Result. Adding ; returns () and fails to compile.

Free bonus

Implementing Display gives you .to_string() free, via the blanket impl impl<T: Display> ToString for T. See Part 12.

From and Into — conversions

Implement From, get Into free
impl From<Celsius> for Fahrenheit {
    fn from(c: Celsius) -> Self { Fahrenheit(c.0 * 9.0 / 5.0 + 32.0) }
}

let f = Fahrenheit::from(Celsius(100.0));   // explicit From
let f: Fahrenheit = Celsius(0.0).into();     // free Into
Rule

Implement From. Never implement Into directly — the blanket impl impl<T, U: From<T>> Into<U> for T does it for you.

Why this matters enormously: From is the backbone of error handling. When ? meets differing error types, Rust automatically calls From::from to convert. Custom error types work precisely because of From impls.

Iterator — the biggest payoff

One method, seventy free
impl Iterator for Counter {
    type Item = u32;                       // associated type — Part 10

    fn next(&mut self) -> Option<Self::Item> {
        if self.count < self.max {
            self.count += 1;
            Some(self.count)
        } else { None }
    }
}

// Now all of this works, for free:
let total: u32 = counter.filter(|x| x % 2 == 0).sum();
for n in counter { ... }
PART 07

Static dispatch and monomorphization

Understand what generics compile to, and Part 8 explains itself.

What you write
fn print_it<T: Display>(x: T) { println!("{}", x); }

print_it(42);
print_it("hello");
print_it(3.14);
What the compiler generates
fn print_it_i32(x: i32)   { println!("{}", x); }
fn print_it_str(x: &str)  { println!("{}", x); }
fn print_it_f64(x: f64)   { println!("{}", x); }

Three separate functions, each call site rewritten to call the right one. This is monomorphization — turning one polymorphic form into many concrete forms.

PropertyEffect
SpeedZero runtime cost. Direct calls, fully inlinable.
Binary sizeGrows with each concrete type used ("code bloat")
Compile timeSlower — more code to generate
ResolutionCompile time. The function is known statically.
This is Rust's zero-cost abstraction promise: generic code runs exactly as fast as hand-written concrete code.
The limitation

Because each T becomes a distinct function on a distinct type, let shapes: Vec<impl Shape> is impossible. A Vec<T> needs every element the same type with the same size. That wall is what trait objects break through.

PART 08

Trait objects and dynamic dispatch

Impossible
let shapes = vec![
    Circle { radius: 1.0 },
    Rectangle { w: 2.0, h: 3.0 },
];
// error[E0308]: mismatched types
Works
let shapes: Vec<Box<dyn Shape>> = vec![
    Box::new(Circle { radius: 1.0 }),
    Box::new(Rectangle { w: 2.0, h: 3.0 }),
];

Read Box<dyn Shape> as "a heap-allocated something that implements Shape".

Why Box is required

dyn Shape is unsized — a Circle might be 8 bytes, a Rectangle 16. Rust needs a known size for variables and vector elements, so you put it behind a pointer, and the pointer has a known size. Any pointer works: &dyn, Box<dyn>, Rc<dyn>, Arc<dyn>.

How it works — the fat pointer

Box<dyn Shape>
┌──────────────┬──────────────┐
│ data pointer │ vtable ptr   │      two words, not one
└──────┬───────┴──────┬───────┘
       │              │
       ▼              ▼
   ┌────────┐    ┌─────────────────────┐
   │ Circle │    │ vtable: Circle:Shape│
   │ r: 5.0 │    ├─────────────────────┤
   └────────┘    │ area()    → 0x1A40  │
                 │ name()    → 0x1A80  │
                 │ summary() → 0x1AC0  │
                 │ drop()    → 0x1B00  │
                 │ size, align         │
                 └─────────────────────┘

Calling s.area() looks the address up in the vtable at runtime, then jumps. That is dynamic dispatch — the decision happens while running, not while compiling.

Static <T: Trait>Dynamic dyn Trait
Dispatch decidedCompile timeRuntime (vtable lookup)
SpeedFastest — inlinableSlight overhead
Binary sizeLarger — copy per typeSmaller — one copy
Mixed collectionsImpossibleThe whole point
Requires pointerNoYes — Box/&/Rc
Compile timeSlowerFaster
Object safetyNot requiredRequired
Which to use

Default to static dispatch. Reach for dyn when: you need a heterogeneous collection; the concrete type is unknown until runtime (plugins, config-driven); monomorphization is bloating the binary; or you store callbacks of differing types (Vec<Box<dyn Fn()>>).

The overhead is a few nanoseconds per call. Do not contort your design to avoid it.

Object safety

Not every trait can become a trait object. The rules:

  • Methods must take self, &self, or &mut self
  • No methods returning Self — the caller could not know the size
  • No generic methods — would need a vtable slot per possible T
  • No associated constants
error[E0038]: the trait `Bad` cannot be made into an object
  = note: method `clone_me` references the `Self` type in its return type

Through a Box<dyn Bad> the concrete type is erased — only a vtable pointer remains. Returning Self would mean returning an unknown-sized value, and the caller has no way to know how much stack to reserve.

Escape hatch

Mark the offending method where Self: Sized to exclude it from the vtable. The rest of the trait stays object-safe.

PART 09

Generic structs with trait bounds

Bounds work on impl blocks, not just functions. This unlocks conditional implementation.

Two impl blocks, different availability
impl<T> Pair<T> {                              // for ALL T
    fn new(x: T, y: T) -> Self { Pair { x, y } }
}

impl<T: Display + PartialOrd> Pair<T> {       // only when T qualifies
    fn cmp_display(&self) { ... }
}

Pair<i32> gets both. Pair<SomeUnprintableType> gets only new — and calling cmp_display on it is a compile error naming the missing bound.

The std library does this everywhere

Vec<T> always has .push(). It only has .sort() when T: Ord, only .dedup() when T: PartialEq, only .to_vec() when T: Clone. That is why .sort() "sometimes does not exist" — the element type does not satisfy the bound.

Traits can be implemented conditionally too. Wrapper<T> is Display exactly when T is — which composes: Wrapper<Wrapper<i32>> prints [[5]].

PART 10

Associated types

Generic parameter
trait Container<T> {
    fn get(&self, i: usize)
        -> Option<&T>;
}
Associated type
trait Container {
    type Item;
    fn get(&self, i: usize)
        -> Option<&Self::Item>;
}

Both work. The difference is how many times a type can implement the trait.

With a generic parameter, a type can implement it many times — Container<i32> and Container<String> for the same type. Now my_box.get(0) is ambiguous; you would write Container::<i32>::get(&my_box, 0) everywhere.

With an associated type, a type implements it once. The implementor fixes Item, and my_box.get(0) is unambiguous.

The rule of thumb

Associated type — when each implementing type has exactly one natural choice. Iterator::Item: a Counter yields u32, period.

Generic parameter — when a type genuinely should implement the trait several ways. From<T>: a type converts from many sources, all useful.

That is the whole distinction, and it explains std's choices exactly.

Pinning an associated type
fn sum_all<I: Iterator<Item = u32>>(iter: I) -> u32 {
    iter.sum()
}
// "an iterator whose Item is specifically u32"
PART 11

Supertraits

Display is a supertrait of Loggable
trait Loggable: Display {
    fn log(&self) {
        println!("[LOG] {}", self);   // can use Display — guaranteed
    }
}

Read trait Loggable: Display as "anything Loggable must also be Display". In exchange, Loggable's methods may rely on Display. That is the trade: demand more from implementors, get more to work with in your defaults.

OOP inheritanceRust supertraits
Child inherits parent's fieldsNo fields — traits hold no data
Child inherits implementationsYou must implement the supertrait yourself
Creates an "is-a" type relationshipOnly a "requires" constraint
Diamond problemCompose freely — no diamond problem
Rust has no struct inheritance at all. Composition plus traits is the entire story.

The standard library encodes real mathematical structure this way: trait Ord: Eq + PartialOrd, and trait Eq: PartialEq. Total ordering requires total equality requires partial equality.

PART 12

Blanket implementations

One impl, every Display type
impl<T: Display> Loggable for T {      // note: `for T`, not a concrete type
    fn log(&self) { println!("[LOG] {}", self); }
}

42.log();                    // all of these now work,
"hello".log();               // including types from other crates,
3.14.log();                  // including types not yet written

The std blanket impls you use daily

You implementYou get freeBecause of
Display.to_string()impl<T: Display> ToString for T

The extension trait pattern

Very common in real Rust — add methods to foreign types:

Adding methods to str
trait StringExt { fn shout(&self) -> String; }

impl StringExt for str {
    fn shout(&self) -> String { format!("{}!!!", self.to_uppercase()) }
}

"hello".shout();   // you just added a method to a std library type

Legal because you own StringExt, even though you do not own str. Part 13 explains exactly why that matters.

The downside — name collisions

Blanket impls are broad, so they can collide with ordinary impls. If a type is Display and you have both an ordinary Loggable impl for it and a blanket Loggable impl over all Display types, a plain e.log() becomes ambiguous:

error[E0034]: multiple applicable items in scope
  note: candidate #1 is defined in an impl of the trait `Loggable11`
  note: candidate #2 is defined in an impl of the trait `Loggable12`

Fix with fully qualified syntax: Loggable11::log(&e), or the most explicit <Event as Loggable11>::log(&e). Better: give extension-trait methods distinctive names so you never collide.

PART 13

The orphan rule

You may implement a trait for a type only if you own the trait, or you own the type — or both.
Three legal, one not
impl MyTrait for MyStruct { }     // OK  — your trait, your type
impl MyTrait for Vec<i32> { }     // OK  — your trait, foreign type
impl Display for MyStruct { }     // OK  — foreign trait, your type
impl Display for Vec<i32> { }     // NO  — both are foreign

Why it exists

Suppose crate A and crate B both write impl Display for Vec<i32>, differently, and your program depends on both. Which impl runs? There is no answer. The orphan rule makes that impossible: a given (trait, type) pair has at most one impl in the entire program. This property is called coherence.

The workaround — newtype

Wrap it, then it is yours
struct Wrapper(Vec<String>);          // Wrapper is MY type

impl fmt::Display for Wrapper {          // now legal
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "[{}]", self.0.join(", "))
    }
}

Zero runtime cost — a single-field tuple struct compiles away entirely. The downside is that Wrapper lacks Vec's methods; implement Deref to see through to the inner value.

Newtypes are also for type safety

Meters(f64) and Feet(f64) both wrap f64, but the compiler refuses to let you mix them. A whole class of unit-confusion bugs becomes a compile error.

PART 14

Operator overloading

Operators are traits in std::ops. Implement the trait, get the operator — a + b is literally sugar for Add::add(a, b).

Implementing +
use std::ops::Add;

impl Add for Point {
    type Output = Point;              // associated type: what + evaluates to

    fn add(self, other: Point) -> Point {
        Point { x: self.x + other.x, y: self.y + other.y }
    }
}

Adding different types

Add has a generic parameter defaulting to Self: trait Add<Rhs = Self>. So impl Mul<f64> for Meters lets you multiply a Meters by a plain number.

A caution

Overload only when the meaning is obvious. Point + Point is clear. User + User is not — write a named method. A surprising operator is worse than a verbose method call.

PART 15

Real-world — a notification system

The shape below — one trait, several channel implementations, a registry holding them as trait objects — appears constantly in real Rust: loggers, payment gateways, storage backends.

The trait: required methods plus composed default
trait Notifier {
    // REQUIRED — every channel supplies these
    fn recipient(&self) -> String;
    fn send_raw(&self, message: &str) -> Result<(), String>;

    // DEFAULT — overridable fallback
    fn channel_name(&self) -> String { String::from("generic") }

    // DEFAULT — the real logic, written ONCE, composed from the above
    fn notify(&self, message: &str) -> Result<(), String> {
        println!("[{}] -> {}", self.channel_name(), self.recipient());
        self.send_raw(message)
    }
}
Each channel: own validation, own failure modes
impl Notifier for Sms {
    fn recipient(&self) -> String { self.phone.clone() }
    fn channel_name(&self) -> String { String::from("SMS") }

    fn send_raw(&self, message: &str) -> Result<(), String> {
        if message.len() > 160 {
            return Err(String::from("SMS too long (max 160)"));
        }
        println!("    {}", message);
        Ok(())
    }
}
The registry — dynamic dispatch over a mixed fleet
struct NotificationCenter { channels: Vec<Box<dyn Notifier>> }

impl NotificationCenter {
    fn add(&mut self, n: Box<dyn Notifier>) -> &mut Self {
        self.channels.push(n);
        self                       // returning &mut Self enables chaining
    }

    fn broadcast(&self, message: &str) -> BroadcastReport {
        for channel in &self.channels {
            match channel.notify(message) {   // vtable picks the right impl
                Ok(()) => report.sent += 1,
                Err(e) => { report.failed += 1; report.errors.push(e); }
            }
        }
        report
    }
}

// usage — method chaining across different concrete types
center.add(Box::new(email))
      .add(Box::new(sms))
      .add(Box::new(slack));

This one example uses: required and default methods, overriding defaults, static dispatch (send_urgent<N: Notifier>), dynamic dispatch (the Vec<Box<dyn>>), a Display impl for the report, ? inside fmt, and method chaining.

PART 16

Common errors and how to read them

Rust's errors are unusually good. Read them fully — the help: line usually contains the literal fix.

E0599 — method not found

error[E0599]: no method named `hello` found for struct `Dog`
  = help: items from traits can only be used if the trait is in scope

Cause: you imported the type but not the trait. Fix: use path::to::Trait;

E0277 — trait bound not satisfied

error[E0277]: `T` doesn't implement `std::fmt::Display`
  help: consider restricting type parameter `T`
    | fn print_it<T: std::fmt::Display>(x: T)

Cause: you used a capability you never required. Fix: add the bound the compiler suggests.

E0038 — not object safe

error[E0038]: the trait `Bad` cannot be made into an object
  = note: method `clone_me` references the `Self` type in its return type

Fix: remove the method, or add where Self: Sized to exclude it from the vtable.

E0117 — orphan rule

error[E0117]: only traits defined in the current crate can be
              implemented for types defined outside of the crate
  = note: define and implement a trait or new type instead

Fix: wrap the foreign type in a newtype.

E0204 — Copy on a heap-owning type

error[E0204]: the trait `Copy` cannot be implemented for this type
 |  s: String,
 |  --------- this field does not implement `Copy`

Fix: derive Clone only. Bitwise-copying heap ownership would double-free.

E0782 — bare trait object

error[E0782]: expected a type, found a trait
  help: add `dyn` keyword before this trait

Fix: Box<dyn Shape>. In Rust 2021+, dyn is mandatory.

E0034 — ambiguous method

error[E0034]: multiple applicable items in scope

Cause: two traits give the same type a method with the same name — usually a blanket impl colliding with an ordinary one. Fix: fully qualified syntax, Trait::method(&value).

PART 17

Decision guide

Trait or enum?

Use a trait whenUse an enum when
Open set — others add types laterClosed set — you know all variants
Behavior varies and data variesData varies, behavior centralized
Library users must extend itAll cases live in your codebase
Adding a type should be easyAdding an operation should be easy
The expression problem

Traits make adding new types easy; enums make adding new operations easy. You cannot have both cheaply — pick based on which axis will actually change. If your shapes are Circle/Rectangle/Square forever, an enum plus match is simpler and faster. If users of your crate should add Triangle without touching your source, use a trait.

impl Trait or dyn Trait?

Do you need a heterogeneous collection? │ ├── YES ──→ dyn Trait (Box<dyn T> / &dyn T / Rc<dyn T>) │ └── NO ───→ Is the concrete type known at compile time? │ ├── YES ──→ impl Trait / <T: Trait> ← default choice │ └── NO ───→ dyn Trait

Required or default method?

Can the trait implement it using only other trait methods? │ ├── YES ──→ default method (free for every implementor) │ └── NO ───→ required method (each type must supply it)

Associated type or generic parameter?

Should one type implement this trait in multiple ways? │ ├── YES ──→ generic parameter: trait Foo<T> (like From<T>) │ └── NO ───→ associated type: trait Foo { type T; } (like Iterator)

Derive or hand-write?

Does the obvious field-by-field behavior do what you want? │ ├── YES ──→ #[derive(...)] │ └── NO ───→ write the impl by hand (e.g. compare users by id only)

Your correctness checks

A 3-4-5 triangle must have area exactly 6.00. A circle of r=3 combined with r=4 must give exactly r=5, since 9 + 16 = 25. A matrix times the identity must return itself unchanged. If those three hold, your implementation is right.

Summary cheat sheet

A trait is a contract of behavior.
Defining
trait Name {
    fn required(&self);              // implementor MUST write it
    fn defaulted(&self) { ... }      // free, overridable
}
trait Name: Supertrait { ... }        // requires another trait
trait Name { type Item; }             // associated type
trait Name<T> { ... }                // generic parameter
Implementing
impl Trait for Type { ... }           // basic
impl<T: Bound> Trait for T { ... }    // BLANKET — every matching type
impl<T: Bound> Type<T> { ... }       // CONDITIONAL methods
#[derive(Debug, Clone, ...)]          // compiler writes it
Using as parameters
fn f(x: &impl Trait)                // STATIC  — sugar
fn f<T: Trait>(x: &T)              // STATIC  — general
fn f<T>(x: &T) where T: Trait     // STATIC  — readable
fn f(x: &dyn Trait)                 // DYNAMIC — vtable
Vec<Box<dyn Trait>>                  // DYNAMIC — mixed collection

The ten rules

  1. The trait must be in scope (use) to call its methods. [E0599]
  2. Orphan rule: you must own the trait or the type. [E0117]
  3. Object safety is required for dyn. [E0038]
  4. Generics → monomorphization → zero runtime cost.
  5. dyn → vtable → tiny runtime cost, much more flexibility.
  6. Default methods cannot access struct fields — use accessors.
  7. Implement From, get Into free. Never implement Into.
  8. Implement Display, get .to_string() free.
  9. dyn is mandatory in Rust 2021+. Bare Box<Trait> is an error.
  10. PartialOrd/Ord derive lexicographically — field order matters.
