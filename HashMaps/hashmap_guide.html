HashMap & HashSet:
lookup by key, not position

A vector answers "what is at index 3?". A map answers "what is stored under this key?" — and answers it in constant time, no matter how much is in there. A set is the same machinery with the values thrown away.

17 parts Companion: hashmap_practice.html Edition 2021 Verified on rustc 1.96
PART 01

The mental model — why maps exist

The problem with vectors

You know vectors now. Say you want to store exam scores by student name. With a vector your options are grim:

The vector approach falls apart
// Two parallel vectors, kept in sync by hand and by hope.
let names  = vec!["ada", "ravi", "meera"];
let scores = vec![90, 78, 88];

// To find Ravi's score you must SCAN:
let mut ravi = 0;
for (i, n) in names.iter().enumerate() {
    if *n == "ravi" { ravi = scores[i]; }
}
// O(n). And if the vectors ever fall out of sync, every
// lookup silently returns the WRONG person's score.

Two separate problems there. The scan is slow — a million students means a million comparisons. And the pairing is a convention you enforce by hand, not a guarantee the compiler checks.

A HashMap stores key–value pairs together and finds any value by its key in constant time — however large the map gets.
The same thing with a map
use std::collections::HashMap;

let mut scores = HashMap::new();
scores.insert("ada", 90);
scores.insert("ravi", 78);
scores.insert("meera", 88);

scores.get("ravi");   // Some(&78) — one step, no scan
The import

HashMap is not in the prelude — you must write use std::collections::HashMap;. Vec and String are imported automatically; HashMap is not. Forgetting this is the single most common first error with maps.

How the constant time works

You do not need this to use maps, but it explains every rule that follows. A hash function turns your key into a number, and that number decides which "bucket" the pair lives in.

insert("ravi", 78)

  "ravi"  ──hash──→  8favc9e2…  ──mod n──→  bucket 3
                                                │
   ┌────┬────┬────┬──────────────┬────┬────┐   │
   │ 0  │ 1  │ 2  │ 3  ("ravi",78)│ 4  │ 5  │ ←─┘
   └────┴────┴────┴──────────────┴────┴────┘

get("ravi")

  "ravi"  ──hash──→  8favc9e2…  ──mod n──→  bucket 3  → found

  The SAME key always hashes to the SAME bucket. So lookup
  goes straight there — it never scans the other buckets.

This is why lookup is O(1): the key itself computes the location. It is also why keys must be hashable and comparable — see Part 13.

Vec<T>HashMap<K, V>
Find by positionO(1) — v[3]Not possible
Find by value/keyO(n) — must scanO(1) — hashes straight to it
OrderKept, exactly as insertedNone — arbitrary
DuplicatesAllowedKeys are unique; inserting again replaces
Use whenSequence, order mattersLookup by name/id

And HashSet?

A HashSet<T> is a HashMap<T, ()> with the values discarded. It answers exactly one question — is this thing present? — in constant time, and it automatically refuses duplicates.

HashMap<K, V>    keys → values     "what is stored under this key?"
HashSet<T>       keys only         "have I seen this before?"

Everything you learn about HashMap keys applies to HashSet
elements unchanged. It is genuinely the same machinery.

Verified: both are 48 bytes on a 64-bit machine, because they are the same structure underneath.

If you know other languages

Python dict / set. Java HashMap / HashSet. JavaScript Map / Set. C++ unordered_map / unordered_set. Same idea everywhere; Rust's differences are ownership and the entry API, which are Parts 5 and 7.

PART 02

Creating a map

Four ways
use std::collections::HashMap;

// 1. Empty, then fill. Needs `mut`.
let mut scores: HashMap<String, i32> = HashMap::new();
scores.insert("ada".to_string(), 90);

// 2. From an array of pairs — the most readable literal form.
let m = HashMap::from([
    ("ada", 90),
    ("ravi", 78),
]);

// 3. Collected from an iterator of pairs.
let names = vec!["x", "y", "z"];
let vals  = vec![10, 20, 30];
let zipped: HashMap<_, _> = names.iter().zip(vals.iter()).collect();

// 4. Pre-sized, when you know roughly how many pairs are coming.
let mut big: HashMap<i32, i32> = HashMap::with_capacity(1000);
Type annotations

Same rule as Vec. HashMap::new() alone is ambiguous — the compiler needs to learn K and V from somewhere. If a later insert pins them down, you can drop the annotation. If nothing does, you get E0282: type annotations needed.

There is no hashmap! macro in the standard library, which surprises people coming from other languages. HashMap::from([...]) is the closest thing and is what you should reach for.

PART 03

Reading values

Exactly the same safety choice you learned with vectors: a method that returns Option, and an indexing form that panics.

.get() — the safe read
let scores = HashMap::from([("ada", 90), ("ravi", 78)]);

scores.get("ada");    // Some(&90)
scores.get("nope");   // None      — no panic, ever

// Handle both cases:
match scores.get("ravi") {
    Some(s) => println!("ravi scored {s}"),
    None    => println!("no record for ravi"),
}

// Or supply a default:
let s = scores.get("nope").copied().unwrap_or(0);   // 0
Indexing — panics on a missing key
let scores = HashMap::from([("ada", 90)]);
let v = scores["zz"];   // PANIC
thread 'main' panicked at src/main.rs:5:14:
no entry found for key
The rule

Prefer .get(). Index with map[key] only when a missing key would mean your program is broken — a configuration value you set yourself two lines earlier, for instance. If the key comes from user input, a file, or a network, .get() is the only defensible choice.

Asymmetry worth noting

Unlike Vec, a HashMap has no IndexMut. You can read map["a"] but you cannot write map["a"] = 5. Use .insert() or the entry API instead. This trips up people arriving from Python.

Other reads

All safe on an empty map
scores.contains_key("ada")   // true / false
scores.len()                  // number of pairs
scores.is_empty()             // clearer than len() == 0
scores.get_mut("ada")        // Option<&mut V> — to modify in place

// get_mut in use:
if let Some(s) = scores.get_mut("ada") {
    *s += 5;      // note the * — s is &mut i32
}
PART 04

Insert, update, remove

insert returns the old value

This is easy to miss and genuinely useful. insert hands back an Option<V>: Some(old) if the key was already present, None if it is new.

Verified output
let mut scores = HashMap::new();

let a = scores.insert("ada", 90);   // None      — brand new key
let b = scores.insert("ada", 95);   // Some(90)  — replaced, old value returned

// The map now holds ada → 95. There is no duplicate.
Keys are unique

Inserting an existing key overwrites silently. There is no error and no warning. If you meant "only insert if absent", use .entry(k).or_insert(v) from Part 5.

Removing

remove also returns what it removed
let mut m = HashMap::from([("a", 1), ("b", 2)]);

m.remove("a");       // Some(1)  — removed and handed back
m.remove("a");       // None     — already gone, no panic

m.clear();           // empty it entirely

Bulk update and filter

values_mut and retain
// Multiply every value by 10
let mut m = HashMap::from([("a", 1), ("b", 2)]);
for v in m.values_mut() {
    *v *= 10;      // a → 10, b → 20
}

// Keep only the pairs you want — same name and meaning as Vec::retain
let mut squares: HashMap<i32, i32> = (1..=6).map(|i| (i, i * i)).collect();
squares.retain(|k, _| k % 2 == 0);
// keys left: [2, 4, 6]

The closure passed to retain receives both the key and the value (|k, v|), so you can filter on either. Use _ for whichever you do not need.

PART 05

The entry API — the most important thing here

If you remember one thing from this guide, make it this part. entry is what makes Rust maps pleasant, and beginners consistently write clumsy code because they have not met it yet.

The problem it solves

"Look up this key. If it is missing, put a default there. Then modify whatever is now there." Written by hand, that is ugly and does the lookup twice:

By hand — two lookups
if !m.contains_key(k) {
    m.insert(k, 0);
}
let v = m.get_mut(k).unwrap();
*v += 1;
With entry — one lookup
*m.entry(k).or_insert(0) += 1;
entry(key) returns a handle to that slot in the map — occupied or vacant — and lets you decide what happens in each case, hashing the key only once.

Reading that one-liner

*m.entry(k).or_insert(0) += 1;
│ │         │              │
│ │         │              └── add 1 to whatever is now there
│ │         └── if the slot is EMPTY, put 0 in it.
│ │             Either way, hand back &mut V pointing at the slot.
│ └── get a handle on the slot for key `k`
└── dereference the &mut V so we can do arithmetic on the value

The leading * catches everyone once. or_insert gives you a mutable reference; the star reaches through it to the number.

The four entry methods

MethodIf key is missingReturns
.or_insert(v)Inserts v&mut V
.or_insert_with(f)Inserts f()&mut V
.or_default()Inserts V::default()&mut V
.and_modify(f)Does nothingthe entry, for chaining
All four, with verified results
// or_insert — the default value is built even if unused
*counts.entry("a").or_insert(0) += 1;

// or_insert_with — LAZY. The closure runs only when actually needed.
// Use this whenever the default is expensive to build (like a Vec).
groups.entry(key).or_insert_with(Vec::new).push(item);

// or_default — uses the type's Default impl. 0 for numbers,
// empty for Vec/String. Shortest form when the default is the obvious one.
let mut d: HashMap<&str, i32> = HashMap::new();
*d.entry("k").or_default() += 5;      // k → 5

// and_modify + or_insert — different behaviour for present vs absent
let mut am: HashMap<&str, i32> = HashMap::new();
am.entry("a").and_modify(|v| *v += 1).or_insert(100);  // absent → 100
am.entry("a").and_modify(|v| *v += 1).or_insert(100);  // present → 101
or_insert vs or_insert_with

or_insert(Vec::new()) constructs an empty Vec every single call, then throws it away when the key already exists. or_insert_with(Vec::new) only calls it when genuinely needed. For cheap values like 0 the difference is nil; for allocations it matters. Note there are no () after Vec::new — you are passing the function itself, not calling it.

PART 06

Counting and grouping — the two patterns you will actually use

These two shapes cover an enormous fraction of real map usage. Learn them as units.

Pattern 1: counting occurrences

Character frequency — verified output
use std::collections::HashMap;

let text = "hello world";
let mut counts: HashMap<char, i32> = HashMap::new();

for c in text.chars().filter(|c| !c.is_whitespace()) {
    *counts.entry(c).or_insert(0) += 1;
}

// sorted for display: [('d',1), ('e',1), ('h',1), ('l',3),
//                     ('o',2), ('r',1), ('w',1)]

Word frequency is the same three lines with .split_whitespace() in place of .chars(). Once you see the shape, you will reach for it constantly.

Pattern 2: grouping into buckets

Group words by first letter — verified output
let words = vec!["apple", "avocado", "banana", "blueberry", "cherry"];
let mut by_letter: HashMap<char, Vec<&str>> = HashMap::new();

for w in &words {
    let first = w.chars().next().unwrap();
    by_letter.entry(first).or_insert_with(Vec::new).push(w);
}

// 'a' → ["apple", "avocado"]
// 'b' → ["banana", "blueberry"]
// 'c' → ["cherry"]
Memorise these two lines

Count: *map.entry(k).or_insert(0) += 1;
Group: map.entry(k).or_insert_with(Vec::new).push(v);

You met the grouping line in the vectors guide. It is the same idiom — worth knowing cold.

Finding the most frequent

max_by_key over the pairs
let most = counts
    .iter()
    .max_by_key(|(_, &count)| count);
// Some(('l', 3))

// CAREFUL: on ties, which one wins is arbitrary — the map has
// no order, so "the maximum" is only well-defined if it is unique.
PART 07

Keys and ownership

A map owns its keys and values. That has consequences you will meet immediately.

Inserting moves the key
let mut m: HashMap<String, i32> = HashMap::new();
let k = String::from("a");
m.insert(k, 1);
println!("{}", k);   // ← k was moved into the map
error[E0382]: borrow of moved value: `k`
 --> src/main.rs:6:20
  |
4 |     let k = String::from("a");
  |         - move occurs because `k` has type `String`,
  |           which does not implement the `Copy` trait
5 |     m.insert(k, 1);
  |              - value moved here
6 |     println!("{}", k);
  |                    ^ value borrowed here after move
  |
help: consider cloning the value if the performance cost is acceptable
  |
5 |     m.insert(k.clone(), 1);
  |               ++++++++

The map must own the key, because it has to keep it alive for as long as the entry exists. Three ways forward:

Fixes
// 1. Clone if you need to keep your own copy
m.insert(k.clone(), 1);
println!("{}", k);          // ✓ k is still yours

// 2. Use the key AFTER inserting, via the map
m.insert(k, 1);
println!("{:?}", m.keys());   // ✓ read it back out

// 3. Best when possible — use &str keys, which are Copy
let mut m: HashMap<&str, i32> = HashMap::new();
m.insert("a", 1);
println!("{}", "a");        // ✓ no ownership problem at all

String keys, &str lookups

A pleasant asymmetry: even when the map owns String keys, you can look up with a plain &str. No allocation needed to ask a question.

This just works
let mut m: HashMap<String, i32> = HashMap::new();
m.insert(String::from("ada"), 90);

m.get("ada");                    // ✓ &str, no String::from needed
m.contains_key("ada");           // ✓ same

// Insert still needs an owned String — that one is unavoidable.
m.insert("ravi".to_string(), 78);
Why that works

get is generic over any Q where String: Borrow<Q>. Since String borrows as str, a &str is accepted. This is your traits topic quietly saving you an allocation on every lookup.

Choosing a key type

Use String keys when the map must outlive the source data or owns its content. Use &str keys when everything lives in the same scope and you want zero copying — but the map is then tied to that data's lifetime.

PART 08

Maps and the borrow checker

The same rule you met with vectors, in a new costume.

Holding a reference while inserting
let mut m: HashMap<&str, Vec<i32>> = HashMap::new();
m.insert("a", vec![1]);

let v = m.get("a").unwrap();   // borrow the map
m.insert("b", vec![2]);        // modify the map
println!("{:?}", v);            // use the borrow
error[E0502]: cannot borrow `m` as mutable because it is also
              borrowed as immutable
 --> src/main.rs:6:5
  |
5 |     let v = m.get("a").unwrap();
  |             - immutable borrow occurs here
6 |     m.insert("b", vec![2]);
  |     ^^^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
7 |     println!("{:?}", v);
  |                      - immutable borrow later used here

The reason is the same as with Vec: inserting can force the map to rehash and reallocate, moving every entry to a new location. Any reference you held would dangle.

Fixes
// 1. Finish with the borrow first (borrows end at last use)
let v = m.get("a").unwrap();
println!("{:?}", v);        // last use — borrow over
m.insert("b", vec![2]);    // ✓ fine now

// 2. Clone what you need out of the map
let v = m.get("a").cloned().unwrap();
m.insert("b", vec![2]);    // ✓ v owns its own data

// 3. For a "read then write same key" cycle, use entry — it
//    holds exactly one borrow for the whole operation.
m.entry("a").or_insert_with(Vec::new).push(9);
A hidden benefit of entry

Fix 3 is why the entry API exists. "Check if present, then insert or modify" is exactly the shape that trips the borrow checker when written by hand — and exactly what entry does in a single borrow. If you are fighting E0502 around a map, entry is usually the answer.

PART 09

Iterating a map

The three iterators, plus keys and values
let mut m = HashMap::from([("a", 1), ("b", 2)]);

// Pairs, by reference. Note the (k, v) tuple destructuring.
for (k, v) in &m {
    println!("{k} = {v}");     // k: &&str, v: &i32
}

// Values mutably
for (k, v) in &mut m {
    *v *= 10;                  // keys are NOT mutable — only values
}

// Consuming — the map is gone afterwards
for (k, v) in m {
    // k: &str, v: i32 — both owned
}

// Just one side:
m.keys()         // iterator of &K
m.values()       // iterator of &V
m.values_mut()   // iterator of &mut V
Keys are immutable

Even with &mut m, you get (&K, &mut V) — the key is read-only. Changing a key would change its hash, putting it in the wrong bucket and corrupting the map. To "rename" a key you must remove and re-insert.

Maps and iterator adapters

Same adapters you know from vectors
let scores = HashMap::from([("ada", 90), ("ravi", 78), ("meera", 88)]);

// Sum of all values
let total: i32 = scores.values().sum();          // 256

// Everyone above 80 — filter on the pair, then take the key
let mut top: Vec<&str> = scores
    .iter()
    .filter(|(_, &v)| v > 80)
    .map(|(k, _)| *k)
    .collect();
top.sort();                                    // ["ada", "meera"]

// Build a NEW map from an old one
let doubled: HashMap<&str, i32> = scores
    .iter()
    .map(|(k, v)| (*k, v * 2))
    .collect();

Notice the sort() on the filtered result. That is not decoration — it is the subject of the next part.

PART 10

Iteration order is arbitrary — and that is deliberate

A HashMap has no order. Not "insertion order", not "sorted order" — no order at all. Do not rely on it, ever.
Do not do this
let m = HashMap::from([("one", 1), ("two", 2), ("three", 3)]);

for (k, v) in &m {
    println!("{k}");   // order differs between runs of the SAME binary
}

Rust goes further than most languages here: it seeds each map with a random hash key at startup, so the order genuinely changes from run to run. This is a security measure — it prevents an attacker from crafting inputs that all collide into one bucket and degrade your map to O(n). It also stops you accidentally depending on an order that was never guaranteed.

If you need order, sort explicitly
// Sorted keys
let mut keys: Vec<_> = m.keys().collect();
keys.sort();
// ["one", "three", "two"]

// Sorted pairs
let mut pairs: Vec<_> = m.iter().collect();
pairs.sort();                       // sorts by key, then value

// Sorted by VALUE, descending — a leaderboard
let mut board: Vec<_> = m.iter().collect();
board.sort_by(|a, b| b.1.cmp(a.1));  // .1 is the value
The habit

Any time you print a map, or compare map output in a test, sort first. Tests that pass locally and fail in CI are very often an unsorted map iteration.

If you find yourself sorting the same map on every use, you want BTreeMap instead — see Part 14.

PART 11

HashSet basics

Everything you now know transfers. A set is a map with no values — it answers "is this present?" and nothing else.

The core operations
use std::collections::HashSet;

let mut s: HashSet<i32> = HashSet::new();

s.insert(1);        // true  — it was newly added
s.insert(1);        // false — already there, set unchanged
s.insert(2);

s.contains(&2);    // true   — note the &
s.remove(&1);      // true   — it was present and is now gone
s.len();           // 1
insert returns a bool — use it

set.insert(x) returns true only if x was not already present. That gives you duplicate detection for free:

if !seen.insert(item) {
    println!("duplicate: {item}");
}

Building a set

Usually from an iterator
// From an array
let a: HashSet<i32> = [1, 2, 3, 4].into_iter().collect();

// From a Vec — this is THE way to deduplicate
let dup = vec![3, 1, 3, 2, 1];
let uniq: HashSet<_> = dup.iter().copied().collect();
let mut out: Vec<_> = uniq.into_iter().collect();
out.sort();      // [1, 2, 3]
Two ways to deduplicate

You now know both. vec.sort() + vec.dedup() keeps sorted order and needs Ord. A HashSet needs Hash + Eq, destroys order, and is O(n) rather than O(n log n). Use the set when order does not matter; use sort+dedup when it does.

PART 12

Set operations

This is where sets earn their place. Four operations, all reading like the mathematics they come from.

All four — verified output
let a: HashSet<i32> = [1, 2, 3, 4].into_iter().collect();
let b: HashSet<i32> = [3, 4, 5, 6].into_iter().collect();

a.intersection(&b)           // [3, 4]        in BOTH
a.union(&b)                  // [1,2,3,4,5,6] in EITHER
a.difference(&b)             // [1, 2]        in a but NOT b
a.symmetric_difference(&b)   // [1, 2, 5, 6]  in exactly ONE

// These return ITERATORS, so collect to use them:
let mut both: Vec<i32> = a.intersection(&b).copied().collect();
both.sort();   // [3, 4]
       a = {1,2,3,4}          b = {3,4,5,6}

        ┌───────────┬───────────┬───────────┐
        │   1, 2    │   3, 4    │   5, 6    │
        │  only a   │   both    │  only b   │
        └───────────┴───────────┴───────────┘

  intersection          ▓▓▓▓▓▓▓▓▓▓▓              {3,4}
  union            ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓       {1,2,3,4,5,6}
  difference(a-b)  ▓▓▓▓▓▓▓▓▓▓▓                   {1,2}
  symmetric_diff   ▓▓▓▓▓▓▓▓▓▓▓            ▓▓▓▓   {1,2,5,6}

Difference is directional: a.difference(&b) is not b.difference(&a). The other three are symmetric.

Relationship tests

These return bool directly
let small: HashSet<i32> = [1, 2].into_iter().collect();

small.is_subset(&a);      // true  — every element of small is in a
a.is_superset(&small);   // true  — the same fact, other way round
a.is_disjoint(&other);   // true  — they share nothing
Where this pays off

Permissions: required.is_subset(&granted). Tags: post_tags.intersection(&filter_tags). Diffing two lists of ids: old.difference(&new) gives deletions, new.difference(&old) gives additions. Each is one line and reads as the question you were actually asking.

PART 13

Custom key types

You will eventually want your own struct as a key. Try it naively and the compiler stops you:

A struct is not automatically a valid key
#[derive(Debug)]
struct Point { x: i32, y: i32 }

let mut m: HashMap<Point, i32> = HashMap::new();
m.insert(Point { x: 1, y: 2 }, 5);
error[E0599]: the method `insert` exists for struct
              `HashMap<Point, i32>`, but its trait bounds were not satisfied
  |
3 | struct Point { x: i32, y: i32 }
  | ------------ doesn't satisfy `Point: Eq` or `Point: Hash`
  |
  = note: the following trait bounds were not satisfied:
          `Point: Eq`
          `Point: Hash`
help: consider annotating `Point` with `#[derive(Eq, Hash, PartialEq)]`
The fix is in the error message
#[derive(Debug, PartialEq, Eq, Hash)]
struct Point { x: i32, y: i32 }

let mut m: HashMap<Point, i32> = HashMap::new();
m.insert(Point { x: 1, y: 2 }, 5);   // ✓ compiles

Why those two traits, specifically

TraitAnswersNeeded because
Hash"What bucket?"Without it there is no way to place or find the key
Eq"Same key?"Two keys can share a bucket; equality settles which is which
The contract between them

If a == b, then hash(a) must equal hash(b). #[derive] guarantees this automatically. If you ever hand-write Hash and break the rule, your map silently loses entries — it looks in one bucket while the key sits in another. Derive unless you have a strong reason not to.

Why floats cannot be keys

HashSet<f64> will not work
let mut s: HashSet<f64> = HashSet::new();
s.insert(1.0);
error[E0599]: the method `insert` exists for struct `HashSet<f64>`,
              but its trait bounds were not satisfied
  = note: the following trait bounds were not satisfied:
          `f64: Eq`
          `f64: Hash`

The same NaN problem you met when sorting floats. NaN != NaN, so f64 implements only PartialEq, never Eq — and a key you cannot reliably compare is a key you cannot reliably find. Use an integer key instead: cents rather than f64 rupees, or round to a fixed precision.

Which types work as keys out of the box

All integers, char, bool, String, &str, and tuples/arrays/Vecs of those. Not f32/f64. Your own types work as soon as you add #[derive(PartialEq, Eq, Hash)] — provided every field is itself hashable.

PART 14

BTreeMap and BTreeSet — the ordered alternatives

Same interface, one crucial difference: they stay sorted by key, always.

Ordered iteration, for free
use std::collections::{BTreeMap, BTreeSet};

let bt = BTreeMap::from([("b", 2), ("a", 1), ("c", 3)]);
// iterating gives [("a", 1), ("b", 2), ("c", 3)] — sorted,
// regardless of the order they went in

let bs: BTreeSet<i32> = [3, 1, 2].into_iter().collect();
// {1, 2, 3}

Do you need the keys in sorted order? ├─ No ────────────────────────→ HashMap / HashSet ← the default └─ Yes ├─ Just for printing once? → HashMap, then sort() └─ Constantly, or you need ranges / min / max ─────→ BTreeMap / BTreeSet
Default to HashMap

Reach for HashMap unless you have a specific reason to want order. It is faster and it is what other Rust programmers expect. Switch to BTreeMap when you need sorted iteration, range queries, or the smallest/largest key — and the switch is nearly free, since the API is almost identical.

PART 15

Real-world patterns

An inventory system

Everything in this guide, working together
use std::collections::HashMap;

#[derive(Debug, Clone)]
struct Item {
    name:  String,
    qty:   u32,
    price: f64,
}

struct Inventory {
    items: HashMap<String, Item>,   // keyed by SKU
}

impl Inventory {
    fn new() -> Self {
        Inventory { items: HashMap::new() }
    }

    // Add stock, creating the entry if this SKU is new
    fn add(&mut self, sku: &str, name: &str, qty: u32, price: f64) {
        self.items
            .entry(sku.to_string())
            .and_modify(|i| i.qty += qty)
            .or_insert(Item {
                name: name.to_string(),
                qty,
                price,
            });
    }

    // Take stock out, refusing if there is not enough
    fn take(&mut self, sku: &str, qty: u32) -> bool {
        match self.items.get_mut(sku) {
            Some(i) if i.qty >= qty => { i.qty -= qty; true }
            _ => false,
        }
    }

    // Total value of everything held
    fn total_value(&self) -> f64 {
        self.items.values().map(|i| i.qty as f64 * i.price).sum()
    }

    // Anything running low — sorted, because map order is arbitrary
    fn low_stock(&self, threshold: u32) -> Vec<&str> {
        let mut low: Vec<&str> = self.items
            .iter()
            .filter(|(_, i)| i.qty < threshold)
            .map(|(sku, _)| sku.as_str())
            .collect();
        low.sort();
        low
    }
}
Worth noticing

and_modify().or_insert() in add handles both "new SKU" and "restock" in one expression. The match guard in take — Some(i) if i.qty >= qty — rejects insufficient stock without a nested if. And low_stock sorts before returning, because map order cannot be trusted.

Caching / memoisation

Compute once, reuse forever
fn expensive(n: u64, cache: &mut HashMap<u64, u64>) -> u64 {
    if let Some(&hit) = cache.get(&n) {
        return hit;                 // already computed
    }
    let result = /* the slow work */ n * n;
    cache.insert(n, result);
    result
}

Deduplicating while preserving order

HashSet as a "seen" tracker
use std::collections::HashSet;

fn dedup_keep_order(items: &[&str]) -> Vec<String> {
    let mut seen = HashSet::new();
    items
        .iter()
        .filter(|s| seen.insert(s.to_string()))  // true only the FIRST time
        .map(|s| s.to_string())
        .collect()
}
// ["a", "b", "a", "c"] -> ["a", "b", "c"]  — first occurrences, in order

This is a genuinely elegant use of insert's return value: filter keeps an item exactly when the set had not seen it, and the set records it in the same step. Collecting into a HashSet would lose the order; this keeps it.

PART 16

Common errors

All real compiler output. Recognise them by shape and they stop being obstacles.

Forgetting the import

error[E0433]: failed to resolve: use of undeclared type `HashMap`
help: consider importing this struct:
      use std::collections::HashMap;

Fix: add use std::collections::HashMap; at the top. The single most common map error.

E0599 — key type is not hashable

error[E0599]: the method `insert` exists for struct `HashMap<Point, i32>`,
              but its trait bounds were not satisfied
  = note: `Point: Eq` and `Point: Hash` not satisfied

Fix: #[derive(PartialEq, Eq, Hash)] on the key type. If the key is f64, you cannot — use an integer instead. See Part 13.

E0382 — key moved into the map

error[E0382]: borrow of moved value: `k`
  = move occurs because `k` has type `String`,
    which does not implement the `Copy` trait

Fix: m.insert(k.clone(), v), or use &str keys, or simply stop using k afterwards. See Part 7.

E0502 — borrow conflict

error[E0502]: cannot borrow `m` as mutable because it is also
              borrowed as immutable

Fix: finish with the reference first, clone the value out, or restructure using entry. See Part 8.

Runtime panic — missing key

thread 'main' panicked at src/main.rs:5:14:
no entry found for key

Fix: use .get(k) and handle the None rather than indexing with m[k]. Compiles fine, fails at runtime — the dangerous kind.

Cannot assign through an index

error[E0594]: cannot assign to data in an index of `HashMap`
  = help: trait `IndexMut` is required to modify indexed content,
          but it is not implemented for `HashMap`

Fix: m.insert(k, v) or *m.entry(k).or_insert(0) = v. Unlike Vec, maps deliberately have no IndexMut.

Read the help lines

Every error above names its own fix — the exact derive to add, the exact import, the exact .clone(). rustc --explain E0599 gives the full explanation. Reading past the first red line is the highest-value habit you can build.

The six things to remember

1. use std::collections::HashMap; — it is not in the prelude 2. .get() returns Option; m[k] panics on a missing key 3. *m.entry(k).or_insert(0) += 1 — the counting idiom 4. .or_insert_with(Vec::new).push(v) — the grouping idiom 5. Iteration order is arbitrary and randomised — sort before printing 6. Custom keys need #[derive(PartialEq, Eq, Hash)]; floats can never be keys
A map trades order for speed. Everything you must remember — the random iteration, the hashable-key requirement, the entry API — is the price of finding any value in one step.
