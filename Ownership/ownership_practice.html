How to use this workbook

  1. Write your attempt before opening the solution.
  2. Compile and run: rustc --edition 2021 practice.rs && ./practice
  3. When the borrow checker rejects you, read the "later used here" line first — that is usually where the fix goes, not where the error points.
  4. If your instinct is .clone(), pause and ask whether & would do. Sometimes it would not, and that is fine — but check.
SET 01

Moves and copies

Which assignments kill the original, and which do not.

1.1easy Keep both alive

Task

Make let s1 = String::from("hello"); let s2 = s1; compile with both names still usable afterwards. Do not change the types.

Solution
Answer — verified
let s1 = String::from("hello");
let s2 = s1.clone();
println!("{s1} {s2}");   // → hello hello
Why

String is not Copy, so plain assignment moves. .clone() makes a second independent allocation, so there are genuinely two owners and both can be freed safely.

1.2easy Predict: does this compile?

Task

Before running: does let a = 5; let b = a; println!("{a} {b}"); compile? Say why, in terms of one trait.

Compiles?

Solution
Yes — verified output a=5 b=5
let a = 5;
let b = a;        // copy, not move — i32 implements Copy
println!("{a} {b}");
The test

i32 lives entirely on the stack. No heap allocation means nothing to double-free, so invalidating a would buy nothing. That is exactly the rule: if the value owns heap memory, it is not Copy.

1.3easy Give and take back

Task

Write fn takes_and_returns(v: Vec<i32>) -> (Vec<i32>, usize) that reports the length and hands the vector back. (This is the clumsy pattern borrowing replaces — write it once to feel why.)

Solution
Answer — verified [1, 2, 3] len=3
fn takes_and_returns(v: Vec<i32>) -> (Vec<i32>, usize) {
    let n = v.len();
    (v, n)
}
Do not ship this

It works, but every caller has to write let (v, n) = takes_and_returns(v); just to keep their own vector. fn len_of(v: &[i32]) -> usize is the real answer — see set 2.

1.4easy Measure the handle

Task

Print size_of::<String>(). Predict the number first, and say what the three parts are.

Bytes, and the three fields

Solution
Answer — verified 24
println!("{}", std::mem::size_of::<String>());   // 24
// ptr (8) + len (8) + cap (8) = 24 bytes on the stack.
// The characters themselves live on the heap.
1.5medium Move through a function

Task

Write fn identity(s: String) -> String that takes ownership and returns it unchanged. Then explain: how many allocations happen when you call it?

Solution
Answer — verified moved
fn identity(s: String) -> String { s }
Zero allocations

Ownership moves in and straight back out. Only the 24-byte handle is copied — twice — and the heap buffer is never touched. Moves are free.

1.6medium Count without consuming

Task

Write a function that counts items in a list of Strings without taking ownership. Pick the most flexible parameter type you can.

Solution
Answer — verified 2
fn count(items: &[String]) -> usize { items.len() }
Why &[String] and not &Vec<String>

A slice parameter accepts vectors, arrays, and sub-ranges. &Vec<String> accepts only vectors, for no benefit at all.

SET 02

Borrowing basics

Reading with &, writing with &mut, and the dereference operator.

2.1easy Length by borrow

Task

Rewrite exercise 1.3 as a borrow: a function that returns the length and leaves the caller's value untouched.

Solution
Answer — verified 5
fn length_of(s: &String) -> usize { s.len() }

No tuple, no giving-back. The next exercise improves it further.

2.2easy Accept both kinds of string

Task

Change 2.1 so it accepts both &String and a plain "literal". One character changes.

Solution
Answer — verified 7 5
fn length_of(s: &str) -> usize { s.len() }

length_of("literal");              // 7
length_of(&String::from("owned"));  // 5
The rule

&String auto-converts to &str, but not the reverse. So &str is strictly more flexible — always prefer it in parameters.

2.3easy Increment through a reference

Task

Write fn bump(n: &mut i32) that adds one. Then call it twice on the same variable.

Solution
Answer — verified 11 from a start of 10
fn bump(n: &mut i32) { *n += 1; }

let mut n = 10;
bump(&mut n);
Three muts

let mut n (the value may change), &mut n (lending it mutably here), n: &mut i32 (this function demands a mutable loan). Miss any one and it will not compile.

2.4easy Push through a mutable borrow

Task

Write fn add(v: &mut Vec<i32>, x: i32). Why is &mut Vec right here, when set 1 said to prefer slices?

Solution
Answer — verified [1, 2, 3]
fn add(v: &mut Vec<i32>, x: i32) { v.push(x); }
When &mut Vec beats &mut [T]

A slice has a fixed length — you can change elements through it, but you cannot grow it. push needs the vector itself. Prefer slices for reading; take &mut Vec when you must resize.

2.5easy Append to a string in place

Task

Write fn append(s: &mut String, suffix: &str). Note the asymmetry in the two parameter types and be able to justify it.

Solution
Answer — verified hi there
fn append(s: &mut String, suffix: &str) {
    s.push_str(suffix);
}
The asymmetry is the point

We modify the first, so it must be &mut String. We only read the second, so &str — which lets callers pass a literal without allocating.

2.6easy Sum a slice

Task

Write fn total(v: &[i32]) -> i32, then call it on both a whole vector and a sub-range of it.

Solution
Answer — verified 10
fn total(v: &[i32]) -> i32 { v.iter().sum() }

total(&v);        // whole vector
total(&v[1..4]);  // a window into it — no copying
2.7medium Return a borrow

Task

Write a function returning the first element of a slice as Option<&i32>. Why can this return a reference safely, when dangle() in the guide could not?

Solution
Answer — verified Some(7)
fn first(v: &[i32]) -> Option<&i32> { v.first() }
The difference

The returned reference borrows from the argument, which the caller still owns. dangle() tried to return a borrow of a local that was about to be dropped — there was nothing for it to borrow from.

2.8medium Double every element in place

Task

Write fn double_all(v: &mut [i32]) that doubles each element. You will need iter_mut() and a dereference.

Solution
Answer — verified: [1, 2, 3] → [2, 4, 6]
fn double_all(v: &mut [i32]) {
    for x in v.iter_mut() { *x *= 2; }
}
Why the *

iter_mut() yields &mut i32, not i32. Assigning through a reference needs an explicit dereference — this is the main place you still have to write * yourself.

SET 03

Fixing real borrow errors

Each of these is broken. Read the error, then fix it — preferring the cheapest fix that expresses your intent.

3.1easy The accidental consumer

Task

This function eats its argument for no reason. Fix the signature.

Broken
fn count(v: Vec<String>) -> usize { v.len() }
Solution
Answer — verified 1
fn count(v: &[String]) -> usize { v.len() }
The compiler told you

This is the exact case behind the note "consider changing this parameter type … to borrow instead if owning the value isn't necessary." If the body only reads, take a borrow.

3.2medium E0502 — shorten the borrow

Task

Make this compile without cloning and without removing the push.

Broken — E0502
let mut v = vec![1, 2, 3];
let first = &v[0];
v.push(4);
println!("{first}");
Solution
Answer — verified [1, 2, 3, 4]
let mut v = vec![1, 2, 3];
let first = v[0];      // copy the i32 out — no live borrow
v.push(4);
println!("{first}");
Why this works

i32 is Copy, so dropping the & copies the value out instead of borrowing the buffer. With no live borrow, push is free to reallocate. For a non-Copy element you would print before pushing instead.

3.3medium The loop that ate the vector

Task

Collect the length of every name, keeping the original vector usable afterwards.

Broken — E0382
for n in names { /* ... */ }
println!("{names:?}");
Solution
Answer — verified [2, 3]
fn lengths(names: &[String]) -> Vec<usize> {
    names.iter().map(|n| n.len()).collect()
}
One character

for n in names calls into_iter() and moves. &names or .iter() borrows instead. The compiler even suggests the & for you.

3.4medium Let NLL do the work

Task

Read from a string via a reference, then mutate it — in one function, no blocks, no clones.

Solution
Answer — verified ab
let mut s = String::from("a");
let r = &s;
let n = r.len();   // last use of r — borrow ends here
s.push('b');       // now legal
Non-lexical lifetimes

The borrow dies at its last use, not at the end of the block. Order your reads before your writes and most E0502s evaporate.

3.5medium Read then append

Task

Write fn duplicate_first(v: &mut Vec<i32>) that appends a copy of the first element. Watch the borrow overlap.

Solution
Answer — verified: [5, 6] → [5, 6, 5]
fn duplicate_first(v: &mut Vec<i32>) {
    let first = v[0];   // copy out first, ending the read
    v.push(first);      // then mutate
}
The trap

v.push(v[0]) looks natural and does not compile: the argument borrows v while push already holds it mutably. Split it into two statements.

3.6medium Counting with the entry API

Task

Write fn bump(m: &mut HashMap<String,i32>, k: &str) that increments a counter, inserting 0 first if absent. Only allocate a String when you must.

Solution
Answer — verified Some(2) after two calls
fn bump(m: &mut HashMap<String, i32>, k: &str) {
    *m.entry(k.to_string()).or_insert(0) += 1;
}
Ownership note

The map owns its keys, so entry needs an owned String — hence to_string(). Lookups (get, contains_key) take &str and allocate nothing.

3.7medium Longest, without cloning

Task

Return the longest string in a slice as a borrow, not a clone.

Solution
Answer — verified Some("longest")
fn longest(v: &[String]) -> Option<&String> {
    v.iter().max_by_key(|s| s.len())
}
Zero allocations

The whole chain moves borrows around and allocates nothing. Returning Option<&String> instead of Option<String> is what makes that possible.

3.8hard Two mutable borrows that are legal

Task

Mutate the first and third elements of a 4-element vector through two simultaneous mutable references. E0499 says you cannot — find the method that makes it legal.

Solution
Answer — verified (10, 20)
let mut d = vec![1, 2, 3, 4];
let (l, r) = d.split_at_mut(2);
l[0] = 10;
r[0] = 20;
// d is now [10, 2, 20, 4]
The real rule

The restriction is on overlapping regions, not on names. split_at_mut proves to the compiler that the two halves are disjoint, so two live &mut into one vector are fine.

SET 04

Slices and string views

Borrowing a window into data somebody else owns.

4.1easy First word

Task

Return the first word of a sentence as a &str — no allocation. Handle the no-space case.

Solution
Answer — verified the
fn first_word(s: &str) -> &str {
    s.split(' ').next().unwrap_or(s)
}
4.2easy Last word

Task

Same, but the last word. Use rfind and slice from there.

Solution
Answer — verified brown
fn last_word(s: &str) -> &str {
    match s.rfind(' ') {
        Some(i) => &s[i+1..],
        None => s,
    }
}
4.3medium Trim the ends

Task

Return a slice with the first and last elements removed. Short inputs must not panic.

Solution
Answer — verified [2, 3, 4] from [1..5]
fn middle(v: &[i32]) -> &[i32] {
    if v.len() <= 2 { v } else { &v[1..v.len()-1] }
}
Guard first

Without the length check, a 1-element slice computes &v[1..0] and panics. Slice ranges are checked at runtime, not by the borrow checker.

4.4easy Reverse a string

Task

Reverse a &str. This one must allocate — explain why a slice cannot do it.

Solution
Answer — verified olleh
fn reverse(s: &str) -> String {
    s.chars().rev().collect()
}
Why owned

A slice can only be a window onto existing bytes. The reversed characters do not exist anywhere in the input, so they need new storage — return String.

4.5easy Take at most n

Task

Return the first n elements as a slice, never panicking when n is too large.

Solution
Answer — verified [1, 2, 3]
fn take(v: &[i32], n: usize) -> &[i32] {
    &v[..n.min(v.len())]
}
4.6hard Palindrome check

Task

Ignoring punctuation and case, is the input a palindrome? Test with "A man, a plan, a canal: Panama".

Solution
Answer — verified true and false
fn is_palindrome(s: &str) -> bool {
    let c: String = s.chars()
        .filter(|c| c.is_alphanumeric())
        .collect::<String>()
        .to_lowercase();
    c == c.chars().rev().collect::<String>()
}
Two allocations, both needed

One for the cleaned string, one for its reverse. You could avoid the second by comparing iterators from both ends — worth trying once you have met DoubleEndedIterator.

4.7easy Join borrowed pieces

Task

Join &["a","b","c"] into "a-b-c". Note where ownership is created.

Solution
Answer — verified a-b-c
fn join(words: &[&str]) -> String {
    words.join("-")
}

Borrowed slices in, one fresh String out — the standard shape for a function that builds something new.

SET 05

Structs and methods

The three self forms, and choosing between them.

Used throughout this set
#[derive(Debug, Clone, PartialEq)]
struct Task { title: String, done: bool, priority: u8 }
5.1easy A constructor that borrows

Task

Write Task::new(title: &str, priority: u8) -> Self. Why &str rather than String?

Solution
Answer
fn new(title: &str, priority: u8) -> Self {
    Task { title: title.to_string(), done: false, priority }
}
Who pays for the allocation

Either way one String gets allocated. With &str, callers can pass a literal directly; with String, they must build one first even when they have a literal in hand.

5.2easy A getter that does not clone

Task

Write title() returning the title without allocating.

Solution
Answer — verified write guide
fn title(&self) -> &str { &self.title }
The common mistake

fn title(&self) -> String { self.title.clone() } allocates on every call. Return &str and let the caller clone only if they need to.

5.3easy Mutate in place

Task

Write complete() which sets done = true. Which self form?

Solution
Answer — verified done=true
fn complete(&mut self) { self.done = true; }

The caller keeps their Task and sees the change. Anything else would force them to reassign.

5.4medium Consume into a field

Task

Write a method that returns the owned title and destroys the task. Name it by convention.

Solution
Answer — verified write guide
fn into_title(self) -> String { self.title }
Why no clone

Taking self by value means we own the whole struct, so the String can simply move out. The rest of the struct is dropped. The into_ prefix warns callers at the call site.

5.5easy A predicate method

Task

is_urgent() — true when priority is 8 or above.

Solution
Answer — verified true for priority 9
fn is_urgent(&self) -> bool { self.priority >= 8 }
5.6medium Filter to borrows

Task

From &[Task], return every unfinished task — without cloning any of them.

Solution
Answer — verified ["second"]
fn pending(tasks: &[Task]) -> Vec<&Task> {
    tasks.iter().filter(|t| !t.done).collect()
}
The return type carries the decision

Vec<&Task> is a vector of borrows — cheap, and tied to the input's lifetime. Vec<Task> would force a clone per match.

5.7medium Consume a whole vector

Task

Turn Vec<Task> into Vec<String> of titles, with no cloning at all.

Solution
Answer — verified ["write guide", "second"]
fn titles(tasks: Vec<Task>) -> Vec<String> {
    tasks.into_iter().map(|t| t.title).collect()
}
Why into_iter matters

Taking the vector by value lets into_iter() yield owned Tasks, so t.title moves out. With .iter() you would get &Task and be forced to clone every title.

SET 06

Collections and ownership

Own on insert, borrow on read — and what it takes to get something back out.

6.1easy Push an owned value

Task

Write fn add(v: &mut Vec<String>, s: String). Why must the second parameter be owned?

Solution
Answer — verified ["a", "b"]
fn add(v: &mut Vec<String>, s: String) { v.push(s); }
Storage requires ownership

The vector will outlive this call, so it cannot hold a borrow of something that might die first. Anything you store you must own.

6.2medium Take one back out

Task

Remove the element at index i and return it as an owned String, or None if out of range.

Solution
Answer — verified Some("a"), rest ["b"]
fn take_at(v: &mut Vec<String>, i: usize) -> Option<String> {
    if i < v.len() { Some(v.remove(i)) } else { None }
}
This is the answer to E0507

let s = v[0]; cannot move out of an index. remove can, because it also shrinks the vector — no gap is left behind. swap_remove is the O(1) version if order does not matter.

6.3medium Group into a map

Task

Write a function appending a value to HashMap<String, Vec<String>>, creating the vector if the key is new.

Solution
Answer — verified Some(["apple", "pear"])
fn group(m: &mut HashMap<String, Vec<String>>, k: &str, val: &str) {
    m.entry(k.to_string())
     .or_insert_with(Vec::new)
     .push(val.to_string());
}
Why or_insert_with

or_insert(Vec::new()) builds a vector on every call, even when the key exists. or_insert_with takes a closure and only calls it when needed.

6.4medium Sorted borrowed keys

Task

Return a map's keys in sorted order, without cloning them.

Solution
Answer — verified ["a", "b"]
fn sorted_keys(m: &HashMap<String, i32>) -> Vec<&String> {
    let mut k: Vec<&String> = m.keys().collect();
    k.sort();
    k
}
Sorting borrows

You are sorting a vector of references. The map is untouched and nothing is allocated but the small vector of pointers. This is also how you get deterministic output from a HashMap, whose iteration order is deliberately arbitrary.

6.5easy Deliberate deep copy

Task

Given &[String], produce an owned Vec<String> the caller can keep independently.

Solution
Answer — verified ["x"]
fn owned_copy(v: &[String]) -> Vec<String> {
    v.to_vec()
}
A legitimate clone

to_vec() clones every element. Here that is exactly right — the caller asked for an independent copy. Cloning is only a smell when it is silencing an error you did not understand.

6.6medium Consume into a map

Task

Turn Vec<i32> into HashMap<i32, i32> mapping each value to its square, consuming the vector.

Solution
Answer — verified [(2, 4), (3, 9)]
fn squares(v: Vec<i32>) -> HashMap<i32, i32> {
    v.into_iter().map(|x| (x, x*x)).collect()
}
SET 07

Designing signatures

The judgement calls. For each one, decide before you write: read it, change it, or take it?

7.1easy Two reads, one owned result

Task

Format a config name and a count into a summary string. Choose the cheapest parameter types.

Solution
Answer — verified cfg x3
fn summary(config: &str, count: usize) -> String {
    format!("{config} x{count}")
}

Borrow what you read, pass Copy scalars by value, return the thing you built. The default shape.

7.2easy Append into a caller's buffer

Task

Write write_line, which appends a line plus a newline to a buffer the caller owns. Why is this better than returning a new String each time?

Solution
Answer — verified "line1\nline2\n"
fn write_line(buf: &mut String, line: &str) {
    buf.push_str(line);
    buf.push('\n');
}
Reusing the allocation

Returning a fresh String per line means one allocation per line. Appending into a caller's buffer reuses capacity — the standard pattern for building output in a loop.

7.3medium Statistics without consuming

Task

Return (done, pending) counts from &[Task]. The caller must still own their tasks afterwards.

Solution
Answer — verified (1, 1)
fn stats(items: &[Task]) -> (usize, usize) {
    let done = items.iter().filter(|t| t.done).count();
    (done, items.len() - done)
}
7.4hard Partition by consuming

Task

Consume Vec<Task> into HashMap<bool, Vec<String>> — titles grouped by done-ness, no clones anywhere.

Solution
Answer — verified done=Some(["a"]) pending=Some(["b"])
fn partition(items: Vec<Task>) -> HashMap<bool, Vec<String>> {
    let mut m: HashMap<bool, Vec<String>> = HashMap::new();
    for t in items {                // moves each Task out
        m.entry(t.done)
         .or_insert_with(Vec::new)
         .push(t.title);          // the String moves — no clone
    }
    m
}
Why the moving for is right here

This is the one place the consuming loop from the guide's Part 08 is exactly what you want. We own items, we are dismantling it, and each t.title moves straight into the map. Borrowing here would force a clone per task.

7.5medium Choose the signature

Task

No code — decide. For each, write &T, &mut T, or T:

a) a function that logs a user's name

b) a function that stores a user in a database struct

c) a function that marks a user as verified

d) a function that returns a user's initials

Solution
Answers
// a) &User      — only reads
// b) User       — stores it, so must own it
// c) &mut User  — changes it, caller keeps it
// d) &User      — reads; returns a fresh String
The question to ask

"What does this function need to do with the value?" Read → &T. Change → &mut T. Keep → T. Only (b) genuinely needs ownership.

7.6hard Spot the unnecessary clone

Task

Three clones below. Which are unnecessary, and what replaces them?

Review this
fn report(tasks: &Vec<Task>) -> String {
    let all = tasks.clone();                       // 1
    let first = all[0].title.clone();              // 2
    let names: Vec<String> =
        all.iter().map(|t| t.title.clone()).collect();  // 3
    format!("{first}: {}", names.len())
}
Solution
All three go
fn report(tasks: &[Task]) -> String {
    let first = &tasks[0].title;   // borrow, do not clone
    format!("{first}: {}", tasks.len())
}
What each one cost

1 cloned every task including every title — the worst. 2 cloned a string only to read it. 3 built an entire vector of strings just to call .len() on it. The parameter also becomes &[Task] for flexibility.

7.7hard When a clone is right

Task

Write a function that returns a task's title uppercased, leaving the original untouched. Justify the allocation.

Solution
Answer
fn shout_title(t: &Task) -> String {
    t.title.to_uppercase()
}
Unavoidable, therefore fine

The uppercased text does not exist anywhere yet, so it needs new storage. This is not a clone-to-silence-the-borrow-checker — it is a genuinely new value. Note we still take &Task: only the result is owned.

FINAL

Capstone: a document buffer

Every method below is an ownership decision. Build it one part at a time — the signature is most of the exercise.

Given
#[derive(Debug, Clone, PartialEq)]
struct Line {
    text: String,
    tags: Vec<String>,
}

struct Document {
    title: String,
    lines: Vec<Line>,
}
C.1medium Construct and fill

Task

new(title: &str) and push_line(&mut self, text: String). Explain why the two string parameters differ.

Solution
Answer — verified title=Notes lines=3
fn new(title: &str) -> Self {
    Document { title: title.to_string(), lines: Vec::new() }
}

fn push_line(&mut self, text: String) {
    self.lines.push(Line { text, tags: Vec::new() });
}
The difference

new is called once, so &str plus one to_string() is friendliest. push_line is called in a loop and stores what it receives, so taking String lets a caller who already owns one hand it over with no allocation at all.

C.2medium Read and edit

Task

line(&self, i) -> Option<&str> and edit_line(&mut self, i, new_text: &str) -> bool. Neither may allocate a new Line.

Solution
Answer — verified Some("ownership is about who frees") and None for index 9
fn line(&self, i: usize) -> Option<&str> {
    self.lines.get(i).map(|l| l.text.as_str())
}

fn edit_line(&mut self, i: usize, new_text: &str) -> bool {
    match self.lines.get_mut(i) {
        Some(l) => { l.text.clear(); l.text.push_str(new_text); true }
        None => false,
    }
}
get and get_mut

Indexing with [i] panics out of range. get/get_mut return Option, which is why both methods can report failure instead of crashing. Reusing the existing String via clear + push_str also keeps its allocated capacity.

C.3medium Tag a line

Task

tag_line(&mut self, i, tag: &str) -> bool, ignoring duplicate tags.

Solution
Answer — verified ["core"] after tagging twice
fn tag_line(&mut self, i: usize, tag: &str) -> bool {
    match self.lines.get_mut(i) {
        Some(l) => {
            if !l.tags.iter().any(|t| t == tag) {
                l.tags.push(tag.to_string());
            }
            true
        }
        None => false,
    }
}
Allocate only on success

tag.to_string() sits inside the if, so a duplicate tag costs nothing. Comparing t == tag works because String compares directly against &str.

C.4hard Query without cloning

Task

lines_with_tag(&self, tag) -> Vec<&str> and word_count(&self) -> usize. No allocations except the result vector.

Solution
Answer — verified core lines = 2, word count = 18
fn lines_with_tag(&self, tag: &str) -> Vec<&str> {
    self.lines.iter()
        .filter(|l| l.tags.iter().any(|t| t == tag))
        .map(|l| l.text.as_str())
        .collect()
}

fn word_count(&self) -> usize {
    self.lines.iter()
        .map(|l| l.text.split_whitespace().count())
        .sum()
}
Borrows all the way down

The returned Vec<&str> holds views into the document's own buffers. The document stays fully intact and untouched, and only the small pointer vector is allocated.

C.5medium Give a line back

Task

remove_line(&mut self, i) -> Option<String> — the caller ends up owning the removed text.

fn remove_line(&mut self, i: usize) -> Option<String> {
    if i < self.lines.len() {
        Some(self.lines.remove(i).text)
    } else {

    }

A move out of a temporary

remove(i) hands back an owned Line. Since we own that temporary, .text moves straight out of it and the discarded tags vector is dropped. No clone required.

fn into_tag_index(self) -> HashMap<String, Vec<String>> {
    let mut idx: HashMap<String, Vec<String>> = HashMap::new();
    for line in self.lines {          // moves each Line out
        for tag in line.tags {         // moves each tag String
            idx.entry(tag)
               .or_insert_with(Vec::new)
               .push(line.text.clone());   // ← the necessary clone
        }
    }
    idx
}
Why that clone is unavoidable

A line with two tags must appear under both keys — the same text in two places. One String cannot have two owners, so the second occurrence needs its own copy. The tags themselves move (no clone), and a line with exactly one tag still pays for one clone; avoiding even that would need Rc<String>, which is a later topic.
