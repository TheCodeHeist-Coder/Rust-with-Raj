Ownership:
who frees this?

Every language answers one question about memory: when is it safe to free this? C makes you answer it by hand, and you get it wrong. Java hires a garbage collector to answer it at runtime, and you pay for the service. Rust answers it while compiling — then erases the whole apparatus from the binary.

PART 01

Why ownership exists at all

Every program that touches memory has to answer one question: when is it safe to free this? Free too early and you have a pointer to memory that now holds something else. Free twice and you corrupt the allocator. Never free and you leak.

There have historically been two answers, and both cost something real.

ApproachUsed byWhat it costs
You free it by handC, C++Use-after-free, double-free, leaks — human error, at runtime, in production
A garbage collector frees itJava, Go, Python, C#Runtime overhead, unpredictable pauses, a runtime to ship
The compiler proves whenRustYou must write code the compiler can prove
Every value has exactly one owner. When the owner goes out of scope, the value is freed.

That is the whole idea. No runtime bookkeeping, no GC thread, no free() for you to forget — because the compiler knows, at compile time, the exact point where each value dies.

The honest trade

The borrow checker will reject programs that are actually fine. That is the deal you are accepting. In exchange, an entire category of bug — the one responsible for roughly 70% of serious security vulnerabilities in large C and C++ codebases — becomes impossible to express. You argue with the compiler now instead of debugging at 3am later.

One thing worth fixing in your head immediately: ownership is not a runtime feature. It has no representation in the compiled binary. It is a set of rules the compiler checks and then throws away. The machine code Rust emits looks like what a careful C programmer would have written by hand.

PART 02

Stack and heap — the picture you must have

You cannot understand moves without this, so it comes first.

The stack is fast and rigid. Values go on and come off in order, like a stack of plates. Every value must have a size known at compile time. Pushing is just moving a pointer along.

The heap is flexible and slower. You ask the allocator for space, it finds a spot and hands back a pointer. Data can grow. Somebody has to give the space back.

A String uses both, and this split is the single most important picture in the language:

          STACK                              HEAP
    ┌─────────────────┐              ┌───┬───┬───┬───┬───┐
 s  │ ptr    ─────────┼─────────────►│ h │ e │ l │ l │ o │
    │ len    5        │              └───┴───┴───┴───┴───┘
    │ cap    5        │
    └─────────────────┘
     24 bytes, fixed,               the actual characters —
     known at compile time          size known only at runtime

A String is a 24-byte handle on the stack, pointing at bytes on the heap.

You do not have to take my word for the sizes:

Measuring the handle — verified output
println!("size_of String  = {}", std::mem::size_of::<String>());
println!("size_of &String = {}", std::mem::size_of::<&String>());
println!("size_of Vec<u8> = {}", std::mem::size_of::<Vec<u8>>());
println!("size_of i32     = {}", std::mem::size_of::<i32>());
// size_of String  = 24
// size_of &String = 8
// size_of Vec<u8> = 24
// size_of i32     = 4

Three pieces of eight bytes: pointer, length, capacity. A Vec is the same shape — not a coincidence, since a String is essentially a Vec<u8> that promises to hold valid UTF-8.

Why this matters next

When you assign a String to another variable, Rust copies the 24-byte handle — cheap. It does not copy the heap bytes. So now two handles point at the same allocation. That is precisely the problem the ownership system exists to solve, and it is what Part 04 is about.

PART 03

The three rules

Memorise these. Everything else in this guide is a consequence.

1. Each value has an owner.  ·  2. Only one owner at a time.  ·  3. When the owner goes out of scope, the value is dropped.

Rule 2 is the one that catches people arriving from other languages. In Python or Java, ten variables can happily refer to one list. In Rust one value has one owner — and if another name wants to use it, you must move ownership (Part 04), copy it (Part 05), clone it (Part 06), or borrow it (Part 09). Those four options are the entire menu.

Rule 3 is what replaces the garbage collector:

Scope is usually just a block
fn main() {
    // s does not exist yet
    {
        let s = String::from("hello");  // s is valid from here
        println!("{s}");
    }                                    // scope ends → s dropped, heap freed
    // using s here would not compile
}

There is no free(). The closing brace is the free. Rust inserts the call for you, and because the point is known at compile time, deciding when costs nothing at runtime.

Drop order runs backwards

Values drop in the opposite order they were declared — last declared, first dropped, exactly like a stack. This occasionally matters, and it is easy to demonstrate:

Verified output
struct Noisy(&'static str);
impl Drop for Noisy {
    fn drop(&mut self) { println!("dropping {}", self.0); }
}

fn main() {
    let _first  = Noisy("first");
    let _second = Noisy("second");
    let _third  = Noisy("third");
}
// dropping third
// dropping second
// dropping first

Drop is an ordinary trait — the same machinery from the traits guide. Implementing it lets you run code when a value dies, which is how Rust closes files and releases locks without finally blocks or defer.

PART 04

Move — the default for heap data

Here is the three-line program that confuses everybody once:

Does not compile
let s1 = String::from("hello");
let s2 = s1;
println!("{s1}");
error[E0382]: borrow of moved value: `s1`
 --> e1.rs:4:16
  |
2 |     let s1 = String::from("hello");
  |         -- move occurs because `s1` has type `String`, which does not implement the `Copy` trait
3 |     let s2 = s1;
  |              -- value moved here
4 |     println!("{s1}");
  |                ^^ value borrowed here after move
  |
help: consider cloning the value if the performance cost is acceptable
  |
3 |     let s2 = s1.clone();
  |                ++++++++

In most languages that middle line copies a reference and both names keep working. In Rust s1 is moved into s2, and s1 stops existing as far as the compiler is concerned.

Why not just copy the heap data?

Go back to the picture from Part 02. If Rust copied the 24-byte handle and left both variables valid, this is what you would have:

        STACK                          HEAP
  ┌────────────────┐          ┌───┬───┬───┬───┬───┐
s1│ ptr ───────────┼─────────►│ h │ e │ l │ l │ o │
  │ len 5          │     ┌───►└───┴───┴───┴───┴───┘
  └────────────────┘     │
  ┌────────────────┐     │     Both owners. Both scopes end.
s2│ ptr ───────────┼─────┘     Both call free on the same
  │ len 5          │           pointer  →  DOUBLE FREE.
  └────────────────┘

Why two owners cannot be permitted: each would free the same allocation.

Rust has three options and takes the third:

  • Copy the heap data too — safe, but silently expensive. A 4 MB string assignment quietly becoming a 4 MB memcpy is exactly the kind of hidden cost Rust refuses to have.
  • Let both free it — a double-free. Not an option.
  • Invalidate the original. Free, safe, and obvious once you see it. This is the move.

So a move costs nothing at runtime. It is a 24-byte handle copy plus a compile-time note that s1 is dead. Nothing is memcpy'd, nothing is freed, nothing happens at all.

Read the message properly

It says "move occurs because s1 has type String, which does not implement the Copy trait." That is the compiler stating the exact rule: types without Copy move; types with Copy copy. Which is which is Part 05.

PART 05

Copy types — when assignment is harmless

This works, and by now you should be able to explain why before reading on:

Verified output
let a = 5;
let b = a;
println!("a={a} b={b}");   // both usable → a=5 b=5

An i32 lives entirely on the stack. There is no allocation, so there is nothing to double-free, so there is no reason to invalidate a. Copying four bytes is as cheap as marking them dead. Types like this implement the Copy trait, and for them assignment copies rather than moves.

Copy — assignment copiesNot Copy — assignment moves
All integers — i32, u8, usize…String
f32, f64Vec<T>
bool, charHashMap, HashSet
Shared references &TMutable references &mut T
Tuples/arrays if every element is CopyAny struct you write, unless you derive it
If the value owns heap memory, it is not Copy.

(i32, i32) is Copy. (i32, String) is not, because one field owns an allocation. That single test predicts every row in the table above.

Making your own type Copy

Both usable afterwards
#[derive(Debug, Clone, Copy)]
struct Point { x: i32, y: i32 }

let p1 = Point { x: 1, y: 2 };
let p2 = p1;
println!("{p1:?} {p2:?}");

You must derive Clone alongside Copy, because Copy is a subtrait of Clone. And you can only derive it when every field is itself Copy — add a String field and the derive stops compiling, which is the compiler enforcing the rule above for you.

Not an error-silencer

Do not reach for Copy to make borrow errors go away. On a large struct it turns every assignment into a silent memcpy. Copy is for small, cheap, value-like things: coordinates, IDs, flags. If you want Copy on something big, what you actually want is a borrow — Part 09.

PART 06

Clone — the explicit deep copy

When you genuinely need two independent owned values, ask for one out loud:

Verified output
let s3 = String::from("hello");
let s4 = s3.clone();
println!("s3={s3} s4={s4}");   // → s3=hello s4=hello

.clone() allocates fresh heap space and copies the bytes into it. Now there really are two independent values with two owners, and both can be freed safely.

        STACK                          HEAP
  ┌────────────────┐          ┌───┬───┬───┬───┬───┐
s3│ ptr ───────────┼─────────►│ h │ e │ l │ l │ o │
  └────────────────┘          └───┴───┴───┴───┴───┘
  ┌────────────────┐          ┌───┬───┬───┬───┬───┐
s4│ ptr ───────────┼─────────►│ h │ e │ l │ l │ o │
  └────────────────┘          └───┴───┴───┴───┴───┘
                        two allocations, two owners, no conflict

.clone() duplicates the heap data — that is the cost you are paying.

Rust makes you write .clone() explicitly out of honesty about cost. In a language where assignment might deep-copy, you cannot tell an expensive line from a cheap one by reading it. In Rust, if you see .clone() an allocation happens; if you do not, none does.

The beginner trap

The borrow checker complains, you add .clone(), the error goes away. It works — and occasionally it is genuinely right. But if .clone() is your fix for every error, you are paying real allocations to avoid learning borrowing. The rule of thumb: clone when you need a second independent value; borrow when you just need to look at the first one.

PART 07

Functions take ownership too

Passing a value to a function moves it, by exactly the same rule as assignment:

Does not compile
fn main() {
    let s = String::from("hello");
    takes_ownership(s);
    println!("{s}");
}

fn takes_ownership(text: String) {
    println!("{text}");
}   // text dropped here — the String is freed
error[E0382]: borrow of moved value: `s`
 --> e2.rs:4:16
  |
2 |     let s = String::from("hello");
  |         - move occurs because `s` has type `String`, which does not implement the `Copy` trait
3 |     takes_ownership(s);
  |                     - value moved here
4 |     println!("{s}");
  |                ^ value borrowed here after move
  |
note: consider changing this parameter type in function `takes_ownership` to borrow instead if owning the value isn't necessary
 --> e2.rs:7:26
  |
7 | fn takes_ownership(text: String) {
  |    ---------------       ^^^^^^ this parameter takes ownership of the value
  |    |
  |    in this function

That second note is the compiler running your design review. It has noticed the function only reads text, and is telling you the parameter type is wrong. This is one of the most useful diagnostics in the language, and acting on it is Part 09.

Giving ownership back, the clumsy way

Before you know about borrowing, the only way to get a value back is to return it:

It works, and you should not write it
fn length_of(s: String) -> (String, usize) {
    let n = s.len();
    (s, n)                          // hand it back
}

let s = String::from("hello");
let (s, n) = length_of(s);         // give, and take back
println!("'{s}' has length {n}");   // → 'hello' has length 5

Borrowing exists precisely so that you never have to write this.

Returning ownership outward

A function can also create an owned value and hand it to the caller. Completely normal, and free — the value is constructed directly where the caller wants it:

The shape most functions should have
fn make_greeting(name: &str) -> String {
    format!("Hello, {name}!")     // ownership moves to the caller
}
The pattern to notice

Take &str, return String. Borrow what you only read; hand back ownership of what you create. That one line is most of good Rust API design, and Part 16 develops it into a full method.

PART 08

Where values actually die

Three things end a value's life. Being able to tell which one happened is most of debugging E0382.

CauseCodeWhat happens
Scope ends{ let s = …; }dropped at the closing brace
Moved elsewherelet b = a;a dead; b will do the dropping
Dropped by handdrop(s);freed right there, not at end of scope

std::mem::drop is not compiler magic. Its entire definition is this:

The whole function
pub fn drop<T>(_x: T) {}

It takes ownership and does nothing. The value dies at the end of drop's body, because that is where its new owner's scope ends. Ownership alone is enough to build it — no special support required.

The loop trap

This is where moves actually bite people in real code:

Does not compile
let names = vec![String::from("a"), String::from("b")];
for n in names {          // moves the whole vec
    println!("{n}");
}
println!("{names:?}");
error[E0382]: borrow of moved value: `names`
   --> e7.rs:6:16
    |
  2 |     let names = vec![String::from("a"), String::from("b")];
    |         ----- move occurs because `names` has type `Vec<String>`, which does not implement the `Copy` trait
  3 |     for n in names {
    |              ----- `names` moved due to this implicit call to `.into_iter()`
...
  6 |     println!("{names:?}");
    |                ^^^^^ value borrowed here after move
    |
note: `into_iter` takes ownership of the receiver `self`, which moves `names`
help: consider iterating over a slice of the `Vec<String>`'s content to avoid moving into the `for` loop
    |
  3 |     for n in &names {
    |              +

The compiler lays out the whole mechanism: for calls .into_iter(), which takes self by value, which moves the vector. The fix is one character — &names — and that character is a borrow. Which is finally what we turn to.

PART 09

References — borrowing without taking

A reference lets a function use a value without owning it. You make one with &:

Compare with the tuple version in Part 07
fn main() {
    let s = String::from("hello");
    let n = length_of(&s);            // lend it
    println!("'{s}' has length {n}");   // s is still ours
}

fn length_of(s: &String) -> usize {
    s.len()
}   // s goes out of scope — but it does not own, so nothing is dropped

No tuple return, no giving-and-taking-back, and s is still usable afterwards. The function borrowed it and gave it back automatically.

        STACK                                   HEAP
  ┌────────────────┐                   ┌───┬───┬───┬───┬───┐
s │ ptr ───────────┼──────────────────►│ h │ e │ l │ l │ o │
  │ len 5          │                   └───┴───┴───┴───┴───┘
  │ cap 5          │                            ▲
  └────────────────┘                            │
  ┌────────────────┐                            │
r │ ptr ───────────┼────────────────────────────┘
  └────────────────┘
    8 bytes            r points at s. s still owns the data.
                       When r dies, nothing is freed.

A reference is a pointer that explicitly does not own what it points at.

The word for this is borrowing, and the metaphor is exact: you may use a borrowed thing, you must give it back, and you may not destroy it. The owner stays responsible for cleanup.

Sharing freely

You can have as many shared references as you like, all alive at once:

Verified output
let s = String::from("hello");
let r1 = &s;
let r2 = &s;
let r3 = &s;
println!("{r1} {r2} {r3}");   // → hello hello hello

Safe, because none of them can change anything. Any number of readers is fine as long as there are no writers — which is the entire rule, stated formally in Part 11.

The real-world shape

A config object read by twenty functions should be passed as &Config to all twenty. No clones, no ownership juggling, no cost beyond passing an 8-byte pointer.

Verified output
struct Config { host: String, port: u16, retries: u8 }

fn describe(c: &Config) -> String {
    format!("{}:{} (retries={})", c.host, c.port, c.retries)
}

let cfg = Config { host: String::from("localhost"), port: 8080, retries: 3 };
println!("{}", describe(&cfg));
println!("{}", describe(&cfg));   // reusable — we only ever borrowed
println!("{}", describe(&cfg));
// localhost:8080 (retries=3)
// localhost:8080 (retries=3)
// localhost:8080 (retries=3)
PART 10

Mutable references — borrowing to change

Shared references are read-only. To modify through a borrow you need &mut, and the value itself must be declared mut:

Verified output
fn bump(c: &mut i32) {
    *c += 1;              // * to reach through the reference
}

let mut count = 0;       // must be mut
bump(&mut count);          // must say &mut at the call site too
bump(&mut count);
println!("count = {count}");   // → count = 2

Three muts in that snippet, and they are three different statements:

WhereWhat it says
let mut countthis variable's value may change
&mut countI am lending it out mutably, right here
c: &mut i32this function requires a mutable loan

The call-site &mut is deliberate. In C++ a reference parameter can modify your variable invisibly at the call site; in Rust you can always see it in the calling code.

The dereference operator

Verified output
let val = 42;
let rf = &val;
println!("*rf = {}  rf = {}  equal: {}", *rf, rf, *rf == val);
// → *rf = 42  rf = 42  equal: true

You mostly do not need it. Rust auto-dereferences for method calls and for traits like Display — that is why rf prints as 42, and why s.len() works on an &String. You need an explicit * mainly when assigning through a reference, as in *c += 1 above.

The three relationships, in one example

Verified output
#[derive(Debug)]
struct Book { title: String }

fn borrow_to_read(b: &Book) -> usize { b.title.len() }
fn annotate(b: &mut Book) { b.title.push_str(" (annotated)"); }
fn donate(b: Book) -> String { b.title }      // consumes it

let mut book = Book { title: String::from("The Rust Book") };
println!("length while borrowed: {}", borrow_to_read(&book));
annotate(&mut book);
println!("after annotate: {}", book.title);
let title = donate(book);            // book is consumed here
println!("donated, got title: {title}");
// length while borrowed: 13
// after annotate: The Rust Book (annotated)
// donated, got title: The Rust Book (annotated)

Three functions, three relationships: read it, change it, take it. That is the entire vocabulary of the language on this subject. The library-book metaphor holds all the way down — you can read a borrowed book, you can pencil notes into one you have mutable access to, and once you have donated it, it is not yours to read any more.

PART 11

The borrowing rules

At any one time: any number of &T, or exactly one &mut T. Never both. And every reference must always be valid.

Two errors enforce that first sentence. Mixing shared with mutable:

Does not compile
let mut s = String::from("hello");
let r1 = &s;
let r2 = &mut s;
println!("{r1} {r2}");
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
 --> e3.rs:4:14
  |
3 |     let r1 = &s;
  |              -- immutable borrow occurs here
4 |     let r2 = &mut s;
  |              ^^^^^^ mutable borrow occurs here
5 |     println!("{r1} {r2}");
  |                -- immutable borrow later used here

And two mutable borrows at once:

Does not compile
let mut s = String::from("hello");
let r1 = &mut s;
let r2 = &mut s;
println!("{r1} {r2}");
error[E0499]: cannot borrow `s` as mutable more than once at a time
 --> e4.rs:4:14
  |
3 |     let r1 = &mut s;
  |              ------ first mutable borrow occurs here
4 |     let r2 = &mut s;
  |              ^^^^^^ second mutable borrow occurs here
5 |     println!("{r1} {r2}");
  |                -- first borrow later used here

Notice that both messages end by pointing at the println! — "later used here." That is the key to the whole system, and Part 13 explains it: the conflict is not that two references exist, it is that both are alive at the same moment.

One sentence

Many readers, or one writer, never both. It is the rule that governs concurrent access to shared data in every language ever written — Rust just enforces it at compile time, for single-threaded code as well. Which is exactly why the same rule later makes Rust's threading safe for free.

PART 12

Why the rules exist

The rules feel arbitrary until you see what they prevent. Here are three real bugs, all caught at compile time.

Bug 1 — the invalidated pointer

This is the best example in the topic, because the danger is completely invisible in the source text:

Does not compile — and that is a rescue, not a nuisance
let mut v = vec![1, 2, 3];
let first = &v[0];      // borrow pointing into the heap buffer
v.push(4);              // may reallocate!
println!("{first}");
error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
 --> e9.rs:4:5
  |
3 |     let first = &v[0];
  |                  - immutable borrow occurs here
4 |     v.push(4);
  |     ^^^^^^^^^ mutable borrow occurs here
5 |     println!("{first}");
  |                ----- immutable borrow later used here

Why this is genuinely dangerous rather than merely pedantic: when a Vec runs out of capacity it allocates a new, larger buffer, copies the elements across, and frees the old one.

BEFORE push:                        AFTER push (reallocation):

  v ──► ┌───┬───┬───┐                 v ──► ┌───┬───┬───┬───┬───┬───┐
        │ 1 │ 2 │ 3 │  cap 3                │ 1 │ 2 │ 3 │ 4 │   │   │  cap 6
        └───┴───┴───┘                       └───┴───┴───┴───┴───┴───┘
          ▲                                   (a new address)
          │
      first                             first ──► ┌───┬───┬───┐
                                                  │ ░ │ ░ │ ░ │  FREED
                                                  └───┴───┴───┘
                                                 dangling pointer

In C++ this compiles, runs, and reads freed memory. In Rust it does not compile.

This is iterator invalidation — the exact bug behind a long line of C++ security advisories. The borrow rule catches it with no runtime check whatsoever.

Bug 2 — the data race

A data race needs three ingredients: two or more pointers to the same data, at least one of them writing, and no synchronisation. The borrowing rule makes that combination unrepresentable — if anyone holds a &mut, nobody else holds any reference at all.

The payoff, later

This is why "fearless concurrency" is not marketing. The rules you are learning now for single-threaded code are the same rules that make multithreaded Rust safe. You are not learning two systems — by the time you reach threads, you will already have done the hard part.

Bug 3 — the dangling return

Rust also refuses to let you return a reference to something about to die:

Does not compile
fn dangle() -> &String {
    let s = String::from("hello");
    &s
}   // s is dropped here — the reference would point at freed memory
error[E0106]: missing lifetime specifier
 --> e5.rs:6:16
  |
6 | fn dangle() -> &String {
  |                ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed from
help: instead, you are more likely to want to return an owned value
  |
6 - fn dangle() -> &String {
6 + fn dangle() -> String {
  |

The compiler's own suggestion is the right fix: return String, not &String. Move ownership out instead of lending something that will not survive the trip. And that phrase — "no value for it to be borrowed from" — is your first sight of lifetimes, which are a topic of their own.

PART 13

NLL — borrows end at their last use

If borrows lasted until the end of their block, Rust would be unbearable to write. They do not. A borrow ends after its last use — a rule called non-lexical lifetimes. So this compiles:

Verified output
let mut s2 = String::from("hello");
let r = &s2;
println!("r={r}");           // last use of r — the borrow ends HERE
s2.push_str(" world");      // legal: nothing borrows s2 any more
println!("s2={s2}");          // → r=hello  then  s2=hello world
let mut s2 = String::from("hello");
let r = &s2;                          ┐
println!("r={r}");                    ┘  r's borrow lives only here
s2.push_str(" world");                   ← free to mutate: no live borrows
println!("s2={s2}");

A borrow's life is its use span, not its enclosing block.

Now go back and reread the E0502 and E0499 messages in Part 11. Both ended with "borrow later used here" pointing at the println! — because that final use is exactly what kept the first borrow alive across the second one. Delete that println! and both examples compile.

A practical debugging move

When you hit E0502 or E0499, find the "later used here" line. Very often you can simply move that use earlier, shortening the borrow's span, and the error disappears with no restructuring at all.

You can also end a borrow deliberately with a block, which is sometimes the cleanest fix available:

Verified output
let mut v = vec![1, 2, 3];
{
    let m = &mut v;
    m.push(4);
    println!("via mut borrow: {m:?}");
}                                // m dies here
println!("after: {v:?}");      // v usable again
// via mut borrow: [1, 2, 3, 4]
// after: [1, 2, 3, 4]
PART 14

Slices, and why &str exists

A slice is a borrow of part of a collection. It is a pointer plus a length, and crucially it owns nothing:

Verified output
let owned: String = String::from("hello world");
let slice: &str = &owned[0..5];
println!("owned={owned} slice={slice}");
println!("size_of &str = {}", std::mem::size_of::<&str>());
// owned=hello world slice=hello
// size_of &str = 16

Sixteen bytes: a pointer and a length. That is why it is called a fat pointer — bigger than the 8-byte &String, because it has to carry how far the window extends.

  owned ──► ┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐
            │ h │ e │ l │ l │ o │   │ w │ o │ r │ l │ d │
            └───┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘
              ▲           ▲
              └───────────┘
              slice = ptr + len 5      no allocation, no copy

A slice is a window onto data that somebody else owns.

The signature rule this produces

Take &str rather than &String and your function accepts both — because &String auto-converts to &str, but not the reverse:

Verified output
fn shout(s: &str) -> String { s.to_uppercase() }

let owned = String::from("hello world");
let literal = "a literal";
println!("{} {}", shout(&owned), shout(literal));
// → HELLO WORLD A LITERAL

The same rule applies to vectors: take &[T], not &Vec<T>, and the function works on vectors, arrays and sub-ranges alike:

Verified output
fn sum(nums: &[i32]) -> i32 { nums.iter().sum() }

let v = vec![10, 20, 30, 40, 50];
println!("sum of all      = {}", sum(&v));        // → 150
println!("sum of middle 3 = {}", sum(&v[1..4]));  // → 90

Returning a slice into the input

A function can return a borrow of its own argument — safe, because the caller still owns the data:

Verified output
fn first_word(s: &str) -> &str {
    match s.find(' ') {
        Some(i) => &s[..i],
        None => s,
    }
}

let sentence = String::from("the quick brown fox");
println!("first word = {}", first_word(&sentence));   // → the

No allocation at all — the returned &str points straight into sentence's buffer. Contrast this with dangle in Part 12: that failed because there was nothing for the reference to borrow from. Here there is — the argument.

Two mutable borrows, legitimately

The one-writer rule is about overlapping regions, not about variable names. split_at_mut hands you two mutable slices over disjoint halves:

Verified output
let mut data = vec![1, 2, 3, 4];
let (left, right) = data.split_at_mut(2);
left[0] = 100;
right[0] = 200;
println!("{data:?}");   // → [100, 2, 200, 4]

Two live &mut into one vector, and it compiles — because the compiler knows they cannot overlap.

PART 15

Structs, partial moves, and collections

Moving one field out of a struct moves only that field, leaving the rest usable:

Does not compile — but only because of one line
struct User { name: String, age: u32 }

let u = User { name: String::from("Ada"), age: 36 };
let n = u.name;             // partial move
println!("{}", u.name);     // error — this field is gone
println!("{}", u.age);      // fine — this one is not
error[E0382]: borrow of moved value: `u.name`
 --> e6.rs:9:20
  |
8 |     let n = u.name;
  |             ------ value moved here
9 |     println!("{}", u.name);
  |                    ^^^^^^ value borrowed here after move
  |
  = note: move occurs because `u.name` has type `String`, which does not implement the `Copy` trait

Read the error carefully: it is about u.name, not u. The struct is partially dead. u.age still works, because u32 is Copy and was never moved.

You cannot move out of an index

Collections refuse partial moves entirely, because there is nowhere to record that one element is dead:

Does not compile
let v = vec![String::from("a"), String::from("b")];
let first = v[0];
error[E0507]: cannot move out of index of `Vec<String>`
 --> e8.rs:3:17
  |
3 |     let first = v[0];
  |                 ^^^^ move occurs because value has type `String`, which does not implement the `Copy` trait
  |
help: consider borrowing here
  |
3 |     let first = &v[0];
  |                 +
help: consider cloning the value if the performance cost is acceptable
  |
3 |     let first = v[0].clone();
  |                     ++++++++

Both suggestions are valid, and choosing between them is the real decision: &v[0] if you only need to look at it, .clone() if you need your own copy. There is a third option the compiler does not mention — v.remove(0) or v.swap_remove(0), which genuinely take the element out and adjust the vector.

Ownership moves into collections

Verified output
let mut scores: HashMap<String, u32> = HashMap::new();
let key = String::from("ada");
scores.insert(key, 10);         // key moves into the map
// println!("{key}");           // would be E0382
if let Some(v) = scores.get("ada") {   // &str lookup — nothing moves
    println!("got {v} without moving anything");
}

The collection takes ownership of what you put into it, and hands out borrows when you look things up. That asymmetry — own on insert, borrow on read — is the same shape you met in the vectors and hashmap guides. Now you know the reason for it.

PART 16

Designing signatures — the decision that matters

Everything so far has been mechanics. This part is judgement, and it is what separates fighting the borrow checker from working with it. For every parameter you write, ask one question: what does this function need to do with the value?

You need to…TakeBecause
read it&T / &str / &[T]cheapest, most flexible, caller keeps the value
modify it in place&mut Tcaller keeps it and sees the change
store it, or consume itTyou genuinely need ownership
maybe store it&T, clone insidedo not make every caller pay for the maybe
The default is &T

Take ownership only when you can say why. A function taking String that only reads it forces every caller to either give up their value or clone — a cost you imposed on them by accident. This is exactly what the compiler was hinting at in Part 07: "consider changing this parameter type … to borrow instead."

A worked example — an inventory

Every method below uses a different relationship, chosen deliberately. Read the comments as design rationale rather than description:

Each signature is a decision
#[derive(Debug, Clone, PartialEq)]
struct Product { sku: String, name: String, price: f64, qty: u32 }

struct Inventory { items: Vec<Product> }

impl Inventory {
    // TAKES OWNERSHIP: the inventory stores it, so it must own it.
    fn add(&mut self, p: Product) {
        self.items.push(p);
    }

    // BORROWS: read-only lookup, returning a borrow tied to &self.
    fn find(&self, sku: &str) -> Option<&Product> {
        self.items.iter().find(|p| p.sku == sku)
    }

    // MUTABLE BORROW: change in place, nothing moves.
    fn restock(&mut self, sku: &str, extra: u32) -> bool {
        match self.items.iter_mut().find(|p| p.sku == sku) {
            Some(p) => { p.qty += extra; true }
            None => false,
        }
    }

    // BORROWS to compute; returns an owned f64.
    fn total_value(&self) -> f64 {
        self.items.iter().map(|p| p.price * p.qty as f64).sum()
    }

    // BORROWS, and returns borrows — no cloning anywhere.
    fn low_stock(&self, threshold: u32) -> Vec<&Product> {
        self.items.iter().filter(|p| p.qty < threshold).collect()
    }

    // GIVES UP OWNERSHIP of one item: removes it and hands it over.
    fn remove(&mut self, sku: &str) -> Option<Product> {
        let idx = self.items.iter().position(|p| p.sku == sku)?;
        Some(self.items.remove(idx))
    }

    // CONSUMES self: transforms the whole thing. No clone needed —
    // we own everything, so the Strings move straight out.
    fn into_price_map(self) -> HashMap<String, f64> {
        self.items.into_iter().map(|p| (p.sku, p.price)).collect()
    }
}
Verified output
// 1. find KB-1 = Some("Keyboard")
//    find ZZ-9 = None
// 2. restock CB-3 by 20 -> true
//    restock ZZ-9       -> false
//    CB-3 qty now = Some(21)
// 3. total value = 1137.40
// 4. low stock (<5) = ["Monitor"]
// 5. removed = Some("Monitor")
//    remaining = 2
// 6. price map keys = ["CB-3", "KB-1"]
//    KB-1 price = Some(49.99)

The three self forms

Methods take self by the same three relationships, and you choose between them the same way:

FormMeaningIn the example above
&selfread the structfind, total_value, low_stock
&mut selfmodify the structadd, restock, remove

The into_ convention

A method that takes self by value conventionally starts with into_, warning you at the call site that the original is being consumed. You have already met one: into_iter(). Now you know why it is named that — and why the for loop back in Part 08 ate the whole vector.

PART 17

Every error in this guide, decoded

All six, each with a one-line diagnosis and the usual fix.

CodeSaysMeansUsual fix
E0382 borrow of moved value you used something after giving it away borrow instead (&x), or clone, or restructure
E0502 cannot borrow as mutable, also borrowed as immutable a reader is still alive when a writer starts shorten the reader's span — move its last use earlier
E0499 cannot borrow as mutable more than once two writers at the same time scope one in a block, or do the work sequentially
E0507 cannot move out of index / borrowed content taking ownership from something you only borrowed &v[0], .clone(), or .remove(i)
E0106 missing lifetime specifier returning a reference to nothing that outlives the call return an owned value instead
E0596 cannot borrow as mutable, not declared as mutable the binding is not mut add mut to the let

That last one is the friendliest error in Rust, and worth seeing once:

error[E0596]: cannot borrow `s` as mutable, as it is not declared as mutable
 --> e10.rs:3:5
  |
3 |     s.push_str(" world");
  |     ^ cannot borrow as mutable
  |
help: consider changing this to be mutable
  |
2 |     let mut s = String::from("hello");
  |         +++

How to read any borrow error

Find the cause line. Find the "later used here" line. Ask whether the second can happen before the first.
  1. Find the line marked "value moved here" or "borrow occurs here" — that is the cause.
  2. Find the line marked "later used here" — that is what keeps the borrow alive.
  3. Ask: can step 2 happen before step 1? That is usually the entire fix.
  4. If not: do you actually need ownership here, or would & do?
  5. Only then reach for .clone().

The compiler's help: suggestions are unusually good on these particular errors — across this guide it proposed .clone(), &names, &v[0], returning String, and adding mut. It is frequently right. Just be sure you pick the suggestion that matches your intent, rather than the first one that makes the red text disappear.

PART 18

Cheat sheet

The rules

// OWNERSHIP
// 1. Each value has one owner.
// 2. Only one owner at a time.
// 3. Owner leaves scope → value dropped.

// BORROWING
// Any number of &T, OR exactly one &mut T. Never both.
// Every reference must always be valid.

What happens on assignment

let b = a;            // a: i32     → copy,   a still usable
let b = a;            // a: String  → move,   a is dead
let b = a.clone();    // a: String  → deep copy, both usable
let b = &a;           // a: String  → borrow, both usable

Parameter forms

fn read(x: &T)          // look at it       — the default choice
fn change(x: &mut T)    // modify in place  — caller keeps it
fn consume(x: T)       // take it          — caller loses it

fn f(s: &str)            // accepts &String AND &str      ← prefer
fn f(s: &String)         // accepts only &String          ← avoid
fn g(v: &[T])           // accepts &Vec, arrays, slices  ← prefer
fn g(v: &Vec<T>)        // accepts only &Vec             ← avoid

Method receivers

fn get(&self)           // read the struct
fn set(&mut self)       // modify the struct
fn into_x(self)         // consume it — name it into_*

Iterating without losing your collection

for x in &v            // borrows      → x: &T       v still usable
for x in &mut v        // mut borrows  → x: &mut T   v still usable
for x in v             // MOVES        → x: T        v is gone

Fixes, in order of preference

Try thisWhen
add &you only need to read — by far the most common real fix
move the last use earlierE0502/E0499, where a borrow simply lives too long
wrap in a block { }you need a borrow to end at a precise point
return owned instead of borrowedE0106 on a return type
add mutE0596 — you forgot to declare it mutable
.clone()you genuinely need two independent values
If you remember one thing

Ownership answers who frees this. Borrowing answers who may look at it, and who may change it. Every borrow-checker error is the compiler telling you that one of those two questions currently has more than one answer.
